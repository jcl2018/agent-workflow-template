# Setup

Milestone: https://github.com/jcl2018/agent-workflow-template/milestone/9

Review: **Reviewed 2026-11-13** <!-- prd P=7f1b1066 R=003227cb N=9c385754 M=471a58c6 U=c8d71f6f -->

## Problem
- I want this toolset to be a workspace I can drop into any repo, for any agent: one install gives Claude Code, Codex or any agent that reads skills the same loop, docs, monitoring and settings, in the right format for each.
- Adopting a repo should never block: it should look at what is there, borrow what fits, learn from a repo I've already set up, and list what doesn't fit instead of refusing.
- Any new session should see the design logic, the docs and every command at once, and an improvement in one repo, or in the template, should reach the others.

## Usage

- `/workflow-setup setup [--dry-run] [--bare] [--from REPO [--allow KEY[,KEY]]] [--no-health] [--no-issues] [--strict]` — Adopts a new or existing repo without ever blocking: it commits the adoption on a `workflow-setup` branch (never overwriting; it makes the standing `Backlog: <Feature>` and `Backlog: Other` milestones, and asks for no other; `--dry-run` previews every file first, `--bare` writes only the config, queue and findings) with PRD pages in the docs format, the Home table, the README How to use sections, the settings with their defaults and, for a public repo with a check command, the scheduled `regression.yml` and `regression-pr.yml`; health runs on the Mac and no repo gets a health workflow. `--from REPO` borrows an adopted repo's settings shape (read-only; the unattended ones such as `auto_merge` stay `held:` until `--allow` names them). Prints `FOUND: <new|existing> repo, base <base>, ...`, `HEALTH START: <the health check's verdict, or not measured (<why>)>`, one `add:`, `convert:`, `skip:` or `no fit:` line per file, `GAP: <what and its fix>` for what setup cannot fix (a bare `agent_command`, an ignore rule outside the repo), `GUARD: <file> mentions .tsv; ...` when a repo hook might refuse the loop's `.tsv` files, `borrow:`, `adapt:`, `skip:` and `held:` lines, `would add to <private folder>: <keys>`, `WOULD FILE: adoption <kind>: ...`, then `WROTE the adoption on branch <branch> at <sha>` and `NEXT: review the branch, then merge it into <base>; ...`, or `DRY RUN: nothing written`, or `NO CHANGE: nothing to add or convert`, and always ends with `ADOPTION VERDICT: GREEN`, `GAPS (<n> warn, <n> fail, <n> unread, <n> steps failed)` after each FAIL, WARN and UNREAD line of the full health check with its fix, `not measured (<why>)` or `not run (dry run)`. What does not fit is one `[adoption]` line per kind in `.loop/findings.md` and, with `gh` signed in and a GitHub remote, one issue tagged `health:adoption` (`--no-issues` or `LOOP_NO_ISSUES=1` skips; `--no-health` or `LOOP_NO_HEALTH=1` skips the health runs). Exits 0 whenever the adoption is on its branch, 3 with `--strict` when the verdict has gaps. Refuses (exit 1) `REFUSED: git <args>: <error>` and, always rolling back (a failed git call mid-adoption too) so nothing stays written, `REFUSED: ... (SETUP_REPO_STATE)`, `(SETUP_BRANCH_DIVERGED)`, `(SETUP_WIKI_DIR)` (wiki_dir is not a folder inside the repo), `(SETUP_MIXED_VERSION)`, `(SETUP_PRIVATE_NAME)`, `(SETUP_PRIVATE_VALUE)` for a local setting or private value on a line the adoption adds, `(SETUP_HOOK_REFUSED)` when the repo's own commit hook refuses (with the hook's output and the `.loop/*.tsv` exemption to add; setup never edits that hook), `--from <path> is not an adopted repo`; exit 2 for `(SETUP_PLANNED_PATH_DIRTY)` and `(SETUP_AGENT_FILE_DIRTY)`; exit 4 `(SETUP_HALF_UNDONE)` when a restore could not finish; exit 130 when interrupted. A killed run is rolled back by the next one (`SETUP_RECOVERED`). A step after the commit that fails (`git hooks`, `private settings`, `issue filing`) prints `NOTE: <step> failed; ... (SETUP_STEP)` (issue filing: `SETUP_FILING` or `SETUP_NOT_FILED`; a failure after the commit: `SETUP_COMMITTED`; an interrupted run that had committed: `SETUP_RECOVERED`) and counts in the verdict. Under Codex (`-s workspace-write`) the git folder, the remote and `~/.workflow-loop` must be writable roots: with a read-only home setup prints `PRIVATE_NOT_WRITTEN` and still adopts the repo, and `go` is refused until the private settings exist. It installs the local schedule (a launch agent file and registry entry outside the repo; you load it by hand, see the Health page) and, with a check command, writes the scheduled `regression.yml` and `regression-pr.yml` for a public repo only (a private repo's regression runs on the Mac). It records `regression_runs` (`mac` for a private repo or one already recorded `mac`, `actions` for any other public one, left unset when visibility is unreadable) and, once the repo is registered, plans nothing new for the schedule on a rerun; it names, as `BLOCKS: <name> (...)`, every required check or rule no commit status can satisfy; it never edits a ruleset or branch protection. Without `--bare` it also inserts the README's template line and the README's and Home's Settings and Automation blocks into the adoption commit; a later render only refreshes them.
- `/workflow-setup reply-hook [--remove]` — Adds the operation session's reply-format Stop hook to the repo's machine-local Claude settings (`--remove` takes it out). Prints `HOOK: <added|updated|removed|already installed|not installed>`, plus `NOTE: start a new Claude Code session ... to load it; ...` after an install. Refuses (exit 1) `REFUSED: <script> is missing. Fix: install the workflow-monitoring skill beside workflow-setup`, `REFUSED: the hook's path <script> holds a single quote. ...`, `REFUSED: the hook (<script>) or the repo is inside a goal's worktree, ...`, `REFUSED: .claude/settings.local.json is committed, ...`, `REFUSED: <path> is not valid JSON (<error>); nothing was written. ...` and `REFUSED: <path> has hooks in a shape this can't edit safely; nothing was written. ...`
- `/workflow-setup govern-hook` — Adds the operation session's govern-only PreToolUse hook (MON-7) to the repo's machine-local Claude settings; `reply-hook` adds it too, and `--remove` takes out only it. It refuses edits, commits and pushes in the operation session; `govern_hook: false` turns it off. Prints `HOOK: <added|updated|removed|already installed|not installed> (govern_hook.py)`, plus a `NOTE:` line after an install. Refuses (exit 1) as `reply-hook` does.
- `/workflow-setup git-hooks [--remove | --check [--json]]` — Installs the private-name scan as `pre-commit`, `commit-msg` and `pre-push` hooks in the repo's git hooks folder, each calling workflow-delivery's `private.py hook` by absolute path (a default `setup` run installs them too, after scanning its own staged files; `--no-git-hooks` or `LOOP_NO_GIT_HOOKS=1` skips that). Prints `HOOK <name>: written|removed|not installed|already calls the scan|kept, it is not the stub setup writes|left alone, it is not ours. Add: <call>`, then `list: PRIVATE LIST: ...` and each hook as `installed`, `stale`, `foreign` or `missing`; `--check --json` prints the same with `"version": 1`. A hook that is not ours is never overwritten. Refuses (exit 1) `REFUSED: core.hooksPath is set, ...`, `REFUSED: private.py or the repo is inside a goal's worktree, ...` and `REFUSED: a path holds a quote, newline or percent sign, ...`, each with the line or step to fix; `REFUSED: a staged adoption file holds a private name` stops `setup` before its commit. Exit codes of the hooks: `skills/workflow-delivery/references/commands.md`, "Private-name hooks".
- `/workflow-setup settings [show [--repo DIR] [--json]]` — Shows the settings reference: every setting with its home, default and meaning; `show` instead gives each value with the layer it came from (the template's `default`, the committed `repo` file or the owner's `local` file, with a local key found in the committed config flagged), so a value that holds a private value is withheld and `env` prints names only. Prints the reference as a Markdown table, one `| <setting> | <home> | <default> | <meaning> |` row per setting, or `| setting | value | layer | home |` rows ending with `NOTE: scripts read repo values directly; a local value wins only where its own home is read`. Refuses nothing.
- `/workflow-setup fill-repo` — Adds every missing repo setting to the repo's loop config with its default, never overwriting one already there. Prints `FILLED <repo>/.loop/config.json: <settings added, or "nothing missing">`. Refuses (exit 1) `REFUSED: criteria_max is <value> in <path>. Fix: a whole number from 1 to 50 (default 10).` and `REFUSED: review_depth is <value> in <path>. Fix: full or condensed.`
- `/workflow-setup update --check [--from ZIP|DIR] [--tag vX] [--template OWNER/NAME]` — Shows what a newer template version brings and writes nothing; it reads the base branch's config from `origin/<base>` before the local branch, so a checkout on any other branch, or with no local `main`, still finds it. Prints `INSTALLED: <v>`, `AVAILABLE: <v>`, `REPO: template_version <v>` (or `..., older than <v>: run update --apply`), the changelog under `WHAT'S NEW:`, an `add:`, `update:` or `remove:` line per skill file, a `LOCAL FIX: <file>` line per skill file edited here, and ends with `UP TO DATE` (exit 0) or `PREVIEW: nothing written. Ask for workflow-setup update to apply` (exit 1, behind). Refuses (exit 2) `REFUSED: no template repo is known (UPDATE_NO_TEMPLATE)`, `REFUSED: gh can't read <repo> releases: <why> (UPDATE_GH)`, `REFUSED: ... (UPDATE_TEMPLATE_MISMATCH)` and `REFUSED: can't read a package at <source>: <why> (UPDATE_BAD_ARCHIVE)`, each with its fix.  Its file locks use `fcntl`, or `msvcrt` byte-range locks where `fcntl` is missing (native Windows Python).
- `/workflow-setup update [--take FILE] [--from ZIP|DIR] [--tag vX]` — Applies it: writes the new skills (a local fix is kept and printed `KEPT: <file>`; `--take FILE` takes the package copy), then this repo's missing settings (with the three built-in routines declared on the repo's Mac task), `template_version`, the entry point, the agent blocks and the Settings and Automation blocks and README line the repo lacks, on branch `workflow-update-v<v>` cut from the base branch. Prints `UPDATED skills to <v>`, `WROTE the repo half on branch workflow-update-v<v> at <sha>: <files>` and `NEXT: merge workflow-update-v<v> into <base> ...` (exit 0), or `PENDING: workflow-update-v<v> is not merged into <base>; merge it` (exit 1). Refuses (exit 2) with `UPDATE_SKIPPED_REPO`, `UPDATE_BRANCH_MERGED`, `UPDATE_PARTIAL` or `UPDATE_LOCKED` and the fix; against a checkout it prints `SKILLS: <folder> is a checkout; update it with git pull (UPDATE_CHECKOUT)` and still writes the repo half. If the commit step is interrupted, update ends git's whole process tree (taskkill /T on native Windows).
- `/workflow-setup update --propose [--file-issue]` — Previews one issue proposing each local fix back to the template: prints `TITLE: Fix from an adopted repo: <files> (<hash>)`, the diff and `PREVIEW: nothing filed` (exit 0); `--file-issue` files it and prints `FILED: <url>` (exit 0) or `ALREADY FILED: <url>` (exit 1). Prints `NOTHING TO PROPOSE ... (PROPOSE_NONE)` when no skill file differs. Refuses (exit 2) `REFUSED: the proposal holds <kind of match> (PROPOSE_SCRUB)` when it names the repo, its owner, the user or a private pattern, and `REFUSED: gh couldn't file the issue (PROPOSE_GH)`, each saving the draft with the fix.
- `/workflow-setup agents [--dry-run]` — Writes the same workflow-loop block into each file `agent_files` names (CLAUDE.md and AGENTS.md by default), replacing only the block. Prints `WIRED <file>` (or `WOULD WIRE <file>`) per file, or `NO CHANGE: every agent file holds the current block` (exit 0). Refuses (exit 2) `REFUSED: <file> has one workflow-loop marker without the other (AGENTS_MARKER)` and `REFUSED: <file> resolves outside the repo (AGENTS_OUTSIDE)`, each with its fix.
- `/workflow-setup migration-check [--repo DIR] [--pr] [--offline]` — Judges whether a repo is fully migrated to the current template and writes nothing: the working tree's files setup writes, the settings table, the Settings and Automation blocks and README line, the `automation` routines and the one local `<repo>-health-regression` task (4 hours or sooner), a pull-request check, the PRD format and Runbooks, the `template_version`, and the published wiki. Prints one `GAP <CODE> <subject>: <what>. Fix: <one-line fix>` per gap, then `NOT CHECKED:` (always branch protection, which no gh read covers), `CHECKED:` and `DOCS:` lines, and last `MIGRATION OK` or `MIGRATION: N gap(s) (a PR-closable, b state)`, with `(--pr: state codes not checked)` or `(offline: wiki not checked)` after it when a flag skipped part. Exit 0 only with no gap, 1 for gaps, 2 for a usage error, 4 when the check could not run (workflow-health missing, or an unexpected error: the line names a private trace file). It also judges the format changes the installed template carries (`MIG_USAGE` a feature page still holding a Usage section, `MIG_RULES` no `.loop/health-rules.json`, `MIG_ROUTINES` an installed scheduled prompt holding more than its Runbook pointer, a state code; each is skipped while the template does not carry the feature), a reply or govern hook installed twice (`MIG_HOOKS`, a state code), and prints what only the owner can do as `OWNER STEP <kind> <name>: <exact instruction>` lines (gh sign-in `gh auth login --web`, a hook not installed, approving the Backlog milestones, the platform smoke cell, and a node or python the repo asks for in `engines`, `.nvmrc`, `.tool-versions` or `requires-python`, with the `winget`, `brew` or `nvm` command), then a `CHECKLIST:` line; an owner step never makes the check fail, and `--pr` skips them. Codes, class and cause: `MIG_VERSION`, `MIG_FILES`, `MIG_SETTINGS`, `MIG_BLOCKS`, `MIG_AUTOMATION`, `MIG_RUNBOOK`, `MIG_FORMAT`, `MIG_CHECKS` are PR-closable (`--pr` checks only these, which is the migrate goal's done line); `MIG_TASK`, `MIG_WIKI_ORPHAN`, `MIG_WIKI_STALE`, `MIG_WIKI_UNREADABLE` are state codes that close on the Mac or in the wiki after the merge (`automation.py local install`, then the owner removes each orphan wiki page named and runs `docs.py publish`; the check lists and never deletes). `--offline` skips the three wiki codes; off a Mac the task check prints `SKIP MIG_TASK (not a Mac)` and is not counted. `LOOP_MIGRATION_ONLINE=1` makes health's migration rule read the wiki too (the 4-hourly run sets it); a repo that deliberately differs says so with an explicit off setting (`health_cron`, `regression_cron`, `digest_mail`), and a standing difference is one open issue, not a stream. Unfollowing a repo in `~/.workflow-loop/repos` also drops it from the Issues version lines. Test-only: `LOOP_TEST=1` with `LOOP_INSTALLED_VERSION`, `LOOP_SCHEDULE_PLATFORM` and `LOOP_SCHEDULE_HOME`. Example of a clean run: `NOT CHECKED: branch protection (no gh read)`, `CHECKED: installed v1.0.0, repo template_version 1.0.0 (working tree), platform darwin, mode online`, `MIGRATION OK`. Example of a gap: `GAP MIG_VERSION template_version: none is set (read as 0.0.0), the template is at v1.0.0. Fix: run the migrate goal (update.py --apply stamps it)`. It needs workflow-health beside workflow-setup. `entry.py lag` prints the one version line (`this repo is at vY, the template is at vX, run the migrate goal`) that `goal.py new` and the entry check show; `goal.py new` refuses only when the majors differ, and a `migrate-` slug is let through. A folder named `<repo>-health-regression` under `~/.claude/scheduled-tasks` counts as the repo's local task (no `MIG_TASK` gap), and a `regression_runs: mac` repo is never asked for `pull_request` in `regression.yml`.

## Requirements

### Functional
- SET-1: **Reviewed 2026-11-13** One command adopts a repo <!-- reviewed 8cd2a972 -->
  - One command sets up a new or existing repo: the loop config, PRD feature pages in the docs format, the Home table and README How to use, the nightly regression in GitHub Actions, the health groups, and every setting with its default.
  - It shows what it found and would change first, then applies it on a branch through the loop, adapting what is there instead of overwriting.
  - It never blocks: what doesn't fit is listed and filed as issues tagged with the right feature, and the rest is adopted.
  - Health is the first and last step: before adopting, a health check records where the repo starts; after adopting, the full health check (every group, Adoption included) must come back green or name each gap with its fix, and that verdict is the adoption result, because if health works, the rest works.
- SET-2: **Reviewed 2026-11-10** Layered settings <!-- reviewed 4adab145 -->
  - Settings come in three layers: the template's defaults, the repo's settings (committed and shared), and my local settings (private, outside the repo); a later layer overrides an earlier one.
  - Every setting has a default and a one-line explanation; I can see each setting's value and which layer it came from, and change any of them at any time.
- SET-4: **Reviewed 2026-11-10** Updates flow both ways <!-- reviewed 22b1453a -->
  - An adopted repo can check for a newer template version, see what's new and update, keeping its own config, pages, rules and local settings.
  - The operation session flags any governed repo running an older template version.
  - A fix made in an adopted repo that belongs in the template is proposed back to the template as an issue.
- SET-5: **Reviewed 2026-11-10** A self-describing workspace <!-- reviewed 5cce9f58 -->
  - Every adopted repo has one entry point that any new session reads first: how the loop, release, operation and workers, docs, regression, health and settings fit together, and which features exist and how to use them.
  - It is generated from the PRD pages and settings, so it is never stale.
- SET-6: **Reviewed 2026-11-10** Adoption is proven <!-- reviewed 48224f33 -->
  - Adoption is proven on test repos shaped like real ones (existing checks, CI tests, a blocking .gitignore, a bare agent command, features that aren't folders), and every adoption defect found in a real repo adds a test repo that reproduces it.
- SET-9: **Reviewed 2026-11-10** Learn from a repo already set up <!-- reviewed c1f9b120 -->
  - Setup can take an adopted repo as its model: it borrows that repo's settings shape, flow, milestone layout and private rules (never private values) and adapts them to the new repo.
- SET-10: **Reviewed 2026-11-10** The right format for every agent <!-- reviewed 06345b05 -->
  - The same skills are wired into each agent's own entry files (for example CLAUDE.md and AGENTS.md), so Claude Code, Codex and other SKILL.md agents run the same loop the same way.
- SET-11: **Reviewed 2026-11-13** Prerequisites first, then a strict replay of the first adoption <!-- reviewed 3d61b462 -->
  - Before it writes anything, setup prints one checklist of what this machine needs: git, python3, gh installed and signed in as me, real symlinks, and a supported platform (no crash on a missing POSIX call, and the qa lane runs on this platform instead of hanging). Each line that fails carries its exact fix, for example the install command, or `gh auth login` run with a device code I can enter from my phone instead of a prompt waiting at the PC.
  - Adoption then replays the first run step by step against its golden result (`dev/toy/adoption-golden.tsv`, eight steps from prerequisites to the first check-in). It stops at the first mismatch, says what differs and asks me to do the exact step that fixes it; it never accepts a looser equivalent.
  - Comes from [#1408](https://github.com/jcl2018/agent-workflow-template/issues/1408), with the Windows crashes in [#1395](https://github.com/jcl2018/agent-workflow-template/issues/1395), [#1396](https://github.com/jcl2018/agent-workflow-template/issues/1396) and [#1397](https://github.com/jcl2018/agent-workflow-template/issues/1397).
- SET-12: **Reviewed 2026-11-13** Adopt all my repos in one pass <!-- reviewed e8a784e2 -->
  - From the operation session, one flow lists my GitHub repos by last push, private ones included, lets me choose which to follow, clones them into one folder, registers each with the board and updates each to the current template version.
  - It ends with the board showing exactly the repos I chose and none of them on an unknown or older template version.
  - Comes from [#1409](https://github.com/jcl2018/agent-workflow-template/issues/1409).
- SET-13: **Reviewed 2026-11-13** Workers are app sessions I can see <!-- reviewed ea44c41d -->
  - When I've chosen app sessions, a goal never falls back to a background worker: it waits for a free session and says so, including when the app refuses to start one because my message came over Remote Control.
  - The pool is kept at `pool_size` sessions (MON-12): it asks me to fill it only when it runs low, and never starts more than that.
  - Worker and pool sessions start on the model one setting names, and the operation session sets it on every session it starts or reuses.
  - The reply and govern hooks are installed exactly once each, however many times setup or either hook command runs.
  - Comes from [#1404](https://github.com/jcl2018/agent-workflow-template/issues/1404).
- SET-14: **Reviewed 2026-11-13** The connectors each repo needs are checked <!-- reviewed c52f6df9 -->
  - For each followed repo, setup reads which connectors its PRDs need (mail accounts, a calendar, a file store, a notification channel) and probes each with a read-only call.
  - It prints each as connected, needs sign-in or missing, with the fix, and names the owner-written files a repo needs that don't exist yet. It never attaches or enables a connector itself: I do, with the narrowest access.
  - Comes from [#1410](https://github.com/jcl2018/agent-workflow-template/issues/1410).
- SET-16: **Reviewed 2026-11-13** A repo is judged fully migrated by one command <!-- reviewed 66eb89ce -->
  - One read-only command lists every gap between a repo and the current template, each with a one-line fix, and exits 0 only when none remain; it writes nothing, and health's Adoption group runs the same check.
  - A repo carries `template_version` (set by update) and one with none counts as behind; a session that starts in a repo behind the installed template is told so in one line and never blocked, except that a new goal is refused when the major version differs.

### Non-functional
- SET-3: **Reviewed 2026-11-13** Shipped as a versioned package. <!-- reviewed 4ddb26bd -->
  - The template ships as one versioned package of separate skills in the Agensi format, every script self-contained and under 20 KB. It works out of the box with a built-in default flow, and is proven to run in both Claude Code and Codex on a clean test repo with no private settings.
- SET-7: **Reviewed 2026-11-10** Safe and repeatable <!-- reviewed fb39932b -->
  - A dry run lists everything before any write; running setup twice changes nothing the second time; nothing existing is overwritten.
- SET-8: **Reviewed 2026-11-10** Private stays private <!-- reviewed 22a16ae7 -->
  - Local settings and private values are never written into the repo, and setup refuses to commit a file that holds one.
- SET-15: **Reviewed 2026-11-13** One private-name list that fits every repo <!-- reviewed 3f8e2427 -->
  - When setup seeds the private-name list, it explains that the list covers every repo on this machine, so a private repo's own name, or a contact it cites on purpose, would block that repo's own commits.
  - A pattern can be scoped, for example to public repos only or to named repos, so a private repo can hold what a public one must never show.
  - Comes from [#1411](https://github.com/jcl2018/agent-workflow-template/issues/1411).
- SET-17: **Reviewed 2026-11-13** The Backlog milestones exist after adoption <!-- reviewed e4d6023c -->
  - Adoption creates one milestone "Backlog: <Feature>" for each feature page and "Backlog: Other", and creates none that already exists. Health's Adoption group warns for each one that is missing.

## Non-goals
- It never commits private settings or values.
- An update never overwrites a repo's own config, requirements, docs or local settings.
- It doesn't rewrite a page that has its own sections; that page is listed for a person.

## Success metrics
- One command adopts a fresh or existing repo with no blocking step, and the health check run right after it is green or names every gap with its fix.
- A new session in an adopted repo can name every feature and how to use it from the entry point alone.
- A template update reaches every governed repo without losing any repo setting or page.
