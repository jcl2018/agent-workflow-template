Done lines (frozen, `.loop/goals/lane-plan-cache.md`): 1) planning under 60 s at load 20 or more on a repo of the size where #710 was measured, shown in the lane's `.times` record; 2) planned row set byte-identical to today's, shown on fixture repos with and without the cache; 3) cache keyed by HEAD, invalidated when HEAD or the row file changes, a test moves HEAD; 4) a regression row reproduces #710, seen failing before and passing after; 5) lanekit.py's copies equal slots.py, scripts under 18 KB, package at 99 files or fewer.

## Problem Statement

Issue #710: a lane's planning step (`tiers.plan`, called by `regression.py run land --reuse --tier goal`; the qa, ship and pr lanes each plan) can use the whole preparation budget before one row runs. On a large consumer repo, under load average 24 to 38, planning took 600 to 900 s and lanes were cut with "planning ran long". The mitigation so far is a raised `prep_budget_minutes` (25) in that repo, which hides the cost and makes every cut lane a 15 to 25 minute loss.

The issue says the cause is a repo scan per row (closure, references). The measurements below say the larger part is something else.

## What Makes This Cool

One wrong default argument costs 80 to 99% of the planning time on this repo and on synthetic fixtures (the large-repo effect is an inference until the by-hand step). Fixing it takes planning from minutes to about a second, and the cache that the done lines ask for then only has to be cheap and safe, not clever.

## Evidence (measured on this repo and on synthetic fixtures; no private repo or store was read)

Profiled `tiers.plan` with `subprocess.run` counting `git` calls, at load average 13 to 29. "Fix A" is the one-line memo fix, "A+B" adds the walk memo.

| Fixture | Rows | Files | Base | Fix A | A + B |
|---|---|---|---|---|---|
| this repo, real land rows | 498 | 381 | 36.5 s, 1,004 git calls (29 s in git) | 8.7 s, 10 calls | 3.3 to 5.3 s |
| synthetic, narrow and wide rows | 1,500 | 6,362 | 111 s, 3,009 calls (110 s in git) | 1.4 s, 11 calls | 1.5 s |
| synthetic, wide rows and a big folder | 800 | 8,662 | 247 s, 4,809 calls (246 s in git) | 0.9 s, 11 calls | 1.2 s |

- Base git calls are exactly 2 per row plus a constant (`diff` and `status` each 500 for 498 rows); after fix A they are 3 `diff` and 3 `status` in total, whatever the row count.
- Root cause 1 (a plain bug, `tiers.py` line 77): `memo.setdefault("from", {}).setdefault(commit, lanes.changed(root, commit) or [])` evaluates its default argument on every call, so `lanes.changed` (a `git diff` plus `lanes.dirty`, a `git status --untracked-files=all` over every file) runs once per row and all but the first result are thrown away. `tiers.since` calls it for every row. `lanes.plan` memoizes the same call correctly (`since` dict), so only the goal tier has the bug.
- Root cause 2 (real but small here): the closure and reference work is per plan, and `lanes.walk` (os.walk of a widened folder) is repeated per row inside `wide_closure`, `names_any` and five places in `narrow.py`. cProfile of fix A: `narrow.narrow` 4.5 of 7 s, `references` 25,576 calls with 272k `stat` calls. Memoizing `walk` per plan took 8.7 s to about 5 s here.
- Inference, not measured: at 37 to 51 ms per `git status` on 6 to 9 thousand files (idle to moderate load) and 0.3 to 0.75 s per call on a large repo at load 24 to 38, 1,000 to 2,000 calls is the 600 to 1,500 s that #710 saw. The stack dump in #710 pointed at `closure` because that is where the sampler found the process; the git time is spent in child processes.
- Planning seconds are already measured and shown: `lane.py lane_exec` writes `.times` (`plan`, `wait`, `cut`) and `lanekit.before_rows` prints "planning Ns" on every LANE line. Done line 1 needs no new instrumentation.
- Size facts: `dev/package.py` caps the shipped files at 99 (`skills/`, listing.json, README.md, LICENSE count 99 today) and each script at 20,480 bytes; health warns at 18,432. 27 scripts are already above 18,432 (lanes.py 19,559, actions.py 19,768, lanekit.py 20,007); tiers.py is 13,619, narrow.py 14,278.

## Constraints

- No new file under `skills/` (the package is at 99). New code goes into existing scripts with room: tiers.py (about 4.8 KB below the warn line), narrow.py. Test and fixture files live under `dev/toy/`, which is not shipped.
- lanes.py, actions.py and lanekit.py must not grow. lanekit.py's copied functions stay equal to slots.py (`test-lane-control.sh`); this change touches neither slots.py nor lanekit.py.
- The planned row set must not change. A cache that makes a row skip when it should run is a false green, so the cache fails open (any doubt means recompute) and a dirty tree never uses it.
- Standard library only; deterministic fixtures; the `land` regression rows must stay fast and not flaky under load.
- Privacy: nothing in the repo, fixtures or messages names the private repo; fixtures are synthetic.

## Premises

1. "The time is the repo scan per row." Mostly wrong. Git subprocess calls are 80 to 99% of planning time in every fixture; the per-row `changed` bug is the root cause. Agree with the issue's remedy (compute once, not per row), disagree with its attribution. This changes the order of work: fix the memo first, prove it, then the cache.
2. "A cache keyed by HEAD is the fix." No: fix A alone takes 111 s to 1.4 s. The cache is required by done line 3 (frozen) and still pays for reruns of a cut lane and for the closure cost on a repo with big folders, so it stays, kept small and fail-open. Agree, with the cache second in value.
3. "The planned row set must be byte-identical." Agree, and it is the main risk: a stale closure would skip a row. Identity is proven four ways (below), not by reasoning.
4. "Time is best measured in seconds." Disagree for the gating row: seconds move with load (the same plan took 36 to 80 s on this repo). The land row counts `git` calls per plan (flat in the row count); seconds appear only in a nightly row with a 30x margin.
5. "Doing nothing is acceptable." No: every cut lane costs a rerun, and the workaround (prep budget 25) hides the same cost at the next 2x of rows or load. Real pain, not hypothetical.
6. Reuse: `lanes.plan` already memoizes `changed` correctly; `.times` and the LANE line already carry planning seconds; `lanes.runner()` already hashes the planner's code and `record_path` already names the per-branch store; `LANES_WIDE=1` is the precedent for an env switch. No distribution work: the fix ships inside the skill package through the normal release.

## Approaches Considered

APPROACH A: fix the eager setdefault only (minimal viable)
  Summary: memoize `tiers.changed` with an explicit `if commit not in memo`.
  Effort: S. Risk: Low.
  Pros: one line, output provably unchanged (the first result was already the one kept); 111 s to 1.4 s measured.
  Cons: no cache, so done line 3 is unmet; closure and walks still repeat per row and per lane.
  Reuses: the `since` pattern in lanes.plan.

APPROACH B: A plus a per-plan `walk` memo
  Summary: `lanes.walk(root, prefix, cache)` keeps its listing in the plan's own `cache` dict.
  Effort: S. Risk: Low.
  Pros: removes the repeated os.walk (about 40% of what is left here, more with big folders); lifetime is the plan, so no stale state and no module global.
  Cons: touches lanes.py (offset to net zero bytes) and five calls in narrow.py; done line 3 still unmet.
  Reuses: the existing `cache` dict that every closure function already receives.

APPROACH C: B plus a persisted closure cache per branch (ideal architecture, recommended)
  Summary: after a clean plan, store the per-row closure results in `<git common dir>/loop/plans/<branch>-<sha8>.json`; the next plan with the same key loads them instead of computing.
  Effort: M. Risk: Medium (a wrong hit is a skipped row), contained by the key, the dirty bypass, fail-open reads and four identity proofs.
  Pros: meets done lines 1 to 4 as written; the qa, ship and pr lanes of a goal and every rerun of a cut lane skip the closure work; one place for the PLAN_CACHE note.
  Cons: a new state file to prune; about 2.2 KB more in tiers.py; ignored files are not in the key (below).
  Reuses: `lanes.record_path` naming, `lanes.runner()` digest, atomic temp plus `os.replace` as in `lanes.save`.

APPROACH D: replace the per-row `git status` with one call and `os.walk` with `git ls-files`
  Summary: batch the git work and list only tracked files.
  Effort: M. Risk: High.
  Pros: fewer git calls than A (3 `status` become 1).
  Cons: `ls-files` omits ignored and untracked files that `os.walk` sees, so closures and the row set can differ (done line 2 breaks); A already makes the git calls constant, so the saving is two calls.
  Rejected: byte-identity is the hard constraint and the gain is two calls. The 3 to 1 status merge stays an optional follow-up if the by-hand measurement shows git status dominating.

APPROACH E (lateral): cache the finished plan (selected rows) by HEAD and diff
  Summary: store `todo` and `reused` instead of closures.
  Effort: M. Risk: High.
  Pros: a hit skips everything.
  Cons: the plan also depends on the lane record (each lane rewrites it), so the key churns and hits are rare; a wrong hit skips rows directly.
  Rejected: closures are stable across record changes and a miss costs one second after A; a plan cache saves little and risks more.

Also rejected: raising `prep_budget_minutes` (status quo; hides the cost).

RECOMMENDATION: C, built in three commits so each is green: (1) fixtures, golden plans from the unchanged v0.27.6 scripts and the #710 row seen failing; (2) fixes A and B; (3) the persisted cache C.

## Recommended Approach

Decisions, one bullet each with its why.

- Fix `tiers.changed` with a real membership test. Why: the root cause; the first result was already the one kept, so output is identical.
- Memoize `lanes.walk` through a third `cache` parameter (default none) used by `wide_closure`, `names_any` and the five `narrow.py` calls. Why: every caller already holds the per-plan `cache`; no global means no stale listing; lanes.py ends at or below 19,559 bytes (hard cap 20,480) by trimming prose in its docstring and comments (a test ratchet enforces it); fallback if the trim cannot cover it: keep `walk` unchanged and wrap it with the same per-plan memo from narrow.py or tiers.py.
- Put the persisted cache in tiers.py (`key`, `warm`, `store`, about 2.2 KB; tiers.py ends near 16 KB, under the warn line). Why: tiers.py is the only planner that needs it, has the room, and keeps lanes.py and the lanekit copy contract untouched.
- Cache file: `<git common dir>/loop/plans/<branch>-<sha8>.json`, same name rule as the record, not under `loop/tests/`. Why: `lean.py` and `controls.py` glob `loop/tests/*.json` as lane records.
- Content: zlib-compressed JSON `{v, key, paths, rows: {command: [path indexes, always, why, table]}}`; only the closure of each row command (deps, always, why, table flag). Why: measured 5.0 MB as plain JSON for 498 rows, 72 KB interned and compressed; the closure is a pure function of the command and the tree, so it is stable across lane-record changes. `zlib` is stdlib and not on the package scanner's obfuscation list.
- Key: sha256 of schema, `lanes.runner()` (digest of regression.py, lanes.py, narrow.py, runs.py, tiers.py), HEAD sha, sha256 of `.loop/regression.tsv`, and `LANES_WIDE`. Why: HEAD and the row file are the done line; the runner digest drops caches written by older planner code; `LANES_WIDE` changes the closure.
- A goal's lanes plan on a clean tree by construction: `lanekit` refuses a lane that starts dirty (`LANE_DIRTY at start`, only the re-rendered Tests tables are committed first as the prep commit) and `lane.py` fails a lane whose rows leave files (`LANE_DIRTY at end`), so the bypass costs the cache nothing in the normal qa, ship and pr sequence. Fixture row `lane-plan-cache:3` runs two consecutive plans on a clean tree and asserts `PLAN_CACHE: hit` on the second, and a plan after a stray untracked file asserts `dirty`.
- A non-empty `lanes.dirty(root)` bypasses the cache (no read, no write). Why: closures read working-tree files; a dirty tree is exactly "HEAD plus a diff the key cannot see". One extra `git status` per plan, constant.
- Ignored files are not in the key (known limit). Why: neither HEAD nor `git status` sees them, so the done line's own definition ("same HEAD and diff") excludes them; a changed ignored file in a closure folder is a rare edge, documented in Regression.md.
- Fail open: unreadable, corrupt, wrong-version, wrong-key or wrongly shaped cache files are ignored and recomputed, never an error. Why: a cache must never block or mis-plan a lane.
- Write atomically (temp plus `os.replace`), no lock, last writer wins; prune files older than 30 days in `loop/plans/` at write. Why: concurrent lanes of one branch write self-consistent files for the same key; no unbounded store.
- `LANES_NO_CACHE=1` turns the persisted cache off (the per-plan memos stay). Why: the "without the cache" arm of the identity test and an owner escape hatch, same style as `LANES_WIDE=1`.
- One extra output line `PLAN_CACHE: <state> (...)`, printed first. States: hit (loaded and used), miss (no usable file or key differs; computed and written), dirty (tree not clean; bypassed), off (`LANES_NO_CACHE=1`), none (no branch, so no record path; nothing persisted). `<sha8>` is the first 8 hex of sha1 of the branch name, as in the record's name; temp files are `<name>.<pid>.tmp`, unique per writer, so concurrent lanes cannot interleave.
- The line is printed first, before the notes and the kind line. Why: a lane log shows whether the cache helped; the row set lines after it stay byte-identical, and `lanekit`'s ROWS parser is unaffected. Tests drop that one line before comparing.
- Planning seconds: no new code; `.times` and the LANE line already print them. Why: done line 1 is "printed in the lane's .times record".

## How identity is proven (done lines 2 and 3)

1. Golden: commit the plan output (all lines but PLAN_CACHE, plus the returned lists) of deterministic fixture repos planned with the unchanged v0.27.6 scripts, before any fix. The fixtures cover narrow and wide rows, a root runner, an unmapped path, a deleted path, a base merge, a usable record and no record. After the fix the cold, warm and `LANES_NO_CACHE=1` plans each equal the golden.
2. Three-way on every fixture: cold (writes the cache), warm (reads it) and off produce equal output.
3. HEAD move (done line 3): plan at HEAD1 and write the cache; commit an edit that gives row A a new reach edge to module B; commit a change to B; plan at HEAD3. Expect `PLAN_CACHE: miss` and A selected "reaches B", equal to the off plan; a stale HEAD1 closure would not select A.
4. Fail-open and bypass: a garbled cache file, a cache with a flipped key, and a dirty tree each plan equal to the off plan (`PLAN_CACHE: miss` or `dirty`). A direct call of `key()` with an edited row file differs (done line 3's row-file clause).
5. Self-run: this repo's own rows planned cold and warm, equal (not golden; it moves with HEAD).

## How time is measured and the #710 row stays fast and not flaky

- Generator `dev/toy/plan-fixture.py` (stdlib, deterministic: fixed content from the index, fixed commit dates and identities, no random): `--rows N --skills S --modules M --docs D --app F` builds a git repo with S skill folders of M linked modules, `# reads:` test scripts (70% narrow, 30% wide, wide ones naming a big `app/` folder when `--app` is set), the rows table, a base commit on main and a feature commit that touches a few files. The scratch generator used for the table above is the prototype.
- Land row `lane-plan-cache:4` (category defect, link to #710): plan 20-row and 120-row fixtures with `LANES_NO_CACHE=1` (so a warm cache cannot mask fix A) and a PATH shim `git` that logs each call; assert calls(120) minus calls(20) is at most 2 (the tally is constant: 3 diff, 3 status, plus the dirty status, merge-base and show calls, the same at both sizes) and calls(20) is at most 30. Base grows by 200 (2 per row): fails. Counting calls is independent of load and of the machine's speed, and the two fixtures take about a second to build. The shim sees every git call however it is spawned.
- Seen red: `regression.py red lane-plan-cache:4 --break-it 'git checkout 6b0f23c -- skills/workflow-regression/scripts/tiers.py skills/workflow-regression/scripts/lanes.py skills/workflow-regression/scripts/narrow.py'` (the v0.27.6 planner), which makes the growth appear.
- Nightly row `lane-plan-cache:1` (done line 1): generate 1,500 rows and about 6,400 files, start 20 busy loops (as `test-operate-load.sh` does), plan cold, assert under 60 s. Base took 111 s at load 13 to 29 on this laptop, fix A about 1.5 s: a 40x gap, so it does not flake. Nightly level so land lanes do not pay for it.
- The by-hand step measures the real large repo (below), because this worker never reads it.
- Land rows `lane-plan-cache:2` (identity, proofs 1 to 5), `lane-plan-cache:3` (HEAD move, tamper, dirty, row-file key), `lane-plan-cache:5` (sizes: lanes.py at most 19,559, actions.py at most 19,768, lanekit.py at most 20,007, tiers.py and narrow.py under 18,432, shipped files at most 99, lane-control copy check still green). Rows keyed `slug:N` render in docs/wiki/Tests.md, which the goal's Touches already lists with Regression.md.
