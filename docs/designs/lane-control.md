# Design: Test lanes run safely side by side and never go stale after a merge (lane-control)

## Problem Statement
A goal's regression lane (`role.lane()` in skills/workflow-delivery/scripts/role.py, running
`regression.py run land --reuse` in a background `lane-exec` child) is shared machine state that each caller treats as
private:

- **150:** with six worktrees running full lanes at once (load ~40), lanes hit the 2700 s limit even though every row
  they reached passed. One or two lanes at a time finish in 20-30 minutes.
- **135:** parallel `regression.py red` runs read regression.tsv, run for minutes, then write the whole file. The last
  writer wins and seen-failing dates are lost.
- **152:** a lane's exit status lives in `<slug>.<name>-lane.<attempt>.rc`. A watcher can't know the attempt, so it
  waited on the wrong name and never fired.
- **168:** after merging main, ship would have recorded against a lane `.ok` that named the pre-merge HEAD.
- **151:** rerunning rows by id writes new PASS dates into `.loop/regression-runs.tsv`, so the wiki Tests tables go
  stale and the next lane fails the docs-freshness row. Merging main does the same.
- **99:** the operate-all toy test fails about 1 run in 3 under load. It uses fixed waits (15 s caps, a 5 s settle loop
  and a fixed 1.5 s quiet window) where it should wait on the goal's report.

Frozen done lines (.loop/goals/lane-control.md) — the design meets them as written:
1. A machine-wide lane limit (a setting, default 2) makes an extra full lane wait its turn with a clear message instead of starting; flow.py and goal.py honor it (150)
2. Parallel red runs never race on .loop/regression.tsv (135)
3. A lane's latest result has one stable path, and a wait command blocks until it ends (152)
4. ship and pr rerun or refuse when HEAD moved since the lane they reuse (168)
5. Rerunning rows by id and merging main never leave the Tests tables stale for the next lane: the lane re-renders them first (151)
6. The operate-all test waits for the goal's report instead of a fixed sleep and passes 10 of 10 under load (99)
7. A toy test proves each, seen failing on the old code; the issues close when this merges

## What Makes This Cool
Six goals can start lanes at the same moment and none of them times out. The third full lane prints one line saying
who holds the slots, then starts the moment one frees, and its 2700 s clock starts then, not before. A watcher can
always find "the latest result" at one fixed path. A by-id rerun or a merge can never fail the next lane over stale
tables.

## Constraints
- Python 3 standard library, bash and git only. Each script stays under 20 KB: regression.py is 19,968 bytes, goal.py
  18,955, role.py 17,711. New logic goes in sibling modules, and regression.py must shrink to make room.
- Touches skills/workflow-regression, skills/workflow-delivery, dev/toy, .loop/regression.tsv and docs/wiki.
  - **One line outside the declared paths:** registering the new private setting `lane_limit` in
    skills/workflow-setup/scripts/settings.py (SET-2 requires every setting to be listed with a default and a one-line
    explanation). Flagged to the operation session.
- The installed skills are never edited. A lane never pushes. Before starting a lane, the foreground caller may make
  exactly one kind of commit: the re-rendered Tests tables and the run-dates file they are rendered from
  (`.loop/regression-runs.tsv`) (done line 5).
- Every caller honors the limit: flow.py qa/ship, goal.py pr, `role.py lane` and a human typing `regression.py run land`.

## Premises
1. All six issues come from shared lane state that callers treat as private, so each fix goes into the shared function
   every caller already uses. Agreed (auto).
2. Only a FULL lane takes a slot. It takes the slot inside `regression.py run`, where the plan (FULL, AFFECTED or
   REUSED) is known. The lane's time limit starts when the slot is acquired, so a queued lane can't time out.
   - Revised after the second opinion: `lane_exec` used to time the whole child process, which would have counted
     queue time against the limit.
3. Before the lane starts, the foreground lane call re-renders the Tests tables and commits the result, never the
   background child. So the lane still tests committed HEAD, and the child never moves HEAD under its own job.
   Agreed, made precise after the second opinion.
4. New code goes in new modules: `skills/workflow-regression/scripts/slots.py` (slots and file locks) and, if role.py
   would pass 20 KB, `skills/workflow-delivery/scripts/lane.py` (the lane machinery moved out of role.py, which
   re-exports it). Agreed.
5. `lane_limit` is a private machine setting in the flow file (`~/.workflow-loop/flow.json`, or `$LOOP_FLOW`). The
   default is 2, and 0 means unlimited. `LOOP_LANE_LIMIT` overrides it for one process, which the tests use. Agreed.
6. Issue 172 (narrowing reruns further) is not needed for these done lines and stays its own follow-up. Agreed.

## Cross-Model Perspective
Second opinion: Claude subagent, cold read. Codex could not run: its model isn't supported on this account.
- **Critical, accepted:** taking the slot inside regression.py, as first stated, makes queue time count against the
  limit, because `lane_exec` runs `child.wait(timeout=limit)` around the whole run and `live()` gives up at
  `started + limit + 60`. Premise 2 is revised: regression.py writes a slot-acquired marker, `lane_exec` starts its
  clock from it, and `live()` knows a queued state.
- **Medium, accepted:** committing from the background lane would move HEAD while the job runs, and `lane()` would kill
  and restart its own lane. The commit happens in the foreground `lane()` call, before the child is spawned.
- **High, partly accepted:** use content-addressed receipts (`<sha>.<cmdhash>.json`) so stale results can't be
  reused.
  - Taken: one stable latest-result file per lane (`.last`), and record checks that compare against HEAD.
  - Not taken: replacing `.ok` and lanes.py's per-branch record with a new receipt store. It changes the reuse
    contract that test-lanes built and that the ship tooling's receipts rely on. It's more than these done lines need.
- **Medium, rejected:** take the PASS dates out of the committed Tests tables instead. The tables showing each row's
  last status and date is a docs contract (REG and DOC pages). Done line 5 names "the lane re-renders them first".
- **Agreed 50% tool:** `fcntl.flock` on N slot files. The kernel frees a dead holder's lock, so there are no stale
  slots. lanes.py already uses flock for its record.

## Approaches Considered
### Approach A: patch each place (minimal)
A lock at each call site, a slot check in role.lane only, and the test fix. Rejected: a human's
`regression.py run land` would ignore the limit, three call sites would need to stay in step, and regression.py has no
room left.
### Approach B: shared lane control (chosen)
Detailed under Recommended Approach. Effort M-L (CC about 2-3 hours, human about 2 days). Risk Med: the queued-state
timing and the prep commit.
### Approach C: a lane daemon
A single queue runner that workers submit lanes to. Rejected: a new long-lived process and a single point of failure,
for what the kernel's flock already gives.

## Recommended Approach
B. Each part below maps to one done line.

**1. Lane slots (done line 1, issue 150): `slots.py`, used by `regression.py run`**
- **Slot files:** `slots.acquire(limit, label)` holds one of `lane_limit` slot files in `~/.workflow-loop/lanes/`
  (`LOOP_LANES_DIR` overrides it for tests). It takes `flock(LOCK_EX | LOCK_NB)` on `slot-0` … `slot-(N-1)` and keeps
  the descriptor open for the life of the process, so a crash frees the slot. The holder writes
  `{label, pid, since}` into its slot file.
- **When it applies:** only a FULL plan takes a slot.
  - That means `run land`/`run nightly` without `--reuse`, or `--reuse` that falls back to FULL (no record, record
    from another worktree, record with FAIL rows, an unmapped or deleted file).
  - AFFECTED and REUSED lanes, by-id runs and `red` never wait.
  - `lane_limit: 0` turns the limit off.
- **Nested runs never take a slot from the same pool:** the slot holder exports `LANE_HELD=<the absolute lanes
  directory it holds a slot in>` into its own environment before running rows, so every row and every regression run a
  row starts inherits it.
  - `acquire` returns at once only when `LANE_HELD` names the same directory it would use. So an inner FULL run can
    never wait on its own parent in the real pool.
  - A toy test that sets a private `LOOP_LANES_DIR` uses a different pool. Its toy lanes still take, and wait for,
    slots in that private pool even when the toy test itself runs inside a real FULL lane.
  - Two checks: a nested FULL run under a held limit of 1 in the same pool starts at once, and the 3-lane LANE_WAIT
    check passes with `LANE_HELD` already set to the real pool, as it would be inside a real lane.
- **The queued channel:** while it waits, regression.py writes the LANE_WAIT line to `<rc>.queued`, a path `lane()`
  passes as `LANE_QUEUED`. It removes that file the moment it takes a slot, just before touching the started marker.
  - `lane()` reads the channel as follows:
    - `.queued` present: WAITING with that line.
    - `.started` present: running.
    - Neither, child alive: still planning. It counts as running (`RUNNING: planning the lane`) for as long as the
      child is alive, up to the queue cap. There is no separate planning deadline, because planning can be slow
      under heavy load.
  - `live()` is the one liveness rule: a child is live while it is alive and either has its started marker (within
    `started + limit + 60`) or does not (planning or queued, within `launch + 4 × limit`). Past that cap,
    `lane_exec` ends it as LANE_TIMEOUT "queued or planning past N s" and kills its group before anything else can
    spawn.
  - The one-lane-per-goal rule and the prep-commit rule both use `live()`, so a planning child blocks a duplicate
    lane and a prep commit exactly as a running one does.
- **Waiting:** while every slot is busy, regression.py prints one line, then polls every 2 s:
  `LANE_WAIT: 2 of 2 lane slots busy (repo/slug-a qa since 14:02, repo/slug-b pr since 14:10); this full lane waits its turn and starts when one frees.`
  - The label comes from `LANE_LABEL`, which `lane()` sets as `<repo>/<slug> <name>`. A hand run is labeled
    `<repo> by hand`.
- **The clock starts at the slot:** `lane()` passes `LANE_STARTED=<rc>.started` to the child. regression.py touches
  that file when its rows start, at once when no slot is needed, otherwise right after the slot is acquired.
  - `lane_exec` waits in short slices. Its deadline is `started.mtime + limit` once the marker exists. A queued lane
    has no deadline, only a queue cap of `4 × limit`, after which it ends as LANE_TIMEOUT "queued past N s".
  - `live()` counts a queued lane (no marker, child alive, inside the queue cap) as live.
- **Callers:** `lane()` returns `running` with the line
  `WAITING: <the LANE_WAIT line>; run this same command again`.
  - flow.py qa/ship and goal.py pr print it unchanged, as they already print RUNNING. Neither caller changes:
    `lane()` derives `LANE_LABEL` itself from the repo folder name, the slug and the lane name.
- **The setting:** `lane_limit` is a private setting in the flow file, with default 2 and a one-line explanation. It
  is registered in settings.py, so `fill-private` adds it and the settings reference (Setup page) lists it.
  `LOOP_LANE_LIMIT` overrides it.

**2. No lost rows (done line 2, issue 135): one locked read-modify-write**
- `slots.locked(path)` wraps a `flock` on `<path>.lock`, following lanes.py's existing pattern.
- `write_rows` and its callers move to `slots.edit_rows(root, change)`: under the lock it re-reads regression.tsv,
  applies only this command's change (red: set this row's `seen_red`; add: add this row; sync: its own rows), and
  writes through `.tmp` and `os.replace`.
- `red` keeps its long run outside the lock and takes the lock only for the update. The non-reuse
  `regression-runs.tsv` write in `cmd_run` gets the same treatment, so two by-id runs can't drop each other's dates.
- regression.py gets smaller: the writer moves out.

**3. One stable result path and a wait command (done line 3, issue 152)**
- **The file:** `<git-common-dir>/loop/runs/<slug>.<name>-lane.last` is JSON, always replaced atomically
  (`.tmp`, then `os.replace`): `{head, attempt, state, rc, line, started, ended, log}`. The transitions, each with its
  one writer:
  - `lane()` writes `starting` when it spawns the child.
  - `lane_exec` writes `queued` when the `.queued` file appears.
  - `lane_exec` writes `running` when the started marker appears.
  - `lane_exec` writes `ended` with rc. It writes this before it writes the `.rc` file.
  - Finalization (`lane()` or `lane_status()`) writes `pass` or `fail` with the LANE line.
  - `pass` and `fail` are terminal. Every writer re-reads `.last` and never replaces a terminal state for the same
    attempt, so a late `ended` can't overwrite a final result.
  - The attempt-suffixed `.rc` stays an internal detail.
- **The command:** `role.py lane-wait SLUG qa|ship|pr [--timeout S]`. It uses `lane_status()`, a read-only path that
  reads the job, `.last` and `.rc` and finalizes an ended lane. It never spawns, kills, renders or commits; `lane()`
  is the only function that does.
  - If a lane for this HEAD is queued or running, it blocks, polling every 2 s, until the lane ends. It prints the
    LANE line and exits 0 on pass, 1 on fail, 2 on `--timeout`.
  - If none is running, it prints `.last` when that file's head is HEAD, else
    `NO LANE: none ran on <head>; start one with role.py lane SLUG NAME` (exit 3).

**4. HEAD moved (done line 4, issue 168)**
- `need_lane` becomes `need_lane(runs, slug, step, reply)`, and `goal.py record` calls it for both qa and ship.
  - Recording the step refuses unless `<slug>.<step>-lane.ok` equals HEAD:
    `REFUSED: HEAD moved since the ship lane passed (lane on 1a2b…, HEAD 3c4d…: the merge or a commit after it). Fix: python3 role.py lane SLUG ship (reruns only the rows the change can affect).`
  - A failed STEP still skips the check, as for qa today.
- flow.py ship already reruns the lane on every call without a running ship job. The refusal covers the in-session
  path and ship's own commits.
- **Order within ship:**
  1. flow.py ship runs the ship lane on HEAD.
  2. The ship skill runs. It may commit fixes, but never a version or CHANGELOG change; those belong to goal.py pr and
     merge.py.
  3. `goal.py record ship` runs.
  - If ship committed nothing, record passes at once.
  - If ship committed, record refuses once. The rerun is AFFECTED: only rows the commits can reach, and it takes no
    slot. Record then passes.
  - A check proves both paths: no commit records directly; one commit records after exactly one rerun.
- goal.py pr already merges the base and then starts a fresh `--reuse` lane on the new HEAD. A test proves pr never
  passes on an `.ok` from before its merge.

**5. Tables never stale (done line 5, issue 151): a prep commit in the foreground `lane()`**
- Before spawning a new lane, when `.loop/docs.tsv` exists, `lane()` runs `criteria.py render`
  (skills/workflow-docs, located relative to this package).
- If the render changed any page, or `.loop/regression-runs.tsv` is modified, it commits exactly those paths:
  `Lane: re-render the Tests tables`. It prints `LANE_PREP: re-rendered the Tests tables (commit abc1234)` and starts
  the lane on the new HEAD.
- Any other dirty file still refuses with `LANE_DIRTY` before anything is rendered or committed.
- This covers both by-id reruns (new dates in regression-runs.tsv) and merges (combined dates).
- **No cycle:** every lane runs `run land --reuse`, and a reusing run writes nothing in the worktree (regression.py
  already says so). So a lane never makes new dates. Only a hand or by-id run, or a merge, does.
  - The sequence is: dates change, then the next `lane()` makes one prep commit, then the lane runs on that commit and
    writes `.ok` with its HEAD, then record compares against that HEAD and passes.
  - At most one prep commit happens per change of dates. A check runs qa, then ship, then record end to end and counts
    exactly one prep commit.
- **The prep commit maps to AFFECTED, not FULL:** the planner already treats `.loop/regression-runs.tsv` as having no
  effect (`NO_EFFECT` in lanes.py). Wiki pages are read by the rows that run tools on the repo root (the docs and
  health rows, which always rerun), so a page change maps to them and is never unmapped. A check proves a lane after a
  prep commit reports AFFECTED.
- **Failures:**
  - No `.loop/docs.tsv`, or criteria.py can't be found (a repo without the docs skill): the prep step is skipped
    silently, as today.
  - `criteria.py render` exits non-zero: `lane()` refuses with
    `LANE_PREP_FAILED: criteria.py render failed: <first error line>. Fix: run it by hand; the lane committed and pushed nothing.`
    Nothing is started.
- **One lane per goal at a time:** `lane()` makes the prep commit and starts a lane only when no other lane job of the
  same slug is live (qa, ship or pr). Otherwise it returns `WAITING: the <name> lane of <slug> is still running; run
  this same command again`. So the prep commit can never move HEAD under a running sibling lane.

**6. operate-all waits for the report (done line 6, issue 99)**
- **Waits:** in dev/toy/test-operate.sh, the `until_*` helpers take a patience setting (default 60 s;
  `TOY_PATIENCE` overrides it) instead of the 15 s cap.
- **Settle:** the settle loop waits until the board shows g's final report, then waits for a quiet gap longer than
  one measured silent pass (the learning `operate-self-wake-pass`), instead of fixed 5 s and 1.5 s windows.
- **Proof under load (land row):** `FAKE_AGENT_DELAY` delays the fake worker's report past the old caps, which the old
  test fails deterministically.
- **10 of 10 (nightly row):** a new script runs test-operate.sh 10 times under a CPU-load generator and requires 10
  passes.

**7. Toy tests and defect rows (done line 7)**
- **Script:** `dev/toy/test-lane-control.sh`, with a `# reads:` header and a "# Value:" card per check.
  - No fake replaces regression.py. The toy repo (made by `setup.py --bare`, as the other toy tests do) gets land rows
    whose commands just `sleep 3`. The real `role.lane()`, the real `regression.py run land` (no record, so FULL), the
    real `slots.acquire`, the `.queued` channel and the started marker all run. Only the work inside the rows is fake,
    so the timing checks are fast and are seen failing on the old code, which has no slot code at all.
- **Checks:**
  - 3 lanes with `LOOP_LANE_LIMIT=2`: one prints LANE_WAIT, all pass, none times out, and the waiting lane's limit
    counts from its slot.
  - 8 parallel `red` runs keep all 8 dates.
  - `.last` names the latest attempt, and `lane-wait` blocks then returns.
  - record ship refuses after a commit and passes after the rerun; pr after a base merge reruns.
  - A by-id rerun, then a lane, gives LANE_PREP and a green docs row.
  - The operate delay check.
- **Defect rows:** one per issue, linked, each seen failing with `regression.py red` on the old code, plus a
  criterion row `lane-control-all` (ALL PASS).

**Docs.** The Regression page (REG) gets lane limits, `.last`, `lane-wait`, the prep commit and the record check. The
Delivery page gets the record check. The Setup settings reference is regenerated. skills/workflow-regression and
workflow-delivery references get their command lines.
