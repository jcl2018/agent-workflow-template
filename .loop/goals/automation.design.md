## Problem Statement

Today only regression runs in GitHub Actions (`regression.yml`, nightly at `regression_cron`), and it labels failures `regression`. Health runs only when someone asks, and its issue filing (`health.py file`) is manual. Nothing tells the owner what happened. The owner approved AUT-1..AUT-5 (scheduled routines in Actions, defect issues, health filing, one digest comment that GitHub emails, one setting per routine) and moving the schedule out of REG-4.

## Premises (accepted)

1. **Two workflows, not one.** Done line 3 names them: `regression.yml` (existing, extended) and `health.yml` (new). The digest posts from the health workflow at the end of its run, so a "round" is regression then health. Health is scheduled 30 minutes after regression by default (`17 */4` and `47 */4`), and the digest reads the state of the issues on GitHub, not a workflow's private output.
2. **One setting per routine:** `regression_cron` and a new `health_cron` in `.loop/config.json`. A cron string sets the schedule; `"off"` turns the routine off. The cron in a workflow file is fixed when the file is written. So:
   - changing a cron means rewriting the workflow (the setup and `workflow` commands do it);
   - each run checks its own schedule against the config and says so in the summary when they differ;
   - `"off"` is read at run time, so it takes effect without a rewrite. The run then writes nothing (no issue, no comment) and says the routine is off.
3. **Nothing scheduled writes to `main`.** The workflows write only issues, labels, comments, a pin and the run summary. That keeps #154 and #134 (protected-branch pushes) out of this goal's way; a test checks that neither workflow pushes.
4. **Defect label (REG-5, AUT-2):** a failing row's issue is labeled `defect`. Its body names the test, what it checks, the feature (wiki page) and the requirement it guards, using `tests.py`'s fields. Existing open issues labeled `regression` are still found by their marker, so nothing is duplicated.
5. **Health on a schedule (AUT-3):**
   - the workflow runs `health.py check` (report to the run summary) and `health.py file` for every group, which opens, updates and closes tagged issues;
   - the judge runs only when an agent key secret is set (default name `ANTHROPIC_API_KEY`, configurable). Otherwise the report says the judge was skipped and why.
   - In a repo whose checkout doesn't contain the skills, the health workflow says the package is missing and writes nothing (AUT-5). This repo carries them in-tree.
6. **Digest (AUT-4):**
   - one pinned issue, "Automation digest", labeled `automation`, is created if missing and pinned;
   - each round adds one comment listing what ran and its result (the latest regression run's conclusion, health's verdict), the new, still-open and fixed issues compared with the previous comment, and for each open issue the request to give the agent;
   - the comment mentions the repo owner (`@` plus `github.repository_owner`, never a hardcoded name), so GitHub's own notifications email it.
7. **REG-4 wording:** the done line gives its meaning, not its words. Drafted as "Runs in GitHub Actions: one command runs the suite the same way for me, the loop and GitHub Actions." It overlaps REG-3, which is noted for the owner and changes nothing.

## Approaches Considered

### A: extend regression, add health and digest in workflow-health (recommended)
- `actions.py` reads `regression_cron`, adds the off check and uses `defect` labels with feature-linked bodies.
- A new `skills/workflow-health/scripts/automation.py` writes `health.yml` and holds the digest logic (`automation.py workflow`, `automation.py digest`). Like `tests.py`, it is self-contained, so the workflow can carry what it needs.
- Setup writes both workflows; toy tests use stub gh.
- Effort L, risk medium.

### B: one automation.yml with regression, health and digest jobs
A natural round, and one digest per round, but it breaks done line 3 (two workflows) and AUT-1 ("every routine runs as a GitHub Actions workflow"). Ruled out.

### C: the digest as a third workflow on `workflow_run`
Cleaner triggers, but "round" pairing gets fiddly and it adds a third workflow. Ruled out for now; A's offset schedule gives the same effect.
