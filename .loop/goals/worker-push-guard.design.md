## Problem Statement

Goal done lines (frozen, `.loop/goals/worker-push-guard.md`, delivery PRD item DEL-9):

1. A pre-push hook that setup installs refuses, for a worker session, any push whose target is main or a branch other
   than `loop/<its goal>`, naming the rule and the fix.
2. The operation session's merge and release steps are unaffected.
3. Regression rows for an allowed own-branch push and refused pushes to main and to another goal branch, each seen
   failing then passing.

Today nothing stops a worker (a session or background agent working in a goal worktree) from running
`git push origin HEAD:main` or pushing a sibling goal's branch; only the operation session's merge step is meant to
publish. The govern hook (MON-7) guards the operation session's own tool calls the other way round; no guard covers a worker.

## What was checked in the code (verified, not assumed)

- Workers always run inside `<git common dir>/loop/worktrees/<slug>` on branch `loop/<slug>` (`goal.py` line 216 makes
  the branch `"loop/" + slug`; `session_bind.py` refuses a session folder outside the worktree). `govern_hook.py` already
  decides "worker" by exactly this location (plus `LOOP_ROLE=worker`), so the location rule has precedent.
- Pushes in the code: `goal.py pr` (`git push -u origin <loop/slug>`, from the worktree), `guards.write_finding`
  (`push -u origin HEAD`, from the worktree, so the remote ref is the current branch), `wiki.py prepare --commit`
  (`HEAD:<branch>`), `release.py cut` (own branch, cwd the goal tree), `autorelease.push_release_commit` (from a temp
  worktree, detached, to main or to `release/vX-<slug>`), `docs.py` (the separate wiki repo, which has no hook of
  ours). `merge.py` publishes by `gh pr merge` on GitHub, not by a push.
- Remote ref of each push, and whether the guard passes it: `goal.py pr` -> `refs/heads/loop/<slug>` (`state["branch"]`),
  pass. `guards.write_finding` (`push -u origin HEAD`) -> the current branch, which is `loop/<slug>` in the worktree,
  pass. `wiki.py prepare --commit` -> `HEAD:<branch>` where branch is `git branch --show-current` of the goal tree
  (wiki.py line 78 area), pass. `release.py cut` -> `branch = state.branch or "loop/" + slug`, and it refuses unless
  the tree is on that branch (release.py lines 313-318), pass; its failure path `--force-with-lease` of the same branch
  also passes. `autorelease` -> `HEAD:refs/heads/<base>` or `release/vX-<slug>`, from the temp tree: not a worker
  location (below), pass. `docs.py` pushes another repository. No existing worker flow targets any other ref, so no
  exemption is needed; `test-goal.sh` and `test-wiki.sh` run `goal.py pr` and `wiki.py prepare --commit` from a goal
  worktree with the hook installed in the new toy as the check that the existing flows still pass.
- The autorelease temp tree is `tempfile.mkdtemp(prefix="release-")` plus `/tree` (autorelease.py `push_release_commit`),
  so it sits in the system temp dir, outside `<common>/loop/worktrees`; the toy row builds it the same way.
- **A leak that decides the rule.** `worker.py loop` runs `release_step` (merge.py, then autorelease) from the loop
  parent with cwd the goal worktree, and `sessions.py report --status merged` does the same from a worker session whose
  environment holds `LOOP_ROLE=worker` (the owner's note: a worker must not run that report, but it does). So
  `LOOP_ROLE=worker` can be set in the process tree of a legitimate merge/release push, and a merge process can start
  with cwd inside a goal worktree. `LOOP_ROLE` therefore cannot be the signal on its own, and cwd of the parent is not
  the push's cwd: the push runs where git runs the hook, the temp release tree.
- `private.py` (workflow-delivery, 9.4 KB on main, v0.27.2) is the single private-name engine: `patterns()` returns
  none/off/on/broken, `scan()`, `refusal(result)` returns `(why, fix, code)` with codes `PRIVATE_NAME`, `PRIVATE_LIST`;
  CLI printing is `REFUSED: <why>. Fix: <fix> (<CODE>)`, exit 2. When no list exists the scan passes with a note.
  guard-enforce (same milestone, replanning, merges first) adds the `private.py hook push` mode that the pre-push stub
  calls with git's ref lines on stdin; its seed.py stub installer and `setup.py --git-hooks` stay.
- The loop's own checkout may already have this goal's skills inside a goal worktree: setup refuses to install hooks
  whose script path is inside `loop/worktrees` (guard-enforce rule). Toy tests must therefore install from a copied
  skills folder, not from the worktree's own path.

## Constraints

- No new skill file (package is at its file cap); standard library only; every script under 18 KB where possible and
  never over 20,480 bytes. private.py has about 10 KB of room; setup's seed.py and setup.py are not widened by this goal
  beyond a few lines.
- Touches: skills/workflow-delivery, skills/workflow-setup, dev/toy, .loop/regression.tsv, docs/wiki/Delivery.md.
- One pre-push hook, shared. No second hook, no competing pre-push, no new stub.
- The branch check runs when no private-name list exists.
- Honest limit: a local hook is a guard against mistakes. `git push --no-verify`, a clone without setup, a repo with
  `core.hooksPath`, and another tool using the API skip it. GitHub branch protection on main (required reviews and
  checks, DEL-5's release PR path) is the real backstop for main; nothing server-side stops a push to another goal's
  branch, which stays a mistake guard.

## Premises

1. The signal is where the push runs, not an environment flag: the push runs inside `<common>/loop/worktrees/<slug>`.
   `LOOP_ROLE` is not read at all: it leaks into the merge/release process tree (above), so any use of it can refuse a
   legitimate publish. Known limit, stated in Delivery.md: a worker that leaves its worktree and pushes from the main
   checkout is not seen; govern-hook-style location is all the hook has, and GitHub branch protection covers main.
2. The allowed target for a worker is exactly `refs/heads/loop/<slug>` where slug is the worktree's folder name.
   Everything else is refused: main, any other branch, tags, deletes (including its own branch), any other ref.
3. Anything not a worker passes this check untouched: the operation checkout, the release temp tree, any other repo
   folder. The operation session is not identified; it is the absence of the worker signal.
4. The check lives in private.py beside the scan, because that is the one engine the pre-push stub already calls.

## Approaches Considered

### Approach A: a worker-branch function in private.py, run first by `hook push` (chosen)
`worker_push(lines)` returns `(why, fix, code)` or None, like `refusal()`. `hook push` calls it before the pattern
scan, so it runs with no private list. Zero new files, zero new hooks, reuses the stdin lines and exit-code mapping
guard-enforce installs. Cost: this goal builds on guard-enforce's `hook push`.

### Approach B: the check in role.py behind a second stub line
Rejected: a second command in the stub means git's stdin must be split between two programs, and the coordinator
ruled out a second hook or competing pre-push.

### Approach C: server-side protection only
Rejected as the whole answer (done line 1 asks for a hook); kept as the named backstop for main.

## Recommended Approach

Approach A. Decisions:

- **Where.** `private.py`: constant `WORKER_PUSH = "WORKER_PUSH"`; `worker_push(lines, env=None)` plus a small
  `where()` helper (about 40 lines in all). `hook push` runs `worker_push` first, then the private-name scan, and exits
  with the stronger refusal; the two refusals print separately if both apply. No pattern-file dependency in this path.
- **Who is a worker.** `where()` gets the git common dir (`git rev-parse --git-common-dir`, absolute) and the
  toplevel (`--show-toplevel`), both `realpath`ed. Worker when the toplevel is under `<common>/loop/worktrees/<slug>`
  (slug = first folder below, which is the folder `goal.py` creates). The temp release tree (system temp dir), the
  operation checkout and any other folder: not a worker, pass. A repo nested inside a worktree has its own common dir
  and no hook of ours, so it is out of scope.
- **What is refused.** Each ref line `<local ref> <local sha> <remote ref> <remote sha>`: refuse unless the remote
  ref is `refs/heads/loop/<slug>` and it is not a delete (local sha all zeros). Force pushes of the own branch pass
  (a worker rebasing its branch is its own business). All lines are checked, so a multi-ref push with one bad ref is
  refused whole.
- **The refusal.** Style of private.py: `REFUSED: a worker session for goal <slug> may push only loop/<slug>, not
  <ref>; nothing was pushed. Fix: push your own branch (goal.py pr <slug>); only the operation session publishes to
  main (merge.py), and another goal's branch is pushed from that goal's own worktree. (WORKER_PUSH)`. It names the
  rule, the ref, the fix and the code, and the code goes into commands.md's code table next to PRIVATE_NAME and
  PRIVATE_LIST. Exit 2, like `private.py scan`.
- **Fail closed.** One rule, everywhere: if the check cannot decide, the push is refused, because a guard that opens on
  error is bypassed by any error. Two internal cases, one code, `WORKER_PUSH_INTERNAL`: `git rev-parse` fails or
  answers nothing (the hook was started by git, so a failure is a real fault, not "not a worker"), and a ref line that
  is not four fields. Message: `REFUSED: the worker-branch check could not read <what>; nothing was pushed. Fix: run
  private.py hook push by hand in this folder to see why; push once with --no-verify only if the owner agrees.
  (WORKER_PUSH_INTERNAL)`. Both codes go in the table. This matches guard-enforce's stub, which already fails closed on
  a missing python, a missing script or a crash, and a missing private.py is its `stale` hook state, flagged by setup
  and health.
- **Setup and health.** Setup installs nothing extra: the pre-push stub guard-enforce writes already calls `hook push`.
  Health's pre-push state (installed/stale/foreign/missing) from guard-enforce covers this guard; this goal adds no
  second state and no duplicate rule. A foreign pre-push hook gets one printed line to add, the same line.
- **core.hooksPath and `--no-verify`.** Setup refuses when `core.hooksPath` is set (guard-enforce) and says so; the
  hook cannot see a `--no-verify` push. What catches them: GitHub branch protection for main (the owner enables it; release PRs go through it). The merge-step scan of the PR diff is guard-enforce's done line 2 and is pending until it merges; it covers private names, not branch targets. Nothing else was verified, so none is claimed. This design names the limit in Delivery.md and does
  not claim more.
- **Ordering with guard-enforce (an explicit gate).** The build starts only when main holds `private.py hook push`
  reading git's four-field ref lines on stdin and a pre-push stub that calls it. That is the whole interface assumed;
  if guard-enforce renames it, the call line follows. If it is not on main when the build starts, the build writes
  nothing and prints `PENDING: guard-enforce's private.py hook push is not on main; merge it, then run this goal again`.
  It never writes a competing `hook push` or stub.

## Tests (toy repos)

A new `dev/toy/test-push-guard.sh` builds with `make.sh` (bare origin, main checkout), copies the skills folder to a temp
dir and installs the hook from that copy (`setup.py --git-hooks`, because setup refuses a worktree path), adds a goal
worktree at `<common>/loop/worktrees/<slug>` on `loop/<slug>`, and a detached temp worktree for the release case.
Red first, per row kind: refusal rows are seen failing with `worker_push` stubbed to return None (the bad push gets
through); allowed rows are seen failing with it stubbed to refuse everything (the good push is blocked). Then green.
Rows:

- `push-own-branch-allowed`: worker worktree, `git push -u origin loop/<slug>` succeeds.
- `push-main-refused`: worker worktree, `git push origin HEAD:main` refused, output holds `WORKER_PUSH` and the Fix line, origin main unchanged.
- `push-other-goal-refused`: worker worktree, `git push origin HEAD:loop/other` refused.
- `push-operation-allowed`: the main checkout, no `LOOP_ROLE`, push to main succeeds.
- `push-release-tree-allowed`: detached temp tree with `LOOP_ROLE=worker` in the environment, push to main succeeds.
- `push-tag-refused`: worker worktree, tag push refused; a delete of the own branch refused.
- `push-no-list-still-refused`: no private-name list, refused push still refused and an allowed push still passes.
- `push-multi-ref-refused`: worker worktree, one push of the own branch plus `HEAD:main` is refused whole.
- `push-internal-fails-closed`: `git rev-parse` made to fail (a broken GIT_DIR in the hook's environment) is refused with
  `WORKER_PUSH_INTERNAL`; a malformed ref line fed to `private.py hook push` by hand is refused the same way.
- `push-worker-env-in-main-checkout-passes`: the known limit above, asserted so that changing it is a decision.
- The flows `goal.py pr`, `wiki.py prepare --commit`, `release.py cut` and the autorelease push run in their toys with
  the hook installed and still pass (the existing toy tests run with the hook installed).
