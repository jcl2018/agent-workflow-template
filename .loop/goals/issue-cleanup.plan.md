# Plan: issue-cleanup

Goal file: .loop/goals/issue-cleanup.md (done lines frozen). Design: .loop/goals/issue-cleanup.design.md (Premises 1-7 are the rules
this plan implements).

## Implementation plan

### Context

The template repository has 820 open issues; 98 have no `regression` label (health findings, enhancements, goal bugs). The 722
defect+regression issues belong to regression-green-2. This goal reads each of the 98 against current `origin/main`, closes the
ones that are fixed, stale or duplicate with a one-line reason and evidence, and turns the rest into finding lines. It writes only
`.loop/findings.md` (plus this goal's design and plan files) in git; the closes go through `gh`.

### Changes

1. Snapshot: list the open non-regression issues with `gh issue list` (number, title, labels, body) into a local file outside git, and
   record the highest number covered (issues filed later are out of scope).
2. Triage in four groups, each by a reviewer subagent reading `origin/main` and writing a verdict table (issue, verdict, evidence):
   (a) size findings (re-run the size check, compare the files named); (b) requirement, criteria, docs, consistency and hygiene
   findings (re-run `workflow-health check` and the page checks); (c) review findings (read the code each names); (d) bugs,
   enhancements, goals and the rest (read the code and the commits since the issue was filed).
3. The worker re-checks every verdict itself before it counts: re-runs the named check or reads the cited code and commit; a verdict
   it cannot confirm becomes `needs-code`, never a close.
4. Folding: a duplicate group keeps its oldest open issue; the others close as duplicates naming it, and the kept one gets one comment
   listing what was folded in.
5. Closing: a small script (kept outside git) reads the verified table and, one issue at a time, prints the line then runs
   `gh issue close N --reason <completed|not planned> --comment "<reason; evidence>"`, stops at the first error and writes what it
   closed to a log; nothing is deleted or edited but state and one comment.
6. `.loop/findings.md`: one line per real piece of work, `- <slug>: <what to build> (issues #N, #M)`, folding issues that need the same
   change, skipping any already covered by a goal in the queue or an existing finding (the line then cites that goal or finding in
   the table instead).
7. The pull request body carries the table of every issue (number, verdict, reason, evidence, goal line), with no private name or
   path.

### Tests

The checks are the evidence: each close names a commit, a PR or a check output a reader can re-run. After the run, a final
`gh issue list` shows no open non-regression issue that is fixed, stale or a duplicate; every remaining one is named in
`.loop/findings.md` or a queued goal; the 722 regression issues are unchanged (count compared before and after).

### Not in scope

The 722 defect+regression issues; any code change; labels, milestones, deletion.

The proof compares number sets (not counts): the open regression numbers in the snapshot are all still open after the run.
- Adopted (High, closer): a script outside git, dry run by default (`--yes` to run), reads a verified table, one `gh issue close N --reason <completed|"not planned"> --comment-file`, 1 s between writes, stops at the first error, appends each close with its prior state and the matching `gh issue reopen N` line to a rollback log, resumes from GitHub's state; tested with a fake `gh` on PATH. Comment text is one line from a template: reason + commit/PR number; never "fixes/closes/resolves #N" (GitHub, the fit check and the defects check act on those words).
- Adopted (High, public safety): the table and every comment pass a grep gate for private paths, names and addresses (the default private-names list plus a home-folder prefix) before anything is posted; the PR body is scanned the same way.
- Adopted (Medium): a fold comment is posted first on the kept issue, once (idempotent); `.loop/findings.md` gets one line per piece of work, capped and in the existing `- <slug>: <text> (issues #N)` form, skipping work already named in a goal or finding; overlap with the regression-green-2 branch's goal files is checked and marked covered; the done lines are proved by two runnable checks (the closed set matches the table; every remaining number is in the table as `needs-code` with a finding line or goal, or `keep`).
- Frozen done line 1 is read as: no remaining open non-regression issue is a duplicate, already fixed or stale as far as the tooling lets it stay closed; a still-firing health finding is a real open finding, not stale. Stated in the PR.

## Findings in prose

1. Premise 4 closes health issues with plain `gh issue close`. For any health issue whose check still fires (the `needs-code` and `duplicate` verdicts) the next health run issues a `reopen` action, so the close is undone within four hours and the issue gets a reopen churn comment. Closing those is pointless. For `stale` verdicts the health tool would have closed them itself on its next run (the rule ran and passed), so the plan adds little there except speed. The only real value is in non-health issues (bugs, enhancements, goal:*, about 36) and in health issues the owner decides to close for good. For those, the supported path is `issues.py close --why "<owner words>" --yes`, which adds `health:closed` so they stay closed while evidence is unchanged. The plan never mentions it.
2. "Duplicate" is not a verdict that works for health issues. Two issues with different keys (for example `size ... scripts` #354 vs `size ... limit` #142, #138 vs #452 for goal.py) are two different rules by design; closing one just means health reopens it. The real duplicate sources are the 18 unlabelled issues and goal bugs, and the groups the filer did not dedupe (a `link` action is only used on open, not retroactively).
3. Folding 18 size issues, 13 requirements row issues and 20 review issues into finding lines is a good outcome, but the findings line must not be the only place; health will keep a live issue per finding. A needs-code health issue should stay open as the tracker (that is what it is for), with the finding line citing it. Closing it and moving it to findings.md duplicates the same work in two stores and then the health run files it again.
4. Evidence standard is too thin. "Re-running the check" is right for health issues, but `workflow-health check` runs the whole twelve groups and judge-based review findings (`review-*`) are non-deterministic (hash ids like Setup-59600e). A review finding that did not reappear in a single run proves little. Rule: stale needs the same rule to have run on a current origin/main commit and passed, citing the SHA; review findings are only stale when the named code or line no longer exists, otherwise leave open.
5. Wrongly closing a real bug: bug/goal:* issues (#439 merge.py crash, #451, #494, #496, #812, #814) were filed hours or days ago; the evidence "a later goal fixed it" must be a merged commit that references the issue or a test that fails without it. Commit titles are not evidence. Several (#439 vs commit "autorelease-fail-crash" v0.27.11, #494 vs worker-no-waiting) are likely genuinely fixed, which is good, but each needs the cited commit and a check, since the repo has 722 regression issues showing fixes often regress.
6. Cross-references: the plan has no step to protect issues referenced by queued/running goals, open PRs, `.loop/queue.md`, findings.md, designs and plans (`Fixes #N`, `closes #N`). Closing an issue a PR says `Closes` is harmless, but closing one a running goal reads (delivery-prd cites #38, #117, #129, #134, #154, #170) breaks its done lines or its judge. Also a goal's frozen done line may name the issue.
7. Safety and reversibility: close is reversible with reopen, but reopening is not free: it notifies, and health `reopen` may race. There is no dry run, no rollback list, no cap. The script "stops on first error" but is not resumable, and a half-run leaves the PR table out of sync with reality. Rate limit: secondary limits on comment+close (about 2 writes per issue, 200 writes) are fine at one per second, but there is no sleep or retry.
8. Moving target: premise 7 records the highest number covered, but the health cron files new issues while the run is working, and also files issues with new keys when this cleanup changes docs/findings. Note #834 was filed after the design; the "98" is already stale. Set the snapshot cut as `number <= N` and re-list immediately before closing.
9. Findings.md is a shared hot file (goals append, board-held notes "for the health-report pass to file"). Appending ~20 lines risks merge conflicts and the very next Touches check; also the existing finding lines retire by the pattern "retired <slug>" and contain no issue numbers, so "already covered by a finding" can't be matched mechanically by issue number. Cite issue numbers in new lines (the plan does) but also add the covered-by mapping to the PR table only.
10. Done line 1 ("no open non-regression issue is a duplicate, already fixed or stale") is unverifiable afterwards because health will reopen/refile; done line 2 ("every issue still open needs code and is covered by a goal or finding line") conflicts with leaving health issues open as trackers. The final check as written ("a final gh issue list shows no ... stale") can pass only at the instant it is run. Reword to a snapshot SHA and number cut.
11. Owner keep list: the plan has no way for the owner to mark issues to keep (milestone/pinned/`keep` label, enhancement requests like #94, #97, #115, #179-#181 which are feature ideas and are NOT stale just because untouched). Enhancements default to needs-code, never stale on age alone.

# Eng review: issue-cleanup plan

Verdict: the shape is right (evidence per close, one at a time, nothing deleted), but three mechanics would make the cleanup undo itself or fail its own done lines. Read-only review; I ran `gh issue list`, grep and git only.

## What I verified in the repo

- `health.py check` writes no file and calls no model (docstring; `cmd_check` only gathers and prints). It does call `workflow-regression/scripts/tests.py list` (read-only). The performance, hygiene and mine groups read local run records, branches and private files, so a local run gives different answers than the CI run, which skips them (health.yml line 76 says so). `report.py review` and `judge` can launch a model (`claude -p`) when CLAUDECODE is unset; under a session they write a prompt file to a temp dir. `preview` also runs the judge. `health.py file`, `report.py file`, `issues.py close --yes`, `automation.py digest`, `mail.py send`, `milestone.py` all write to GitHub. So "re-run workflow-health check" is safe only as `python3 skills/workflow-health/scripts/health.py check --group <g> --json`; the plan never names the command, and "the page checks" and "re-run the size check" are not commands.
- health.yml runs `health.py file --group requirements,traceability,consistency,docs,freshness,tests,security,size,adoption` on a cron every 4 hours (`health_cron` in .loop/config.json). `file.py plan()` reopens any closed health issue whose finding still fires (kind `reopen`), and re-files it if no issue holds the key. The only thing that keeps a close closed is the `health:closed` label while the evidence hash is unchanged. It auto-closes an issue only when its rule ran and the finding is gone.
- Live counts right now: 98 non-regression open (matches), but 836 regression-labelled open, not 722 (CI keeps filing them; regression-green-2 is also running). One of the 98 carries only `defect`, one carries `automation` (the pinned digest issue). 18 of the 98 have no label at all. About 58 carry `health`.
- `.loop/findings.md` already has 28 lines; `health.py` hygiene warns above `FINDINGS_WARN = 5` open lines (`- ` prefix). Only `- slug: ...` lines count; `[closed]` marks a line closed for defects.py; `retired ...` lines do not start with a dash. Findings are not auto-queued: the queue parser (`graph.parse`) wants `- slug: x | touches: ... | goal: ... | done: ...` lines in `.loop/queue.md`, and slug must match `^[a-z0-9][a-z0-9-]{0,50}$`. guards.write_finding appends `- slug: text` and runs a private-name scan on the commit.
- Working tree has uncommitted `.loop/queue.md` (35 added goal lines) and `.loop/config.json`; the plan's "already covered by a queued goal" check must read queue.md from the right place (this worktree's queue.md versus the main checkout's).

## Findings in prose

1. Closes of still-firing health findings get reopened within 4 hours. The plan closes `fixed` and `duplicate` issues with `gh issue close` and no label. A `fixed` verdict is only as good as the CI check agreeing, and a duplicate group's closed members share the same marker key as the kept one; `plan()` prefers an open duplicate, but if the kept one is ever closed or the evidence hash differs, the closed one reopens. Also a health issue the owner calls stale but whose rule only runs locally (hygiene, performance, mine) is never auto-closed or re-opened by CI, so those are safe; the CI-run groups are not. Amend: for every closed issue that carries a `health` marker, verify with the exact CI command (`health.py check --group <the CI group> --json`) that its key no longer fires (stale/fixed) or that an open sibling holds the key (duplicate); for duplicates and any close not backed by a silent check, also add `health:closed` (`gh issue edit N --add-label health:closed`, after `gh label create health:closed --force`), which is what `issues.py close` does. That is a label edit, so the plan's "nothing edited but state and one comment" and the Not-in-scope "labels" must change to allow this one label, or the plan must not close firing-health issues at all (they stay needs-code). Then add a final proof: after the closes, run `health.py preview --group ...` (read-only) and require zero `reopen` and zero `open` actions that name a closed issue number.

2. Wrong baseline for done line proof: 722 is stale. The regression count is 836 now and drifting (CI files more every night; regression-green-2 closes some). "Unchanged" cannot be proven by comparing counts. Amend: snapshot the exact set of regression issue numbers (sorted list, plus the sha) at start; the closer script refuses any issue number that is not in the snapshotted non-regression set AND re-fetches labels immediately before each close (abort if `regression` is now present); the final proof is "none of the numbers closed by this run has the regression label, and every closed number was in the snapshot set", not a count equality. Also state the fetch limit explicitly (`--limit 1000`; default 30 silently truncates) and assert the fetched count is below the limit.

3. Scope leaks in the 98. Exclude the `automation` issue (the pinned digest; `automation.py digest` edits its body and comments; closing it makes the next round create a new one and breaks pin state). Decide the lone `defect`-only issue and any issue labelled `goal:*` (they belong to named goals; a `goal:` label may mean the goal is still running or queued). Decide issues authored by the loop itself versus the owner. Add an explicit exclude list and put it in the table as verdict `skip`.

4. The closing script is under-specified. Amend to: input is a TSV `number<TAB>verdict<TAB>reason<TAB>evidence<TAB>kept` produced and reviewed before any close; before each close do `gh issue view N --json state,labels,updatedAt,comments`; skip if already closed (idempotence, rerun after a failure resumes safely), skip if labels now include `regression`, skip if the issue changed after the snapshot (`updatedAt` newer than snapshot, someone commented); `gh issue close N --reason completed|"not planned" --comment ...` (the flag value for not planned is the literal `"not planned"`; gh versions before 2.4x differ, so check `gh --version` and try one close on a throwaway first, or use `gh api -X PATCH repos/{owner}/{repo}/issues/N -f state=closed -f state_reason=not_planned` which is version independent); write the comment body to a file and pass `--body-file`/`--comment` from a variable, never interpolate evidence through a shell string (issue titles and bodies are untrusted text; the evidence column must be built from commit shas, PR numbers and command names only); append a log line (`N verdict timestamp url`) after each success, fsync; stop on first non-zero exit; sleep 1-2 s between closes (secondary rate limit on content creation, comments count; ~100 closes plus ~10 fold comments is fine but a 403/429 must stop, not retry blindly); a `--dry-run` default that prints the full table and needs `--yes` to act, matching `issues.py close`'s convention. Log lives outside git; on resume read the log and `gh` state both (gh state is truth).

5. Comment text safety (public repo). The comment must name only public things: commit sha, `#N`, PR number, a command like `health.py check --group size` and its one-line output. No local paths (a home-folder path), no `.git/loop/worktrees`, no private setting names, no mine-group rule names (health.py deliberately keeps mine output private), no owner quotes beyond what the issue shows. Add a mechanical gate: grep the whole TSV and the PR table for a home-folder prefix, `~/`, `.review`, `.git/loop`, `@`, `mine`, and for any token from the private-name scan (`skills/workflow-delivery/scripts/private.py`: run its scan over the table file) before the first close; abort on any hit. Also avoid writing `fixes #N`, `closes #N` or `resolves #N` in the findings lines, goal files or the PR body: `fit.py`/`defects.py` FIXES regexp treats those as "this goal fixes #N" and requires defect tests, and GitHub auto-closes issues named after "Closes #N" when the PR merges, which would close needs-code issues. Use "issues #N" as the plan already does, and say "refs" in the PR body.

6. Duplicate folding: "keeps its oldest open issue" is wrong for health issues. The kept issue should be the one the health marker key lives on (the one `health.py preview` would update; `file.py` line 108 prefers an open duplicate, otherwise first seen), else a later health run updates the newer one and treats the older as an unmatched marker. Rule: keep the issue whose `<!-- loop-health KEY` marker matches the current finding key; if neither has a marker (enhancements, goal bugs), keep the oldest. Never keep an issue that is itself fixed or stale: resolve the group's verdict first, then fold. Write the fold comment on the kept issue before closing the dupes (so a failure mid-way leaves the information); the comment lists numbers only. Make the fold comment idempotent: check for an existing comment containing a marker like `<!-- issue-cleanup folded #A #B -->` before posting.

7. Verdict verification needs per-group commands, not prose. Amend step 2/3 with: (a) size: `health.py check --group size --json` and compare `rows[]` subject to the files named in each issue (the issue's marker key gives the key; `key_of` in issues.py extracts it); (b) requirements/criteria/consistency/docs/traceability: the same command with that group; hygiene/performance reproduce only locally and need the tree state of the issue's day, so treat as needs-evidence, default `needs-code`; (c) review findings (`health:review-*`): the review is a model judgement that `check` cannot re-run; verdict must cite the code line and a commit; do not call `report.py review` (it can start a model; under CLAUDECODE it only writes a prompt file but still, avoid); (d) run all against `origin/main` in a clean detached worktree (`git worktree add --detach /tmp/x origin/main`, or this worktree after `git fetch` and checkout of origin/main) not the dirty working tree: the current tree has uncommitted queue.md/config.json that change the health output and HEAD is not origin/main (origin/main moved by at least one merge since HEAD). Record the origin/main sha used in the table and fetch immediately before. Also note that a green `check` on a size or requirements row is only valid if "that rule itself ran and read its data": require no UNREAD row for the key (file.py closes only under that condition).

8. Subagent verdicts: the worker "re-checks every verdict" which for 98 issues is large and unverifiable. Make the re-check mechanical for the cheap majority (health check output by key) and require cited file:line plus commit sha for the rest; sample-audit is not acceptable for closes since each is public. A verdict with no recorded evidence string is rejected by the script (empty evidence column = refuse).

9. findings.md line format and queue consumption. Existing format: `- slug: text` one line, slug lowercase kebab, text one line (write_finding collapses whitespace), `[closed]` suffix marks done, `retired` lines for history. Amend step 6: slug must pass `^[a-z0-9][a-z0-9-]*$`, unique against existing slugs (grep), line must start with `- `, no newlines, no `|` (queue lines use pipes; avoid ambiguity), mention `issues #N, #M` at the end (the plan does this), and commit through the same private scan. Expect many lines: the file has 28 lines and `FINDINGS_WARN = 5` already warns (hygiene `findings open`). Adding, say, 30 more lines makes the hygiene row worse; either fold aggressively to one line per real piece of work (the plan's intent: say a target, e.g. at most 15 new lines), or accept and note it. Nothing consumes findings.md automatically into queue.md: the queue wants `slug | touches | goal | done` lines, so done line 2 "has a new goal line in .loop/findings.md" is satisfied literally but nothing runs it; say in the PR that a person or `batch.py add` promotes lines. Do not write to queue.md (not in `Touches`, and the working tree has 35 uncommitted goal lines).

10. Interplay with regression-green-2 and others. Branches `loop/regression-green-2`, `loop/regression-all` etc. exist; regression-green-2 cleans up the `regression` labelled issues, and the health CI also files `regression` issues. Both may touch `.loop/findings.md` (write_finding appends; a merge conflict on the last line is likely) and `.loop/regression.tsv` links.
