## Problem Statement

The template forces one GitHub milestone per feature page plus a Backlog, and checks, creates and fills them everywhere. The owner plans by version (for example v1.0) for visualization and wants that restriction gone: a milestone is free form and nothing requires a feature page, issue or pull request to have one. The four done lines in `.loop/goals/milestone-freeform.md` are frozen and this design only meets them. Issues keep their feature and group tags, a milestone that exists is still shown, and a version milestone works as before.

## Constraints

- Done lines and Verify by hand belong to delivery, never to the owner as decisions.
- Reviewed requirement lines are locked (DOC-2). The only supported route to reword one is the owner's un-review (section Recommended Approach, item b).
- No check, health rule, docs check, `goal.py pr` or setup step may fail, warn or refuse for a missing milestone, so the answer to "what replaces a removed check" is nothing. (An owner command such as `milestone.py move` may refuse a typo; that is not a check.)
- Coordination: the health code was just split into `report.py`, `issues.py`, `defects.py`, `judge.py`, `rules.py`, and the estimate-accuracy goal reworks the same files now. Edits there stay to the milestone hunks listed below.
- Other repos' Home pages and feature pages, which carry a Milestone cell and a `Milestone:` line, must keep passing.

## Premises

1. A milestone is metadata the owner sets by hand; no code derives or requires one. Agree.
2. A feature's issues are found by a tag, not a milestone. A `feature:<Page>` label, made the way `health:<group>` labels already are, carries what the milestone carried. Agree.
3. Removing a check removes it outright: no replacement warning, no soft note. Agree.
4. A `Milestone:` line on a page and the Home Milestone cell stay legal and displayed, never required. Agree.
5. A free-form milestone (v1.0) is made or used by name, with `gh` or `milestone.py`, never inferred from a page. Agree.

## Approaches Considered

### Approach A: remove at the root, keep display, replace the identity with a tag (recommended)
Delete each requirement and creation, make `milestone.py` name-based, tag by `feature:<Page>`, reword the wiki through the owner's un-review, rewrite the rows. Effort L, risk medium (many files, small hunks). Reuses `tag_of`, `label create --force`, `feature_of`, the digest marker.

### Approach B: minimal, turn the checks off
Leave the code, make each rule return nothing and add a setting. Effort S, risk low, but the code keeps creating milestones (done line 2 fails) and a dead rule per place remains. Rejected.

### Approach C: drop the Milestone column and `Milestone:` line from the format
Cleanest format, but breaks other repos' Home pages and removes the Home display (done line 3). Rejected.

## Recommended Approach

Approach A. Decisions with their reasons:

- **(b) Rewording Reviewed lines.** A Reviewed line is sealed by `<!-- reviewed HASH -->` and the page by `<!-- prd P= R= N= M= U= -->`; a changed word is `LOCKED`. The supported route is the owner's un-review, as in earlier commits that sent requirement lines back to Unreviewed for rewording: run `criteria.py unreview DOC-4 DOC-10 HLT-2 HLT-4 AUT-2 AUT-3 SET-1 Documentation Health Automation Setup --user` with `LOOP_OWNER_WORDS` set to the owner's own goal message, quoted exactly as it stands in the goal file's title line (the command logs it in the git common dir under `loop/reviews.tsv`). The basis is frozen done line 1, which the owner wrote: "... are reworded so milestones are optional and free form, each changed line Unreviewed, with the wording shown in the PR" - it names the lines to change and orders them Unreviewed, so the un-review is the owner's instruction carried out, not the goal's own initiative; the earlier rewording commits likewise cite the owner's words in their messages. The command checks every argument before writing anything, so a refusal leaves no partial rewording. Then edit the lines, then `criteria.py render` for the Tests tables. The command turns a line into `- ID: **Unreviewed** text` with no stamp and the page into `Review: **Unreviewed**`; the owner re-reviews later. A page is un-reviewed with its lines because Problem, Success metrics and Usage text below also change (page fingerprints). Home has no Review line (it is not a PRD page) and the Regression page is already Unreviewed, so neither needs the command; Delivery, Monitoring and Guardrails keep their text. If the command refuses (no owner words), stop and report; never hand-edit a stamp. The commit message quotes the owner's words, as the earlier commits did.
- **Wording shown in the PR.** The PR body is the goal file plus `## Result`, so the worker adds one `## Wording changes` section to `.loop/goals/milestone-freeform.md` (outside the frozen done lines) with a before and after list per line, committed before `goal.py pr`. No tool change.
- **Proposed wording** (the worker may polish, not change meaning):
  - DOC-10: `One Tests page, every release noted, milestones optional` with sub-bullets: one full Tests page; every release has a release note; `A milestone is optional and free form, used to plan by version (for example v1.0); nothing requires a feature page, issue or pull request to have one, and no check fails or warns for lacking one.`
  - DOC-4 bullet: `Home holds one table with four columns: Feature, What it does, How to use (a link to the README section), Milestone (optional: empty, or a link to the free-form milestone the feature is planned on).`
  - HLT-4: title `Findings become issues tagged with their feature and group`; bullet one: `Each finding, from a rule or from the review, is one GitHub issue tagged with its group or kind and the feature it is about; it sits on a milestone only when I put it there.`
  - HLT-2 (Traceability and Docs groups): `issue to feature` replaces `issue to milestone to feature`; `every open issue on a milestone` is dropped from Docs.
  - AUT-2: `... one issue labeled defect and tagged with the feature it guards ...`; AUT-3: `Every finding becomes one issue tagged with its group and its feature ...`; the Automation Problem line and success metric say tagged with its feature.
  - SET-1: `... the Home table and README How to use, the nightly regression ...` (no milestone per feature, no Backlog) and `... filed as issues tagged with the right feature`. Setup makes no milestone.
- **(c) Home Milestone column.** The four-column header stays exact, so other repos pass unchanged. The cell is not validated at all: empty or any text, one link or `v1.0`. Rule 6 is deleted and nothing replaces it. Empty cells split fine (`cells()` keeps them). The row-count and README-link checks stay. The docs template says optional.
- **(d) `Milestone:` line and v1.0.** `prd.py` already treats the line as optional and keeps the Review line after it; nothing changes there. `milestone.py` loses `features`, `goal_feature`, `new --all`, `new FEATURE or backlog`, `link_page` and `attach`, and becomes name-based: `new TITLE [--live]` prints `CREATED TITLE`, `EXISTS TITLE` (a second run creates nothing) or, without `--live` and a token, `WOULD create milestone TITLE`; `move ISSUE TITLE|none [--live]` puts the issue on any existing title or clears it, and prints `REFUSED: no milestone TITLE. Fix: milestone.py new TITLE --live` (exit 1) for a title that does not exist; a gh error is `REFUSED: could not ...: <error>` (exit 1). These are the owner's own commands, never run by a check, rule or setup step. A v1.0 milestone made on GitHub or by `new v1.0` works as before: it shows on Home when the owner links it, in the digest as a suffix, in triage and judge as the issue's own milestone. The Usage entry `/workflow-docs milestones` becomes `/workflow-docs milestone new TITLE | move ISSUE TITLE`, with SKILL.md's command map updated in step so the Usage-versus-code docs rule still passes.
- **(e) What replaces the removed checks.** Nothing; no row, note, warning or refusal. Display code that cannot read milestone titles prints no title.
- **Feature tag.** `file.py` and the regression workflow add `--label feature:<Page>` (the page name from `.loop/docs.tsv`; no label when the finding fits no page) and create it with `gh label create --force` beside the existing tag labels. One helper, `issues.feature_label(page)`, makes the name for both writing and reading: `feature:` plus the page name cut to 50 characters (GitHub's limit), kept as written; page names are file names, so they hold no spaces or slashes. Reading never parses a label back: `issues.feature_group(issue)` compares the issue's labels with `feature_label(p)` for each page `p` in `.loop/docs.tsv` (case-insensitive). With no feature label it falls back to the issue's milestone title only when that title equals a known page name (an old feature milestone); a title such as v1.0 or Backlog, or no milestone, gives `No feature`, so a free-form milestone never becomes a feature. A repeat `file` run backfills: the `update` act adds the feature label when an open health issue lacks it. A failed label or issue write is the existing per-issue `FAILED <action>: <error>` line, nothing new. Triage lists, `--feature` filters, the digest headings, `covering` (subject token on an open non-health issue, no milestone test) and judge line 252 all use it. The `placed=` marker field stays parseable and is written empty; an issue the owner put on any milestone is never touched, so no `move` act exists.
- **Backlog.** Never made, never a fallback. An existing Backlog milestone is read like any other.
