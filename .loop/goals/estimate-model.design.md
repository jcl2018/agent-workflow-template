## Problem Statement

Issue 96: every queued goal on the live board shows about 15 minutes left. `board_status.left_time` sums, per step, the median time of all other finished runs, so every queued goal gets the same number whatever its size. Finished goals here took from under 5 minutes to many hours (the median is about 29 minutes of logged step time). Issue 37 adds a second gap: a goal stuck far past its estimate only shows a quiet "over" note in its flow lines, never under Issues.

The frozen done lines (in `.loop/goals/estimate-model.md`) set the target:
1. The estimate comes from finished goals like this one (similar done-line count and touched areas), per step, falling back to all finished goals; more done lines or touched areas means a longer estimate.
2. The board shows a range ("20 to 45m") and "rough" when fewer than 5 similar goals exist.
3. Running goals refine their estimate from the steps they have finished.
4. A goal whose current step has run more than 3 times its estimate shows under Issues as stalled, naming the step and how long it has run.
5. A defect test linked to issue 96 proves two queued goals of different sizes get different estimates inside the range of their similar past goals.
6. Each done line becomes Given/When/Then scenarios on the Monitoring PRD page under MON-4, linked to rows.

## What Makes This Cool

Once a goal is running, the range tightens from its own pace. A goal sitting in ship for three hours against a 20-minute estimate turns up under Issues instead of hiding in the flow lines.

## Premises

1. The right problem is the size-blind model, not the per-step timing. `seconds_by_step` already reads each step's time from the run log; the fix is which runs feed the median and how size scales it. (Agreed, recommended.)
2. A goal's size is two counts we already have: its done lines (queue line `done:` parts, or the goal file's numbered list) and its touched areas (the `touches` list folded to areas by the one rule under Recommended Approach). Measured 2026-11-10: all 57 of 57 finished runs on this repo resolve both counts (goal file in the main checkout plus the run record's `touches`), so no new fields are needed in run records. (Agreed.)
3. Logged times are noisy: in-session goals include waiting for the owner, so some steps read hours. Medians and a 25th-to-75th percentile range absorb that better than means; capping outliers is out of scope. (Agreed.)
4. Doing nothing keeps every queued goal at about 15 minutes, which the owner already called wrong (issue 96). (Agreed.)
5. The deliverable is code inside existing skills; distribution is the existing release path (merge.py, the packaged ZIP). No new artifact. (Agreed.)

## Approaches Considered

### Approach A: Nearest-size medians with scaling (minimal viable plus the guarantee)
For each step, take finished goals whose done-line count and area count are each within 1 of this goal's ("similar"). Scale each one's step time by this goal's size over its size (size = done lines + areas), take the median, and clamp it to the similar goals' own min and max for that step. With no similar goal for a step, use that step's median over all finished goals. Sum the remaining steps. The range is the summed 25th and 75th percentiles of the same scaled values. "Rough" when fewer than 5 similar goals. Effort S (human ~1 day / CC ~30 min). Risk Low. Reuses `seconds_by_step`, `usual`, `step_left`, `graph.parse`.

### Approach B: Fitted per-step model (ideal architecture)
Fit time = a + b x done + c x areas per step by least squares over finished goals; show the prediction interval as the range. Effort M. Risk Med: 50-odd noisy samples give unstable fits, and "similar goals" and "rough" lose their plain meaning. Rejected: the done lines ask for medians of similar goals, and the fit is harder to explain on a board.

### Approach C: Size buckets (lateral)
Put goals in small/medium/large buckets by done lines + areas and show each bucket's median and range. Effort S. Risk Low. Rejected: two goals in the same bucket get the same estimate, which breaks "more done lines or touched areas gets a longer estimate".

## Recommended Approach

Approach A, auto-chosen as the recommended option (unattended run). Details:

- **Size:** `graph.size(item)` returns `(done_count, area_count)` from a parsed queue line; `board_status.size_of(run, root)` finds the same for a run: the queue line if it is still there, else `.loop/goals/<slug>.md` in the run's worktree, then in the main checkout (numbered Done lines; the run record's `touches`). Write a size as `(d, a)` and its scalar as `s = d + a`. Similarity uses both counts; scaling uses `s`; ordering is the componentwise one (a goal is larger when it has more done lines or more areas and no fewer of the other). Unknown size is `None`.
- **Area folding (one rule):** a path under `skills/` folds to its first two parts (`skills/workflow-monitoring/scripts/x.py` -> `skills/workflow-monitoring`); any other path with a folder folds to its first part (`dev/toy/t.sh` -> `dev`, `.github/workflows/x.yml` -> `.github`, `docs/wiki/Home.md` -> `docs`, `.loop/docs.tsv` -> `.loop`); a root file is its own area (`README.md`). The area count is the number of distinct folded areas.
- **Similar goals:** for a size `(d, a)`, the finished runs (status done, other slug, known size) with `|d_i - d| <= 1` and `|a_i - a| <= 1`, as done line 1 asks (similar done-line count and touched areas). The goal-level similar count is the number of such runs for the goal's own size, whatever steps they logged.
- **Per-step estimate, in this order:**
  1. Rates: for each similar goal that logged the step, `rate_i = t_i / s_i` (seconds per size unit). If no similar goal logged the step, the rates come from every finished goal of known size that logged it (the fallback, scaled the same way, so two goals of different sizes still differ).
  2. Raw estimate: `raw(s) = s x median(rates)`. The range is `low = s x q25(rates)`, `high = s x q75(rates)` using `statistics.quantiles(rates, n=4, method="inclusive")`; with exactly one rate, low = high = that one value times `s`.
  3. Monotone envelope over the componentwise grid: `est(d, a) = max over d' = 0..d, a' = 0..a with s' = d' + a' >= 1 of raw(d', a') x s / s'`, where `raw(d', a')` is computed the same way (similar set and rates for size `(d', a')`) on the same finished runs. If `(d2, a2)` is larger than `(d1, a1)`, every term of `est(d1, a1)` also appears in `est(d2, a2)` multiplied by `s2 / s1 > 1`, so `est(d2, a2) > est(d1, a1)`: a goal with more done lines or more touched areas (and no fewer of the other) always gets a longer estimate. Goals that are larger in one count and smaller in the other are not ordered, and done line 1 asks nothing of them. The grid is small (done lines and areas are under 15 here).
  4. Precedence: monotonicity wins over staying inside the similar goals' range. The envelope lifts an estimate only when a smaller size has a higher per-unit rate; then `high` is widened to `est` so the shown range always contains the estimate. When the envelope does not bind, `est = raw`, which lies between the similar goals' smallest and largest scaled times. The issue 96 defect test uses fixture runs where the envelope does not bind and asserts both properties for sizes 3 and 12.
  5. Unknown size: the step's median over all finished goals, unscaled; always "rough". This is the one accepted exception to monotonicity (there is no size to order by).
- **Rough:** the goal-level similar count is under 5, or the size is unknown.
- **Refining a running goal:** finished steps count with their actual time (zero left). Pace = (sum of actual times) / (sum of estimates) over the finished steps that had an estimate; with no such step, pace = 1; clamped to 0.5..2. Pace multiplies the estimate, low and high of the current step (before it overruns) and of every remaining step. Once the current step runs past its pace-adjusted estimate, `step_left`'s re-estimate takes over for that step, as today.
- **Board text:** `board_status.estimate_text(...)` returns `"<low> to <high> left"` using `status_graph.span` for each end (for example `20m to 45m left`, `1h10m to 3h00m left`), plus `", rough"` when rough; `"no estimate yet"` when no finished goal logged any step. `left_time` keeps returning the estimate in seconds, so the Finish line and status graph still work.
- **Stalled (issue 37):** `board_status.stalled(run, runs, at)` returns `(step, spent, estimate)` when a running goal's current step has run more than 3 times that step's pace-adjusted estimate (the estimate before any `step_left` re-estimate, so a growing re-estimate can never hide a stall). A step with no estimate is never flagged. `live_board.issues` appends `- <slug> is stalled: <step> has run <spent> (estimate <est>)` and a fix line pointing at the worker.
- **Tests:** a new toy test with fixture run records and goal files proves done lines 1 to 5, including the issue 96 defect row (two queued goals of sizes 3 (2 done lines, 1 area) and 12 (7 done lines, 5 areas) get different estimates, each inside its similar goals' min-max), seen failing once on the old code.
