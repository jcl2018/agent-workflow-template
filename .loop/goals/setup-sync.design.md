# Design: setup-sync: updates both ways, a generated entry point, one loop for every agent

Generated by /office-hours on 2026-11-10
Branch: loop/setup-sync
Repo: agent-workflow-template
Status: DRAFT
Mode: Builder

## Problem Statement

The template is meant to be a workspace any repo and any agent can carry. Three gaps stop that today:

- SET-4: an adopted repo can preview and apply a newer skills package (`update.py --from PACKAGE`), but it has no
  `--check` against the template's latest release, the repo half (new settings, generated files) never catches up, the
  operation board can't see which governed repo is behind, and a fix someone makes to a skill inside an adopted repo
  dies there.
- SET-5: a new session in an adopted repo has no single page to read first. The design logic sits in
  `skills/design-guide.md`, the features in `docs/wiki/*.md`, the settings in `.loop/config.json`.
- SET-10: setup writes nothing into `CLAUDE.md` or `AGENTS.md`, so Claude Code and Codex each discover the loop on
  their own, or not at all.
- Issue 47: without the private skill suite, delivery refuses every step, so the package does nothing standalone.

## What Makes This Cool

One `update` in any adopted repo brings the skills and every generated file up to the template's newest version and
stamps the repo with it (files setup newly seeds, such as a
new workflow, still arrive by running setup again, which only adds); the board then shows at a glance which repos lag. A fix made in any repo flows back as a
ready-to-file issue with its diff. And a fresh Codex session reads the same `AGENTS.md` block a Claude session reads in
`CLAUDE.md`, lands on `.loop/START.md`, and can name every feature and its command without a human.

## Constraints

- Every script self-contained and under 20 KB (`criteria.py` is already at 20,356 bytes; don't touch it).
- `setup-adopt` follows this goal and edits `skills/workflow-setup` too: new code goes in new modules, with only
  small call sites in `setup.py`.
- Nothing private in the repo: the entry point lists repo settings only; private values never appear. No private
  names in committed files or in the proposed issue body.
- The approved Delivery PRD (2026-11-10) says a goal "won't start without the flow set up" and `goal.py new` refuses
  with no skill flow. Issue 47 must not break that.
- Done lines are frozen.

## Premises

1. The update source of truth is a built package (ZIP with `PACKAGE.json`); the template's GitHub release carries it.
   `--from` stays for a local ZIP or folder.
2. Update has its own repo half: it adds missing repo settings, always overwrites `template_version`, regenerates
   `.loop/START.md` and the marked agent blocks, and only ever adds to hand-written data (config values, pages, rules,
   local settings), which is how it keeps them.
3. A skill file that differs from the installed package's hash is a local fix, and a local fix is by definition
   template-worthy: that's the detector for "proposed back".
4. A built-in default flow can live behind the existing flow file: setup writes a flow file whose steps say
   `built-in`, so "won't start without the flow set up" still holds while no private suite is needed.
5. The entry point is generated data about the repo, so it belongs in `.loop/`, and docs check owns its freshness.

## Approaches Considered

### Approach A: Patch in place (minimal)
Add `--check` and propose to `update.py`, write `START.md` and the agent blocks from inside `setup.py`, special-case
"no flow" in `flow.py`. Smallest diff. Rejected: `setup.py` (13 KB) would collide with setup-adopt in every hunk and
approach 20 KB; making "no flow" mean "built-in" contradicts the approved Delivery PRD and the `no-flow-refused` row.

### Approach B: Own modules, thin call sites (recommended)
- `workflow-setup/scripts/update.py` grows `--check`, a default source (the template's latest release), the repo half,
  the local-fix detector and `--propose`.
- New `workflow-docs/scripts/entry.py` renders, writes and checks `.loop/START.md` and the agent blocks; `docs.py
  check` calls it.
- New `workflow-setup/scripts/agents.py` wires the block into `CLAUDE.md` and `AGENTS.md` (via `entry.py`'s renderer).
- `workflow-monitoring/scripts/board_status.py` gets `template_lag()`; the live board's Issues list shows it.
- `workflow-delivery/scripts/flow.py` accepts the reserved step value `built-in`, whose routine lives in
  `workflow-delivery/references/default-flow.md`; `settings.py`'s suite default becomes `built-in`.

### Approach C: The agent files are the entry point (lateral)
Put the whole explanation in the `CLAUDE.md`/`AGENTS.md` block. Rejected: two copies of a long page, and a repo's own
`CLAUDE.md` gets buried under generated text.

## Recommended Approach

Approach B. Decisions:

### SET-4 update both ways (`update.py`)
- Two halves, one script. The skills half writes only the skills folder, as today. The repo half writes one target
  repo: `--repo DIR`, default the git toplevel of the current folder, skipped (with a line saying so) when that folder
  has no `.loop/config.json`. update.py's docstring invariant is revised to say exactly this. A skills folder shared by
  several repos updates once; every other repo catches up by running `update` there, and the board's lag line names
  each one still behind.
- `update.py --check` (and no flag, as today) is the preview: INSTALLED, AVAILABLE, WHAT'S NEW, each skill file to add,
  update or remove, each LOCAL FIX, and the repo's `template_version` against AVAILABLE. Writes nothing.
- `update.py --apply` (the Command map's `update`) applies the skills half (skipping local fixes, below), then the repo
  half whenever the repo's `template_version` is older than the installed package, even when no skill file changed.
- The repo half is its own code path in update.py, not a re-run of setup.py: (1) add each missing repo setting
  (settings.py's fill, never changing a value already set); (2) always overwrite `template_version` with the installed
  version, the one config value update owns, and write the resolved TEMPLATE into the installed
  `workflow-package.json` as `repo` on every apply (carried from the old stamp or the source), so the next default
  `--check` still finds it; (3) `entry.py write` (regenerates `.loop/START.md`); (4) `agents.py wire`
  (replaces only the marked block). Generated files (START.md, the marked blocks, the stamp) are replaced; hand-written
  data (existing config values, wiki pages, health rules, private settings) is only ever added to.
- Git: it refuses (with the fix) when any of the four paths below has uncommitted changes, then commits on a fresh
  branch `workflow-update-vX` cut from the config's base branch (an existing branch of that name
  is reused only if it isn't merged, else refused with the fix), staging exactly `.loop/config.json`,
  `.loop/START.md`, `CLAUDE.md` and `AGENTS.md`, message "Update the workflow loop to vX". It never merges or pushes.
  The person merges it like setup's branch.
- Source: `--from ZIP|DIR`, else the template's latest GitHub release. Releases carry no ZIP asset today (`gh release
  view` lists none), so update downloads the release's source archive (`gh release download TAG --repo TEMPLATE
  --archive zip`), which GitHub makes for every release, and `load()` learns to build the manifest from a source tree
  with no PACKAGE.json: every file under `skills/` (no `__pycache__`), the version from `VERSION`, the changelog from
  `CHANGELOG.md`. No change to the release step. TEMPLATE comes from the repo setting `template_repo` (new TABLE row,
  default empty), else the installed manifest's `repo` key (the package build writes it from `origin`); with neither,
  `--check` exits 2 naming `--from`. Errors (no gh, no release, a bad archive) exit 2; up to date 0; newer 1.
- Local fixes: a skill file whose hash differs from the installed `workflow-package.json` is a LOCAL FIX, a candidate to
  propose back (the person decides at the preview). `--apply` keeps it (KEPT) and says how to resolve it: `--take FILE`
  overwrites it with the package copy; `--propose` sends it back. A local fix in a file the new package drops is kept
  and reported, never deleted. An install with no `workflow-package.json` prints "LOCAL FIX: cannot detect (no
  workflow-package.json)" and updates as today.
- `--propose` (preview, prints the full title and body) / `--propose --file-issue` (files it with `gh issue create
  --repo TEMPLATE`): title "Fix from an adopted repo: <files>", body the unified diff of each local fix against the
  package copy and the version it was made on. Before printing or filing, it refuses when the body or title contains
  the repo's folder name, its `origin` owner or name, the home folder path, the user name, or any private
  `leak_prefixes` pattern; with `leak_prefixes` empty, the built-in checks still run.
- Board: `board_status.template_lag(root)` reads each followed repo (`~/.workflow-loop/repos` plus this one) and
  returns "REPO runs template vX, older than vY: run /workflow-setup update there" for each repo whose
  `template_version` is older than the installed package; a missing stamp reads "template version unknown". The live
  board lists these under Issues.

### SET-5 the entry point (`entry.py`, `.loop/START.md`)
- Rendered, deterministic (no clock), from: a short "How it fits together" part filled from this repo's own settings
  (its base branch, check commands, review depth, auto_merge, parallel, regression and health schedules) using the
  narrative in `workflow-docs/references/start.md`; a Features table from every PRD page in `wiki_dir` (name, milestone,
  the first sentence of Problem, and its Usage bullets as "how to use it"); a Settings table from `.loop/config.json`
  (each repo setting, its value, its `_help` line). Private settings are named as living in `~/.workflow-loop/` and
  never shown.
- The SKILL.md rule "Don't write skill instructions into the repo" gets one stated exception: the generated entry
  point and the marked agent block, which SET-5 and SET-10 (owner-approved) require, are rebuilt from the installed
  skills and the repo's data, and nobody edits them by hand.
- `entry.py render|write|check`. `docs.py check` runs the check: `STALE .loop/START.md` or `MISSING .loop/START.md`
  (exit 1), plus the agent blocks below, only in a repo whose config has `criteria: true`.
- Who regenerates it: `docs.py audit` (the one docs command) fixes it mechanically by running `entry.py write`, like the
  milestone lines it already fixes; a goal whose change makes it stale runs audit (or `entry.py write`) in build and
  commits it on the goal's branch, and the land lane's docs check catches a goal that forgot.

### SET-10 one loop, every agent (`agents.py`)
- One block, rendered by `entry.py`, between `<!-- workflow-loop -->` and `<!-- /workflow-loop -->`: read
  `.loop/START.md` first; the installed `workflow-*` skills, each with its one-line description from its SKILL.md
  frontmatter; how to run a command (ask for `<skill> <command>`; each skill's Command map names the exact script).
- `agents.py wire [--dry-run]` writes the block into `CLAUDE.md` and `AGENTS.md`, creating either file if missing and
  replacing only the block if present; text outside it is never touched. `setup.py` calls it (and stages both files).
- `entry.py check` also fails when either file's block is missing or differs (`STALE CLAUDE.md`, `STALE AGENTS.md`).

### Issue 47: built-in default flow
- Reserved step value `built-in`. `flow.py` reads that step's routine from `references/default-flow.md` (one section per
  step: idea writes `.loop/goals/<slug>.design.md`; plan writes the plan into the goal file; review reads the diff
  against base and fixes or lists findings; qa runs the repo's checks and the regression lane; ship checks version and
  changelog habits) and puts it in the prompt in place of "Use the X skill".
- Per-step rules, for all-built-in and mixed flows alike: the probe is required only when the step about to run maps to
  a named skill; `command` is required only when the step runs headless (no worker session); an in-session step needs
  neither. `flow()` checks the five steps are mapped (a skill or `built-in`), and the probe and command at the step.
- `goal.py new` already accepts any non-empty value for the five steps, so an all-built-in flow file starts a goal
  unchanged; a regression row proves it. No flow file, or one with empty steps, still refuses (`no-flow-refused`
  unchanged): the approved Delivery PRD holds.
- `settings.py`'s suite default becomes `built-in` for the five suite steps, and its private fill treats a suite whose
  every value is empty (with no `steps`) as never configured and fills it with `built-in`: machines set up before this
  change get the default flow on their next setup run. Update's repo half never writes the private flow file. A suite with any real value is never touched.
- The listing text and README say the package runs standalone through the built-in flow, and a configured suite
  replaces it step by step. Close issue 47 with that decision.

### Docs
- `docs/wiki/Setup.md`: SET-4 and SET-5 take the approved 2026-11-10 wording, SET-10 is added, each with its reviewed
  stamp; Usage gains `update --check`, `update`, `update --propose`, `entry` and `agents` lines; the Tests table is
  re-rendered from the rows.
- README How to use names `update --check` / `update` and the entry point; `loop-files.md` lists `START.md`,
  `template_version`, `template_repo`, the agent block and the `built-in` step value.

## Success Criteria

The frozen done lines, each proven by a regression row seen failing then passing, listed in the Setup Tests table:

  values, wiki pages, rules and private settings are byte-identical after; `template_version` is stamped.
- The live board run with a followed toy repo stamped older lists it under Issues.
- A toy local fix shows as LOCAL FIX, `update` keeps it, and `--propose --file-issue` files one issue (fake gh) whose
  body holds the diff and no repo name.
- `entry.py check` passes after write, fails STALE after a PRD page's Usage changes, and `docs.py check` fails with it.
- `agents.py wire` writes the same block into `CLAUDE.md` and `AGENTS.md`, keeps text outside it, and changes nothing
  on a second run.
- With a flow file whose steps are `built-in` and no probe, `goal.py new` starts a goal and `flow.py SLUG idea` in a
  worker prints IN SESSION with the built-in routine; with no flow file it still refuses.
