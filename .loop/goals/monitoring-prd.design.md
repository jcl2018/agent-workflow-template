## Problem Statement

The owner approved the Monitoring PRD on 2026-11-10 (MON-4, MON-6 to MON-12). Today the operation session:

- prints the full live board at every check-in (operate.py `one_pass` runs `board.py board`, which runs live_board.py),
  although MON-4 now limits the board to `report`, `dashboard` and "where do things stand";
- leaves a merged goal's session busy when the goal was already done (issue 175: `sessions.py report` takes the KEPT
  branch at sessions.py:293 and returns before `release()`), and never removes the goal's worktree or branch (MON-6);
- starts ready goals in `watch --once`, but never proposes merges or splits, never orders the merge line by the
  critical path, and logs no reason for a change (MON-10);
- waits on the owner for every worker question, even routine ones with a recommended answer (MON-11);
- can edit, commit and push like any session; only goal steps refuse (role.py guard), MON-7;
- names a silent worker only after an hour (live_board `QUIET` 3600; board.py uses 1800), MON-8;
- has no time bound on the board: `pr_states` asks gh once per done run, each with a 20 s timeout (MON-9);
- starts a brand-new session for each goal when the pool is empty, and cannot create sessions itself, since only the
  desktop app can (MON-12).

Plus ten issues: 94 and 123 (dependencies as a flat `a --> b` list, not a graph), 97 (long raw Issues lines, a shared
stop shown as four failures), 111 (report and board digest ignore held and freezing goals), 112 (`holds_slot` ignores
the pool), 113 (four places work out goal state alone), 114 (no attempt identity on reports), 115 (held time is time
since last change), 122 (pool edge cases), 175 (above).

## What Makes This Cool

The owner runs ten goals at once and is asked only for what is truly theirs. Every check-in has the same layout, every
change the operation session makes comes with its reason, a finished session goes straight to the next goal, and the
board shows the whole graph on a phone.

## Constraints

- Scripts stay under 20 KB (workflow-health). live_board.py 18.6 KB, watch.py 19.5 KB, sessions.py 18.5 KB,
  reply_hook.py 19.3 KB and board.py 16.2 KB are near it, so nearly all new code goes into new modules, and edits to those
  files are a few lines each.
- estimate-model (commit 7eb7f72) edits live_board.py and merges first; delivery-prd edits skills/workflow-monitoring too.
  Keep live_board.py edits to call sites, and merge main often.
- Done lines are frozen. Monitoring.md's requirement text belongs to docs-format: this goal only adds rows to its Tests
  section (re-rendered from regression rows) and its Usage lines.
- Only the desktop app can create, archive or rename a session. A script can record, ask and print the one action;
  the operation session (an LLM with the app's tools) does the act.
- No private names or paths in committed files. Every regression row is seen failing on the old code.

## Premises

Each "Agreed" is the worker's own call with the recommended answer (unattended step); the owner approves at the PR.

1. One shared module decides a goal's state (issue 113). Board, report, digest, watch and handoff read it, so held,
   freezing, silent and slot-holding mean the same everywhere (fixes 111 and 112 as side effects). Agreed.
2. The check-in reply (MON-5 layout) is what the operation session prints at each pass; the board is printed only for
   `report`, `dashboard` and the status question (MON-4). operate.py prints a check-in block instead of the board. Agreed.
3. MON-10 re-planning is advisory except for starts: starting ready goals is automatic (it is today), while merges,
   splits and merge-line order are proposals logged with reasons and listed in the check-in. Nothing running is
   stopped. A merge or split changes frozen goals, so only the owner applies one (with the existing `board.py retire`
   and a new queue line); full auto never applies a merge or a split, and never reorders merge.py: the merge-line order
   is advisory, shown in the check-in. Agreed.
4. Full auto (MON-11) acts on structured decisions, and only from the operation session: a worker's waiting report
   records the question, the options, the recommended one and a required kind; the worker's own process never answers.
   At its next pass the operation session's `auto.py pass` sends the recommended answer for each decision that is not
   excluded, and logs question, answer and reason. Only kind `routine` can be auto-answered; a missing or unknown kind,
   a keyword hit or an owner answer it would contradict all wait. Any doubt waits. Agreed.
5. MON-7 is kept by a Claude Code PreToolUse hook (like the reply hook's Stop hook): a guard against the operation
   session's own tool use, not a sandbox. In the operation session it blocks Edit, Write and NotebookEdit, and Bash
   commands whose parsed git subcommand writes history (commit, push, merge, rebase, reset, cherry-pick, revert, am),
   unless the command runs one of the listed merge and post-merge scripts. It recognises the operation session the
   same way reply_hook does. Agreed.
6. The session pool (MON-12) is a size target over the existing pool file. Scripts count free/busy/total and say how
   many are missing (K, below); the operation session asks the owner at the desktop while K > 0 and the owner hasn't
   declined that shortfall, and on their word creates all K sessions in one step and registers them with one command.
   Agreed.
7. MON-6 cleanup: a merged goal's session returns to the pool (or is archived when the pool is full), and its worktree
   and branch are removed only when the PR is merged on GitHub and the worktree has no uncommitted change. Agreed.

## Approaches Considered

### Approach A: Minimal patches in place
Patch each file where the behaviour lives (live_board, sessions, operate, watch, board). Effort M, risk high: four
files are within 2 KB of the 20 KB limit, and two other goals edit the same files. Rejected for the size limit.

### Approach B: New modules behind thin call sites (recommended)
New modules, each one concern, each under 10 KB; existing files gain one import and a call:

| Module | Does | Requirement / issue |
|---|---|---|
| `goal_state.py` | `classify(run, taken, at)` → state (running, waiting, failed, stopped, held, freezing, silent, done, merged, retired, queued), held_at, holds_slot with the pool; used by live_board, board, monitor, watch, handoff | 113, 111, 112, 115, MON-8 |
| `dep_graph.py` | draws running and queued goals top to bottom, ≤ 60 columns, markers `[>]` running, `[=]` holding, `[ ]` queued, `[?]` waiting on you, with a legend; multi-parent goals drawn once with every arrow | 94, 123 |
| `issue_lines.py` | turns Issues into ≤ 60-column lines, groups goals stopped by one cause (usage limit) into one line, never prints raw agent output, and says "paused until …" for the finish while all work is paused | 97 |
| `pool.py` | `status` (free/busy/total vs `pool_size`), `need` (missing count, one-step fix), `add ID… ` (register new idle sessions), `return SLUG` (back to the pool or archive), quarantines one bad entry instead of blocking all, attempt ids | MON-12, MON-6, 114, 122, 175 |
| `replan.py` | at each check-in: re-read progress, list starts (watch does them), propose merges (same PRD and overlapping touches), propose splits (a goal two or more others wait on whose queue line names a ready part), order the merge line critical path first; append each change with its reason to `loop/replan.log` | MON-10 |
| `auto.py` | `decide SLUG` for a waiting report: excluded → Needs you; else full auto sends the recommended answer, logs to `loop/auto.log`; config read at each decision | MON-11 |
| `govern_hook.py` | the PreToolUse hook for MON-7, installed by `setup.py --govern-hook`, `govern_hook: false` turns it off | MON-7 |
| `checkin.py` | the check-in block operate.py prints instead of the board: headline, All sessions (with pool free/busy/total), Dependencies (dep_graph), Needs you (issue_lines + auto-excluded decisions), Coming up, then Re-plan and Auto-answered logs | MON-4, MON-5, MON-10, MON-11 |

Effort L, risk medium. Reuses graph.read_pool/assigned/ready, status_graph.chain (critical path), reply_hook's
operation-session detection, settings.py TABLE for defaults, live_board.fit for width.

### Approach C: One "operator brain" module replacing watch and board
Rewrite watch/board/monitor around a single state engine. Best long-term, but XL and collides with estimate-model and
delivery-prd mid-flight. Rejected for scope and merge risk.

## Recommended Approach

Approach B. Details by requirement:

**MON-4 / check-ins.** operate.py `one_pass` keeps building board.json and board pages (dashboard needs them) but prints
`checkin.py`'s block, not the live board. `monitor.py report`, `monitor.py dashboard` and `board.py board` (asked
directly) still print the board. SKILL.md and operation.md say the board prints only for report, dashboard and "where do
things stand".

**MON-6 / issue 175.** In sessions.py `cmd_report`, the KEPT branch frees the session when the report is `merged`
(a 3-line change). A merged report then runs `pool.py return SLUG`: the session goes back to the pool as free (watch's
next pass assigns it the next ready goal), unless the pool's total is already above `pool_size`, when it is marked
`archive` and the check-in tells the operation session to archive it with the app. One rule, used by MON-6 and
MON-12 alike: archive exactly when total > pool_size; a regression row checks total = pool_size keeps it and
pool_size + 1 archives it. The worktree is removed with
`git worktree remove` (refused when dirty: then the check-in names it) and the branch with `git branch -D` after gh says
MERGED. `worker.py cleanup` already deletes merged `loop/*` branches; pool.py reuses it.

**MON-7.** govern_hook.py reads the PreToolUse JSON. It acts only when the session is the operation session: the same
signal as reply_hook (latest signal `operate.py run`, cwd not under loop/worktrees), or a session id recorded in
`loop/operation.id` by `operate.py claim`. It blocks Edit, Write and NotebookEdit, and Bash commands where shlex
splitting (on `&&`, `;`, `|`) finds `git` with any `-C DIR`/`-c k=v`/`--git-dir` options skipped and a subcommand in
commit, push, merge, rebase, reset, cherry-pick, revert or am. The rule is per segment: each segment is judged on its
own, a segment that runs a listed script (skills/workflow-release/scripts/merge.py, release.py, autorelease.py,
wiki.py, or skills/workflow-monitoring/scripts/pool.py `return` and worker.py `cleanup`: the merge and post-merge
steps) is allowed, and a git history-write segment is blocked even when another segment of the same command runs a
listed script, so `merge.py X && git push origin main` is blocked. A regression row checks that case. The block names the worker command. It is
a guard against accidental tool use, which is what MON-7's done line asks of the session; shell writes such as
`sed -i` are not parsed and are out of its claim. Fail open on error, log one line.

**MON-8.** goal_state's silent rule: a session or background worker with no report for `silent_minutes` (default 30)
shows under Needs you with its fix. live_board's QUIET default becomes 1800 and reads goal_state.

**MON-9.** `pr_states` runs gh calls in a thread pool with a 5 s timeout each and caches each PR's state in
`loop/pr-states.json` for 60 s (a MERGED or CLOSED state forever); health is read from the cached verdict when one is
under 10 minutes old. A toy test builds the board for 12 goals with a fake gh that sleeps 3 s and asserts < 10 s.

**MON-10.** replan.py runs in operate.py's pass after watch. It never stops or restarts a running goal. Log format, one
line per change: `<time> <kind> <slugs>: <reason>`; the check-in lists the changes since the last check-in.

**MON-11.** `full_auto` in settings.py TABLE, default true. Workers report a question with
`sessions.py report SLUG --status waiting --ask Q --words W1 --words W2 --recommend W1 --kind K` (K in routine,
destructive, money, security, owner). The report only records `waiting` with `recommend` and `kind`; the worker's
process never answers. `auto.py pass`, run by operate.py's pass after watch (and by the operation session at a manual
check-in), decides each waiting goal once:
- excluded (stays under Needs you, logged "waits: <why>") when the kind is missing, unknown or not `routine`; when
  there is no `--recommend`; when the question or the words match a keyword (delete, remove, drop, rm, reset --hard,
  force, overwrite, publish, release, deploy, merge to main, push, pay, purchase, billing, cost, permission, access,
  token, secret, credential, key, license); or when `loop/answers.jsonl` holds an owner answer for the same goal and
  the same question key (the question lower-cased, spaces collapsed) with different words;
- otherwise answered: auto.py sends the recommended words through `operate.py send` (the inbox and the session
  message, the channel an owner answer uses), the worker treats them as the owner's answer and runs `goal.py answer`
  itself as today, and auto.py appends `time | slug | question | answer | reason` to `loop/auto.log` and marks the
  run's `waiting.auto` so it is never sent twice.
`operate.py send` appends each owner answer to `loop/answers.jsonl` (slug, question key, words). With `full_auto` false
nothing is sent; the setting is read at each decision, so turning it off applies at the next one.

**MON-12.** `pool_size` (default 20) in settings. `pool.py status` prints `pool: F free, B busy, T total (target N)`; the
board and check-in show it. K = max(pool_size - total, ready goals - free, 0). While K > 0 the check-in's Needs you
asks: "Fill the session pool: create K sessions? (type: fill pool, or: no pool)". The ask repeats at each check-in
until filled; "no pool" records the declined K in `loop/pool.json`, and the ask comes back only when K grows past it.
On "fill pool", the operation session creates K sessions with the app in one step and runs `pool.py add ID1 ID2 …`. assign takes a pooled free session first
(existing). A ready goal that finds no free session waits under Needs you with that one action.

**Issues.** 111: monitor report and board digest list held/freezing via goal_state. 112: holds_slot reads the pool
(goal_state). 113: goal_state. 114: bind stamps `attempt` (a counter) on the run and pool entry; reports carry it and an
older attempt's report is recorded but not applied; freed_from survives reuse in a `history` list. 115: `held_at`
stamped when a goal first reads as held, cleared when bound; the board shows "held 2h". 122: (1) a retired run with a
busy session shows in Issues and is freed by `pool.py return`; (2) = 175; (3) read_pool quarantines a malformed entry
into `loop/session-pool.bad.json` and carries on, naming it under Issues.

**Remedy**

### R3-19 — consistency (minor)

**Problem**

**Remedy**

> Reword Premise 5 to the per-segment rule: a segment that runs a listed script is allowed, and a git history-write segment is blocked whatever its sibling segments run.
