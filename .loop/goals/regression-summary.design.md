## Problem Statement

Tests show up in three places, and each shows less than REG-2 asks:

- **GitHub run summary** (`actions.py` WORKFLOW): one flat `| Row | Result |` table. Toy tests that run as rows inherit the job's `GITHUB_STEP_SUMMARY` and append their fixture tables to it (issue 92: `check-1 PASS`, `flag FAIL`, `add-median-1 PASS` bury the real results).
- **Wiki Tests tables** (`criteria.py table`/`scenario`): grouped by page and requirement already, one line per test, but no kind and no issue state for defect tests.
- **Health report** (`health.py`): no test list at all, only sync findings.

## Premises (accepted)

1. A *feature* is the wiki page that holds the requirement a row guards (row goal or id = requirement ID -> its page). Rows that guard no requirement (goal `-` or a done line `slug:N`) fall in one last group, "Other".
2. The fix for issue 92 belongs at the root, the workflow runner: a row's environment never carries `GITHUB_STEP_SUMMARY`, the same way it never carries the GitHub token. Toy tests also stop inheriting it, as a second guard.
3. The wiki must stay deterministic (docs check compares a fresh render). So issue states are not fetched live when rendering: `regression.py run` records each defect link's state with its date in the run record, and every place reads that.
4. Done line 5 is already true on main (`sync` prints no `NODESC`, issue 91 is closed). It needs a recorded result, not new work, plus a check that every description is one line.
5. The wiki renderer lives in `skills/workflow-docs/scripts/criteria.py`, outside the declared touches. Done line 4 can't be met without editing it, so the build edits it and the PR says so. narrow-rows edits `lanes.py`; this goal leaves `lanes.py` alone.

## Approaches Considered

### Approach A: three renderers, aligned by a test (minimal)
Extend each of the three in place with the same fields; a toy test renders one fixture three ways and compares fields. Effort S-M, risk low. The format still lives in three places and drifts the day someone edits one.

### Approach B: one renderer, `tests.py`, used everywhere (recommended)
A new stdlib-only `skills/workflow-regression/scripts/tests.py` owns the one fixed format: it reads the wiki pages (requirement IDs and words by page), `.loop/regression.tsv`, the run record and the recorded issue states, and prints the grouped list as Markdown tables (`list --markdown`) or plain lines (`list`). `--results FILE --took S` renders a run's own results with a header (totals and run time) for the GitHub summary.
- The workflow embeds `tests.py`'s source when `regression.py workflow` writes it, because a consumer repo's GitHub job has only its own checkout. The coverage test that the committed workflow equals the generated one keeps them in step.
- `criteria.py` imports `tests.py` from its sibling skill for each line's fields (the import pattern health already uses for siblings), keeping its requirement headings, Given/When/Then words and **not enforced** markers that DOC-3 and audit rely on.
- `health.py` prints the grouped list after its verdict by running the sibling `tests.py list`.
Effort M-L, risk medium (workflow size; cross-skill import).

### Approach C: summary links out to the wiki (lateral)
The run summary shows totals and links to the wiki Tests tables. Ruled out: done line 3 wants the tables in the summary.

## Recommended Approach

B, because REG-2 says "one fixed format", and one renderer is the only way it stays one.

Per-test fields, in this order everywhere: test name, kind (requirement or defect), guards (requirement ID and words, or issue link and its recorded state), checks (the row's one-line description), runs (land = every push and nightly, nightly, by a person), last result and date, seen failing (date or no).

## Done-line map

1. REG-2: `criteria.py unreview REG-2 --user`, rewrite the line word for word, `criteria.py review REG-2 --user --date 2026-11-08`.
2. Strip `GITHUB_STEP_SUMMARY` from `ROW_ENV`; new defect row linked to issue 92 runs the runner with a row that writes to the summary, and checks the summary holds only real rows; `red --break` removing the strip shows it fail.
3. Workflow summary: one header (totals, run time), then one table per feature from `tests.py`.
4. Wiki Tests lines and the health report use `tests.py`'s fields.
5. Recorded result for `every-row-described`, plus a one-line check.
6. Toy test: a made-up repo with two features, requirement and defect rows, renders the expected tables.
7. Each done line gets Given/When/Then rows under the requirement it serves on the Regression page (REG-2, REG-4 and the defect section), rendered by `criteria.py render`.

## Open Questions

- Script sizes: `regression.py` (19,856) and `criteria.py` (19,117) are near the 20 KB limit, so new code goes in `tests.py`, and each edit there must stay small.
- The workflow grows by the size of `tests.py`; keep it lean.

## Success Criteria

The seven frozen done lines, checked by their rows; the land lane, docs check and health stay green.
