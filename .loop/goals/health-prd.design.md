## Problem Statement

The owner approved a new Health PRD (HLT-1..HLT-9, 2026-11-10). Health today has 7 groups (size, criteria, docs, hygiene,
cost shown as performance, mine, controls) and 12 rules. Every health issue lands on Backlog. A model "judge" gives
suggestions. The PRD asks for four things:
- **Groups.** Exactly twelve groups, each with a stated angle, plus Mine. Every rule has a negative control.
- **Review.** A reviewer that reads everything per feature and reports conflicts, gaps, drift, weak tests and savings,
  with evidence.
- **Filing.** Findings filed on the milestone of the feature they are about, with an open issue that already covers
  one linked, not duplicated.
- **Triage.** Open findings shown per feature.

The non-functional requirements: deterministic and read-only (HLT-1), under 60 seconds without controls (HLT-7), and
evidence or nothing (HLT-9).

Four open issues are in scope:
- **118.** An Unreviewed requirement with no row fails health.
- **124.** Cost is UNREAD when no finished goal recorded tokens.
- **158.** The judge's error drops the command's stderr.
- **159.** Stale run chart and SKILL.md description.

## What Makes This Cool

One command tells the owner, per feature, where the repo falls short of its own PRDs. Every finding becomes an issue on
that feature's milestone with its evidence. The owner triages them in one place.

## Constraints

- Scripts under 20 KB (health.py is 18.4 KB): the new rules live in new modules, one per few groups.
- At most 12 groups plus Mine; the cap moves from rules to groups (HLT-2 caps groups).
- check stays read-only and deterministic; only `file` and triage's batch close write, and only GitHub issues.
- The wiki page Health.md is rewritten by the docs-format goal; this goal adds rows and re-renders its Tests, and links
  rows to HLT ids.
- lane-control is adding a REG-7 rule in skills/workflow-health: edits stay isolated (new modules, small edits to
  health.py's tables).
- The first inspection waits for docs-format and the owner's word after the preview.

## Premises

The worker took each premise with the recommended answer (an unattended step).
1. The twelve groups are built from today's rules, regrouped, plus new deterministic rules. Each rule is a small
   function returning rows, and each rule has a fixture in controls.py. Agreed.
2. review is a new command (review.py) with two layers:
   - deterministic analyses per feature (gaps, conflicts and drift that can be checked mechanically);
   - the judge command for the judgment kinds (conflicts in meaning, weak tests, savings).
   Every model finding must cite evidence that review.py can verify exists: a requirement ID on a page, a file:line in
   the repo, a regression row id, or an issue number. Unverifiable findings are dropped. Agreed.
3. A finding's feature comes from its subject:
   - a path, mapped through .loop/docs.tsv (the longest prefix wins);
   - a requirement ID's page;
   - an issue's milestone;
   - review findings name their feature.
   Backlog only when nothing fits. Agreed.
4. "An open issue already covers it" is decided deterministically: an open issue on that milestone whose title or body
   names the finding's subject (the same path, requirement ID or row id) and is not itself a health issue. Agreed.
5. A batch close records the owner's words on each issue and a `health:closed` label. The finding's marker carries an
   evidence hash, so a closed finding is refiled only when its evidence hash changes. Agreed.

## Recommended Approach

B. The groups and rules:
- **Requirements.**
  - `rows`: a Reviewed requirement with no row FAILs. An Unreviewed one WARNs "not enforced" (fixes 118).
  - `proof`: a draft row FAILs (never-failed belongs to Tests `seen-red`).
  - `done`: done lines with no row WARN.
  - `not-enforced-7d`: a Reviewed requirement whose review stamp is older than 7 days, with rows but none passing in
    the last recorded run, FAILs.
- **Traceability.**
  - `defect-tests`: as today.
  - `issue-milestone`: an open issue with no milestone WARNs.
  - `row-requirement`: a row whose goal id names no requirement on any page FAILs.
- **Consistency.**
  - `ids-unique`: a requirement id defined on two pages FAILs.
  - `refs`: a reference to a missing id in a page or row FAILs.
  - `usage-readme`: a `/skill verb` in the README that no page Usage names WARNs.
- **Docs.** `docs-check`: composes docs.py check, as today.
- **Freshness.**
  - `nightly`: the newest nightly lane record is older than 24 hours (WARN; INFO when no nightly is set up).
  - `unreleased`: merged work unreleased for over 3 days (commits after the last release tag, older than 3 days) WARNs.
  - `finding-age`: an open health issue older than 30 days WARNs.
- **Tests.**
  - `seen-red`: a row never seen failing FAILs (moved from proof).
  - `skipped`: a row recorded SKIPPED for over 7 days WARNs.
  - `network`: a row command that names curl, wget or http:// outside fakegh WARNs.
- **Performance.**
  - `cost`: as today, but goals with no tokens recorded are left out (fixes 124); UNREAD only when no finished goal
    can be read at all.
  - `test-time`: as today.
  - `check-time`: measured in-process; PASS under 60 seconds, WARN over, no number in the line, no file written.
- **Security and privacy.**
  - `private`: tracked files hold no private names, paths, emails or keys, from the private patterns setting
    (`leak_patterns` in the private flow file); a fixture plants one.
  - `scan-hook`: the commit scan hook is installed (`.git/hooks/pre-commit` or core.hooksPath) and WARNs when missing.
  - `workflow-permissions`: each workflow declares `permissions:`.
- **Size.**
  - `scripts`: as today.
  - `skill-lines`: SKILL.md under 150 lines.
  - `requirements-per-page`: at most the docs limit.
- **Hygiene.** `findings`, `waiting`, `branches`, `worktrees` and `local-branches` (as today), and
  `idle-sessions` (a busy pool session whose goal ended, WARN).
- **Adoption.**
  - `config`: config.json parses and has base.
  - `checks-run-tests`: every enabled check runs at least one row.
  - `template-version`: VERSION matches listing.json's version.
  - `scheduled`: the nightly and health workflows exist.
- **Controls.** `controls`: every rule has a negative control and fires on its fixture.
- **Mine.** As today.

Each group prints its angle under its heading: `== Requirements (my angle: is every promise I approved proven?) ==`.
The group cap is `MAX_GROUPS = 12`, enforced at import. Rules are uncapped, but each needs a control (refuse otherwise).

review (`review.py [--feature NAME]`):
- Per feature (docs.tsv pages except Home), it reads the page requirements, Usage and Problem, the README, the
  feature's milestone and open issues (gh, read-only), its rows and the code under its paths.
- Deterministic findings:
  - conflicts: a page breaking DOC-1's limits;
  - gaps: no non-functional requirement, an untested requirement, an open issue naming no requirement id, a done
    line with no row;
  - drift: a Usage command whose verb isn't in the skill's command map.
- Model findings come through judge_command with a prompt asking for tagged lines
  `FINDING|feature|kind|angle|evidence|fix`. Each evidence is verified (a page id exists, a file:line exists, a row id
  exists, an issue number is open or closed in gh). Unverified ones are dropped and counted.
- It ends with ranked next steps per feature and writes nothing.

file and preview:
- A finding's milestone comes from feature.py (paths through docs.tsv, requirement ids through their page, review
  findings through their feature). Backlog only when nothing fits.
- Labels: health plus `health:<group>` or `health:review-<kind>`.
- A covering open issue (premise 4) gets a LINK action: a comment on that issue naming the finding, and no new issue.
- The marker gains `evidence=<sha8>`. A closed issue labelled `health:closed` with the same evidence hash is SAME, not
  reopened.

triage (`file.py triage [--feature NAME]`, exposed as `health.py triage`):
- It lists open health issues per milestone by kind (label), age in days and count.
- `triage --close --feature F --kind K [--older DAYS] --why "owner's words"` always prints the full list of matched
  issues first. Without `--yes` that is all it does. With `--yes` it closes exactly the printed list, with the words as
  a comment and the `health:closed` label. It refuses without --why.

Issue fixes:
- **118.** Requirements rows split Reviewed and Unreviewed: Reviewed-ness is read from the page (the criteria.py LINE
  regex) inside health, and sync's GAP lines are joined with it.
- **124.** Cost leaves out goals with no tokens recorded.
- **158.** The judge's error carries the first stderr line, and setup's check runs the judge command with `--version`
  when there is one (otherwise it reports "untested").
- **159.** The SKILL.md description and the commands reference charts are rewritten (check, preview, file, review,
  triage).

## Rule contracts (from the spec review)

These contracts supersede any conflicting text above.


- One owner per condition. Requirements `proof` covers draft rows only, and Tests `seen-red` owns "never seen
  failing". Requirements `rows` covers a Reviewed requirement with no row. `not-enforced-7d` covers a Reviewed
  requirement whose review stamp (`**Reviewed YYYY-MM-DD**` on its page line) is older than 7 days and that has rows,
  none passing in the last recorded run. Hygiene `findings` counts open health issues over the cap of 5. Freshness
  `finding-age` names any open health issue older than 30 days. Review never re-reports a condition a check rule
  owns: it reuses check's rows for DOC-1 limits, done lines and untested requirements.
- No volatile text in a line. `check-time` is measured in-process: PASS under 60 seconds, WARN over, with no number
  in the line, so two runs print the same lines (HLT-1). No file is written. Ages and counts appear only in WARN
  details, never in a PASS.
- Network and local state:
  - gh-dependent rules (`issue-milestone`, `finding-age`, issue references) share one batched
    `gh issue list --state all --limit 500 --json ...` per run, paginated until no page is full (no 500 cap). An issue
    number not in the fetched set is looked up with `gh issue view N` (cached per run). With gh missing or failing they
    are INFO "gh not available here", never PASS, never FAIL.
  - Local-only rules (`scan-hook`, `idle-sessions`, `nightly`, `private` with no patterns) are INFO "not applicable
    here" where their local state is absent, such as the scheduled workflow's fresh clone.
  - The goal: a fresh clone without gh is not red for missing local state.
- `private` shows only `file:line` and the pattern's name, never the matched text, in check and in filed issues. Its
  control asserts the planted text appears in no output.
- Evidence hash: `sha8(key + "|" + evidence)`. A row's `evidence` field holds only stable citations (a requirement id,
  a path, a row id, an issue number). Never details, ages, counts or sizes. A review finding's hash input is normalized:
  its feature and kind plus its verified citations, each with line numbers stripped to the path, sorted. Different but
  equivalent model wording or a shifted line keeps the same hash. A
  closed `health:closed` issue with the same hash stays closed.
- LINK is idempotent. The comment carries `<!-- loop-health-link KEY evidence=H -->`, and file skips an issue whose
  comments already hold that marker. Covering means an exact token match with boundaries: the same path, requirement
  id or row id in the title or body of an open, non-health issue on the feature's milestone. Findings with no such
  subject never LINK.
- Review to file:
  - `review [--feature F] [--json]` prints findings and writes nothing.
  - `preview --review FILE` and `file --review FILE` read a saved `review --json` output that the caller redirects
    (`review --json > r.json`). Filing never calls the model, and preview and file see the same findings.
  - A model finding's feature must be a docs.tsv page; otherwise its milestone is Backlog.
- Review without a judge: the deterministic layer always runs. With judge_command absent or failing, review prints
  `JUDGE UNAVAILABLE: <the command's first stderr line or reason>` and its deterministic findings, and exits 0. HLT-1's
  determinism covers check and review's deterministic layer; model findings are labelled as such.
- triage `--close` is a dry run by default: it lists each matched issue (number, title, age). `--yes` closes them with
  the owner's words. Zero matches prints `NOTHING TO CLOSE`, and --why is required. triage lives in a new triage.py
  (file.py is 8.1 KB; it gains the milestone map, LINK and the hash).
- Groups are exactly twelve, checked by an equality assert at import. Every rule except the controls rule itself and
  Mine's private rules needs a control. A rule without one makes health.py refuse with exit 2, as today. lane-control's
  REG-7 rule registers by adding its name to its group in groups.py.
- Precise inputs:
  - `network`: a land row command containing `curl `, `wget `, `http://` or `https://`, unless the path is under
    `dev/toy/fakegh`.
  - `checks-run-tests`: each level a workflow runs (land, nightly) has at least one row.
  - 158's setup check: `command -v` on judge_command's first word, printed as found or missing. The judge's error
    carries the command's first stderr line.

**Remedy**

### R2-6 — completeness (blocking)

**Problem**

**Remedy**

> Normalize review evidence before hashing: for example, strip line numbers to the path, sort multiple citations, and hash only the verified citation set plus feature and kind. Or state that review findings are deduplicated by a stable key that leaves out the model's free text.
