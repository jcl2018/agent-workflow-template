## Problem Statement

The owner approved ("a", 2026-11-10) a Deployments section for feature pages: "A feature page that ships something
people can open has a Deployments section (optional otherwise): one row per public or private page, with its link, who
can open it (public or sign-in), what it shows, and the live build (the sha in build.txt). A check fails when a listed
public link doesn't answer or the live build isn't the promoted one."

Today the page contract (criteria.py, driven by the `rules` block in skills/workflow-docs/references/template.md)
refuses any section but Problem, an optional Usage, Requirements, Non-goals, Success metrics and Tests (`SECTIONS`), so
a deploying repo's pilot cannot add one. The owner widened it the same day: "the newsletter also gets a deployment for the
delivery… send the attachment to that email", so the section covers pages people open and deliveries people receive.
Also in this goal: issue 495, the govern hook blocks `git pull --ff-only`, which only
fast-forwards and is safe in the operation session.

## What Makes This Cool

A page that ships something says where it lives, who can open it and which build is live, in the same enforced format
as everything else, so a reader of the wiki can open the thing the page describes.

## Constraints

- Scripts stay under 20 KB: criteria.py 18.4 KB, docs.py 18.0 KB, prd.py 17.8 KB, pageformat.py 16.1 KB. The shape
  check goes in pageformat.py (room ~4 KB); criteria.py only learns where the section may sit.
- The skill package cap: 99 files, 97 used. No new file under skills/ (a toy test under dev/ is outside the package).
- The live-link and promoted-build check stays in a deploying repo's pilot for now (the operation session's brief); the template
  only checks the table's shape.
- Done lines frozen; the Documentation page is Reviewed, so adding DOC-14 changes its Requirements fingerprint and needs
  the owner's review stamp, which the owner gave: "a".

## Premises

Each "Agreed" is the worker's call with the recommended answer (unattended); the owner approves at the PR.

1. Deployments is an optional section placed after Success metrics and before Tests, like Usage is optional between
   Problem and Requirements. Its name, columns and access words live in the rules block, so a repo can see and change
   them in one place. Agreed.
2. The template checks shape only. The section holds one or two tables and blank lines, nothing else (no prose, no
   empty section): a Page table with the header exactly `| Page | Link | Access | Shows | Live build |`, and/or a Delivery
   table with exactly `| Delivery | Channel | Recipients | What's sent | Status |` (cells compared after trimming spaces,
   case-sensitive), each with its separator row and at least one row of five cells; at most one table of each kind.
   Page rows: Page and Shows non-empty, Link an http(s) URL (bare or `[text](url)`), Access `public` or `sign-in`, Live
   build a 7 to 40 hex sha (a page with no build yet is refused: the owner's wording gives every page a live build).
   Delivery rows: Delivery, Channel, What's sent and Status non-empty, Recipients a group name and never an email
   address (anything matching `x@y.z` is refused). A `|` inside a cell must be escaped `\|` (as in every table here).
   Each refusal reads `FORMAT <Page>:<line>: Deployments: DOC-14 <what> (got <value>). Fix: <how>`, the shape of the
   DOC-4..DOC-9 refusals, and names the table and column. Agreed.
3. Deployments is not part of the PRD fingerprints: it is live data that changes with each deploy, not owner wording.
   Sections are split at their `## ` headings (criteria.sections, pageformat.parts), and prd.names fingerprints only
   Problem, Requirements, Non-goals, Success metrics and Usage, so Success metrics ends at the Deployments heading and
   the fingerprints need no change. prd.py's review and convert paths (review_text, convert_text) list a page's sections
   leaving out the optional Usage; they leave out the optional Deployments the same way (rules key deployments_section),
   so `criteria.py review PAGE --user` and `prd.py convert` work on a page that has it. A toy case proves a Deployments
   edit leaves a Reviewed page neither LOCKED nor CHANGED, and that review works on a page with the section.
   render rewrites only what follows `## Tests` (render.py keeps everything before it), and Deployments sits before
   Tests, so a render keeps it byte for byte; a toy case proves it. Agreed.
4. Issue 495: the govern hook passes `git pull --ff-only` (a fast-forward cannot rewrite history) and keeps refusing
   plain `git pull`. The pull's own flags are read anywhere after `pull` (before or after the remote and branch), after
   the git options the hook already skips (`-C`, `-c`, `--git-dir`, `--work-tree`, wrappers). It passes only with
   `--ff-only` present and none of `-r`, `--rebase`, `--rebase=<mode>` or `--no-ff`. A `pull.rebase` setting cannot turn
   an `--ff-only` pull into a rebase (`--ff-only` refuses anything but a fast-forward), so it stays safe. Negative
   controls: plain pull, `-r`, `--rebase=merges`, `--no-ff` and `--ff-only --rebase` stay refused. Agreed.
5. DOC-14 carries both owner messages: the line is the approved wording widened with the delivery clause, "or a
   delivery people receive (for example a scheduled email), with its channel, recipients as a group, what is sent and
   its status" (the owner's own words, relayed by the operation session on 2026-11-10). Its sub-bullets list only what
   the template checks (the optional section, the two tables, the refusals), and one sub-bullet says the live-link and
   promoted-build check runs in the deploying repo's pilot for now, so the requirement never claims a check the template
   doesn't run. No Non-goal or other owner text changes. The requirement and page stamps use the owner's "a" (the
   operation session's brief says to mark it Reviewed with it); the PR body quotes both owner messages and names the
   worker-written sub-bullets, so the owner confirms them at the PR, the only gate. Agreed.
6. `deployments` joins `pageformat.CHECKS` and the template's `format` line; a repo whose `format` line leaves it out
   skips the shape check silently, like any other format check. The section's place in the order is always enforced.
   Agreed.
7. docs.py check runs the page contract through `criteria.contract` (docs.py contract), so one change covers both done
   line 1 paths; toy cases run both `criteria.py`'s contract path and `docs.py check` on a good and a malformed page.
   Agreed.

## Approaches Considered

### Approach A: rules-driven optional section plus a pageformat check (recommended)
Add `deployments_section`, `deployments_columns` and `deployments_access` to the rules block; criteria.py's section
order accepts the optional section after Success metrics; pageformat.py gains a `deployments` check (in `format`, so a
repo can turn it off) that returns DOC-14 refusals. Effort S, risk low. Reuses the Usage pattern and the FORMAT refusal
shape.

### Approach B: allow any extra section after Success metrics
Loosen the contract to accept unknown sections. Effort XS, but it lets drift back in, which the page format exists to
stop. Rejected.

## Recommended Approach

Approach A.
- template.md: rules keys (`deployments_section`, `deployments_page`, `deployments_delivery`, `deployments_access`),
  `deployments` in `format`, the Layout paragraph (optional Deployments after Success metrics; the DOC-4..DOC-9 range
  gains DOC-14, the next free id on the Documentation page) and a Deployments bullet describing both tables and the
  refusals.
- criteria.py: `want` inserts the Deployments section after Success metrics when the page has it (a few lines).
- pageformat.py: `deployments(body)` and the `deployments` check name; criteria calls it with the other format checks.
- Documentation.md: DOC-14 under Functional with the owner's wording, sub-bullets for the checkable behaviours, stamped
  Reviewed through `criteria.py review DOC-14 --user` and the page review, with the owner's words "a".
- govern_hook.py: `pull` blocked unless `--ff-only` is present and no `--rebase`/`--no-ff`.
- Tests: dev/toy/test-deployments.sh (page with and without the section, each malformed form named, the Documentation
  requirement present and Reviewed); regression rows guarding DOC-14 and defect rows for #495 (plain pull still
  blocked, ff-only passes), each seen failing then passing.
