## Problem Statement

The owner approved the Delivery PRD on 2026-11-10. Five requirements are new and not yet built, and six issues
(38, 117, 129, 134, 154, 170) map onto them. The frozen done lines:

1. DEL-6: small goals (up to 3 done lines, one skill) run a condensed plan and review, larger goals run full, the owner
   can override per goal, and every goal still runs its full test lane.
2. DEL-5: the release bump is patch unless the goal says minor or major (issue 170), and a release on a protected main
   goes through a PR instead of a direct push (issue 154).
3. DEL-7: a stopped or crashed goal resumes from its last recorded step, shown by a test that kills a goal mid-step.
4. DEL-8: each goal carries a time and token budget and the board flags a goal over either.
5. DEL-9: goal.py pr and merge.py refuse to push when the private-name scan finds a match.
6. Each of DEL-5..DEL-9 has a regression row seen failing then passing, and the Delivery page Tests table lists them.
7. Issues 38, 117, 129 and 134 are fixed, each with a defect row seen failing then passing.

What is missing today:

- DEL-6 Review depth fits the goal. Today `review_depth` is one repo-wide switch (`full` or `condensed`). A two-line
  fix pays for the same CEO, DX and Eng plan review as a twelve-file feature.
- DEL-5 Release bumps patch by default. `release.auto_need` returns `minor` for any new file or `feat` commit and
  `ask` for a removed file, and `autorelease.need_of` turns `ask` into a silent **major** bump (issue 170: a release PR
  proposed 1.4.0.2 -> 2.0.0.0 for removing two demo tabs). On a protected main, the release push is refused three
  times and nothing is released (issues 134, 154).
- DEL-7 Resumable. A stopped or crashed goal should go on from its last recorded step. The pieces exist (`goal.py
  resume`, `watch.py resume`, the flow record), but nothing stops a revived agent from rerunning a recorded step from
  the start, and no test kills a goal mid-step and resumes it.
- DEL-8 Budgeted. `time_budget_minutes` and `token_budget` are repo settings that health reads after the fact. A goal
  does not carry its own budget, and the live board says nothing while a goal runs over.
- DEL-9 Nothing private ships. The only private-name scan is an untracked pre-commit hook in one checkout. `goal.py
  pr` and `merge.py` push without any scan.
- Issue 38: record the outside-voice (judge) and idea-run results. Step replies carry verdicts from outside voices,
  but the run record and the pull request keep only the STEP line.
- Issue 117: touches can't name GitHub-side surfaces (wiki, milestones, project boards); nothing warns that a repo
  script regenerates what a goal deletes; a worker session can't find its own session id to bind itself.
- Issue 129: the release skill and its references describe a draft release, while `merge.py` (auto_merge on)
  publishes directly; and a wiki publish into a GitHub wiki with no first page fails with no fix named.

## What Makes This Cool

One goal makes the loop cheaper where it should be (small goals stop paying for full reviews), safer where it must be
(no silent major bumps, nothing private pushed), and sturdier (a crash costs one step, not the goal). Every rule is a
deterministic script check with a toy test seen failing first.

## Premises

1. DEL-6 can be met with the existing two values. `full` keeps every goal at full depth (this repo's choice);
   `condensed` now means "by size": a small goal runs condensed, a larger goal must run full. One rule for both: the
   owner's per-goal override (`goal.py set SLUG --depth`, operation-only) beats the setting and the size; nothing a
   worker runs can lower a goal's depth. No setup change is needed. Rollout note: a repo on `condensed` sees its large
   goals held to full; the release note says so. — agreed (recommended)
2. "Small" is decided once at freeze from the frozen goal: at most 3 done lines, no `github:` touch, and at most one
   code area, where an area is a touched path's first two components (`skills/workflow-release`, `src/api`, or a
   top-level file like `calc.py`). Paths under `docs/`, `.loop/`, `dev/toy/`, `test/` and `tests/` are not areas.
   No touches declared counts as large. This works in a repo with no `skills/` tree. — agreed
3. The release bump is decided in one shared place, `release.auto_need`, so both release paths (merge.py's automatic one
   and release.py's cut) follow it: a change of only docs, tests or `.loop` stays `leave` for the cut path (automatic:
   patch), everything else is the goal's own `bump` (minor or major, recorded by `goal.py set SLUG --bump`) or `patch`.
   `ask` is never produced again. `fit.py` only records the bump; `auto_need` decides. The existing `release.bump`
   rule applies: patch moves the last number (1.4.0.2 -> 1.4.0.3), minor the second, major the first. — agreed
4. Resume means: the run record is the truth; `flow.py` refuses to rerun a step the record already holds (no try used,
   `--again` to rerun on purpose), and every resume path names the step to go on from. — agreed
5. The private-name list lives outside the repo, beside the flow file (`~/.workflow-loop/private-names`, one regex per
   line; `LOOP_PRIVATE_NAMES` names another file). With no list the scan says so and passes: there is nothing to match.
   — agreed
6. Second opinion (Phase 3.5): skipped in this unattended run; landscape search skipped (internal tooling, nothing to
   learn from the web). — auto-decided

## Approaches Considered

### Approach A: Minimal — patch each caller

Edit `goal.py`, `flow.py`, `autorelease.py`, `merge.py` and `live_board.py` in place for each rule.
Effort S, risk high: `goal.py` passes 20 KB, the shared monitoring and release files collide with lane-control and
estimate-model, and each rule's logic is spread over callers.

### Approach B: Two new delivery modules, one-line hooks in shared files (recommended)

- `skills/workflow-delivery/scripts/fit.py`: everything decided at freeze and read later — size and depth
  (`size_of`, `depth_for`), the recorded bump, the budget, `goal.py set`, `resume_at`, verdict capture and the pull
  request body.
- `skills/workflow-release/scripts/release_pr.py`: the protected-main release PR (detect, push the branch, open, merge,
  record, tag after it lands); `autorelease.py` calls it on a refused push.
- `skills/workflow-delivery/scripts/private.py`: the private-name scan, used by `goal.py pr` and, by path, by
  `merge.py`/`autorelease.py` (the same sibling-skill path `session_bind.py` already uses).
- `skills/workflow-monitoring/scripts/board_budget.py`: the budget line for the live board.
- Shared files get one call each.
Effort M, risk low. Reuses guards' no-try refusals, role's base-branch config read, the flow record, fakegh.

### Approach C: A setup-level depth model

Add `review_depth: size` and per-goal settings in setup. Cleaner names, but outside touches and changes every repo's
default on the next rollout — an owner decision, not this goal's.

## Recommended Approach

Approach B. Details per done line:

**DEL-6 depth by size (done line 1).** `goal.py new` stores `state["size"] = {"small", "why"}` from `fit.size_of(done
lines, touches)`. The owner overrides with `goal.py set SLUG --depth full|condensed --why TEXT`, operation-only (refuses
`LOOP_ROLE=worker`, like `touches`), stored as `state["depth_override"]` and logged; it binds steps started after it.
`fit.depth_for(setting, state)`:
- an override, if any, wins;
- else setting `full` → full;
- else setting `condensed` → small goal condensed ("small goal: 2 done lines, one area"), larger full.
`role.depth_of(cfg, state)` returns the goal's decided depth when the state has one, else today's rule. `flow.py`'s
depth prompt and `guards.check_record` use it, so a large goal under `condensed` has a condensed review refused, and a
small one is told to run condensed (one spec-review round, a lighter plan review, one review pass). The live board's
depth line and the PR body show the decided depth and why. The qa lane is untouched by depth: a test proves a small
condensed goal still runs the full `land` lane.

**DEL-5 patch default (done line 2).** `release.auto_need` returns `leave` for a change of only docs, tests or `.loop`,
else `(state["bump"] or "patch", reason)`; a removed file or BREAKING commit is named in the reason, never mapped to
major. `goal.py set SLUG --bump minor|major`, operation-only like the rest of `set`, records the goal's own bump:
the operation session runs it right after freezing a goal whose text or queue line says minor or major; otherwise the
goal stays patch. `set` treats an unset `LOOP_ROLE` as the operation (the operation session runs without it, and goal
steps already refuse outside a worker); this is accepted as the same advisory boundary `resume` and `touches` use. `autorelease.need_of` maps `leave` to patch
(unchanged) and loses its `ask` branch.

Protected main (`release_pr.py`): when the release push is refused with a protection message (GH006, GH013,
"protected branch", "through a pull request", "rule violations"), the release commit is pushed to `release/vX` and a
release PR is opened and recorded as `state["release_pr"]`. It is merged with `gh pr merge` directly, never through
`merge.py`, so merging it can't start another release; `merge.py SLUG` already returns `ALREADY released` once the
goal records `release_url`. After it lands, origin/base is fetched, the version file there must read vX (if it doesn't, because
another release landed first or the PR was edited, no release is created: `release_error` under Issues says "the
release PR merged but VERSION on <base> reads <found>, not vX; check it, then run merge.py SLUG", and every rerun
reports the same until it matches), and the GitHub release is created with `--target` set to that base commit's SHA (right for a merge or a squash). Reruns of `merge.py
SLUG` with `release_pr` set: MERGED → tag and release; OPEN → try the merge again, and if it still can't merge (required
checks, required review, or the loop not allowed to merge) record `release_error` under Issues: "release PR <url> needs
the owner to approve and merge it; then run merge.py SLUG"; CLOSED → clear `release_pr` and `release_pushed` and start
the release again. A toy check proves one goal gets exactly one release through the release PR.

**DEL-7 resume (done line 3).** `fit.resume_at(state)` names the first unrecorded flow step (build when the plan is
recorded and the label says build; `pr` when all are recorded). `guards.cmd_resume` and mend's resume prompt say
"Resume at <step>"; `goal.py show` adds `resume_at`. `flow.py SLUG STEP` on a step whose record is done or skipped
refuses with no try (`ALREADY_RECORDED`, exit 2, naming the resume step) unless `--again`. Toy test: freeze, record
idea and plan, start review with a stand-in agent that sleeps, SIGKILL it and its flow, then show that the run record
keeps idea and plan, `flow.py idea` refuses, the crashed review counts one try, and rerunning review completes and the
goal reaches pr. The trace a crash leaves already exists: `flow.py` writes the step's `.job` (pid, start time) before the
agent runs, and a session step's `.asked` marker; the next `flow.py` call finds the dead pid, writes no STEP line, and
`record` counts that as a failed try. `resume_at` is an ordered rule over the record only: the first of idea, plan,
review, qa, ship whose record is not done or skipped; except that when idea and plan are recorded and review is not,
it says "build or review" (build leaves no record; the worker's commits decide). All recorded → `pr`. A started but
unfinished step is therefore the resume step. `--again` reruns a recorded step on purpose: it clears that step's
record and every later step's record (depth and verdicts too), logs what it cleared, uses no try, and any worker may
pass it (it only adds work). It never touches the goal's try counter (`state["tries"]`, one counter for the whole goal,
not per step), so rerunning an earlier step can't reset a later step's used tries; a toy check proves the counter is
unchanged after `--again`. A toy check reruns plan with `--again` after review is recorded and shows review cleared.

**DEL-8 budget (done line 4).** At freeze the goal carries `state["budget"] = {"minutes", "tokens"}` from
`time_budget_minutes`/`token_budget`; `goal.py new` takes no budget flag. `flow.py`'s token stop reads the
goal's budget first. `board_budget.line(run, cfg)` prints `budget: 35m of 120m, 0.4M of 3.0M tokens`, with
`OVER time` / `OVER tokens` when spent; elapsed time runs from the freeze log entry to now (or to the last update for a
finished goal). Spent tokens are the run record's `tokens`, written when each step ends (flow.py from the agent's JSON,
or `goal.py step --tokens`), so the figure moves step by step. The time budget is shown, never stopped; the token budget
keeps its existing stop before a new step. A larger budget is set only with `goal.py set SLUG --budget-minutes N
--budget-tokens N` (operation-only). The live board prints the line under each running and held goal.

**DEL-9 private scan (done line 5).** `private.scan(top, base_ref, texts)` reads the list, then checks the branch name,
changed file names, added diff lines and commit messages from base to HEAD, plus named texts. A hit prints only its
place, never the matched string or pattern: `path:line`, `commit:<short sha>`, `branch`, or `<text name>:<line>`
(`pr-title`, `pr-body`, `release-notes`). What the loop pushes or posts, and how each is covered:
- `goal.py pr`: the branch (name, files, lines, commits), the PR title and body. Refuses before the push
  (`REFUSED (no try used) ... PRIVATE_NAME`, exit 2, nothing pushed).
- `merge.py`: the PR branch against the base again, plus the release notes, before merging; refuses with nothing
  merged.
- `autorelease`/`release_pr`: the release commit (VERSION, CHANGELOG lines: commit subjects and verify steps, already
  in the branch scan) and the release notes; the `release/vX` branch name is fixed text.
- The wiki publish copies `docs/wiki` from origin/base: pages this goal changes are in its diff; the rest landed
  through earlier scanned goals.
- The loop posts no PR or issue comments.
With no list file the scan passes but says so where it's seen: the PR body gets "Private-name scan: no list at
~/.workflow-loop/private-names, nothing was checked", and the goal's log and report carry the same line. `merge.py`
and `autorelease` load `private.py` from the sibling delivery skill; if it is missing they refuse (fail closed), since
the loop can't run goals without delivery anyway.

**Issue 38 (done line 7).** `goal.py record` keeps each `VERDICT: <who>: <verdict>` line of a reply under
`state["verdicts"][step]`, and the flow prompt asks for them. The PR body's Result lists each step with its depth,
tokens and verdicts, so the idea run's result and every outside voice are on record.

**Issue 117 (done line 7).** Touches accept `github:<surface>` entries (wiki, milestones, projects, releases, labels,
issues), validated by `guards.check_path` and listed in the PR body. At `pr`, for each file the goal deletes, tracked
scripts and `.github/workflows` that name its path print `WARN: <script> names <path>, which this goal deletes; it may
write it back`, also listed in the PR body. `sessions.py bind SLUG self` binds the calling session from
`CLAUDE_CODE_HOST_SESSION_ID` (refusing with the fix when it's unset). Verified in this very worker session: the
variable is set by the desktop app to `local_e529…`, the same id the app's own session lookup returns and the id this
goal was bound with.

**Issue 129 (done line 7).** The release skill, its references and delivery's commands.md say plainly: with auto_merge on,
`merge.py` publishes the release (no draft); a repo without auto_merge cuts a draft with `release.py`. A wiki publish
whose clone fails because the GitHub wiki has no first page names the fix: create the first page in the repo's Wiki tab,
then run merge.py again.

**Rows (done line 6 and 7).** One requirement row per DEL-5..9 and one defect row per issue 38, 117, 129, 134, 154 and
170 (linked `#N`; 154 and 170 also covered by the DEL-5 row), each seen failing on the old code first (`regression.py red`), all in one toy test `dev/toy/test-delivery-prd.sh`
whose PASS lines the rows grep. The Delivery page's Tests table is re-rendered from the rows.

**Remedy**
