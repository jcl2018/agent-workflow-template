## Problem Statement

PR 177 built the scheduled regression and health workflows and the digest comment on the pinned `Automation digest`
issue. The owner approved a new Automation PRD on 2026-11-10 that goes further:

- AUT-2 and AUT-3: every defect issue and every health finding sits on the milestone of the feature it is about. Today
  regression issues get no milestone, and health files everything on Backlog.
- AUT-4: one email per round to the owner, with the same text as the digest comment, grouped by feature. Today the
  digest is a comment only, relying on GitHub's own notification mail, and its issue lists are flat.
- AUT-6: the address and the mail key live only in GitHub secrets.
- AUT-7: the run summary shows each round's duration and Actions minutes, and flags a round over 45 minutes.

## Constraints

- Script size: `automation.py` is 16,070 bytes against the 20 KB limit, and `regression.py` 20,246, so new logic goes
  in new scripts. The regression workflow is self-contained (it carries `tests.py` inline), written by `actions.py`.
- The scheduled workflows never push, merge or release (non-goal kept from PR 177).
- Sender: the owner approved Cloudflare Email Service for the template. Another of the owner's projects sends through a Gmail
  app password, so the sender is pluggable: Cloudflare by default, SMTP as the other choice.
- Never write the owner's address anywhere: not in the repo, a log, an issue, the digest comment or a test fixture.
- lane-control is editing `regression.yml` and the health rules in parallel: merge main before the pull request.
- Touches: `skills/workflow-health`, `skills/workflow-regression`, `skills/workflow-setup`, `.github`,
  `.loop/config.json`, `.loop/regression.tsv`, `dev/toy`, `docs/wiki/Automation.md`, and `.loop/docs.tsv` (added by
  the operation session on 2026-11-10). This goal adds `mail.py` and `rounds.py` to the Automation row itself, so they
  never map to the Health page.

## Premises

1. **A round is regression then health, and the digest closes it** (kept from PR 177): health runs 30 minutes after
   regression, and the email goes out from the health workflow right after the digest comment.
2. **The email is the posted comment.** The mail step reads the digest comment for this run back from the issue and
   sends that text. It accepts only a comment whose author is `github-actions[bot]` (the job token's identity) and
   whose last line is the marker with `run=R` for this run; with several, the newest. A look-alike comment from anyone
   else is ignored, so a third party can't put text in the owner's mail. It reads only the newest page of comments
   (the issue comments API, `per_page=30`, last page), so a long history costs nothing. So the email and the comment
   can't differ, and a rerun that already posted the comment can still send a mail that failed.
3. **The mail step is its own workflow step**, the only one that holds the mail secrets. The digest step never sees
   them, and the mail step prints only the secret names, never their values.
4. **"Sends nothing twice" is state on the digest issue**: the body marker gains `mailed=R`. The mail step skips when
   `mailed` equals this run, and writes `mailed=R` only after the provider accepts the message. (If that state write
   fails after a send, it says `MAIL: sent, but couldn't save mailed=R; a rerun will send again`.)
5. **One meaning of feature: a `.loop/docs.tsv` page other than Home** (milestone.py's `features()`), Backlog as the
   fallback, and no milestone is ever created outside that set.
   - A defect's feature is the wiki page `tests.py` names for its row, only when that page is such a feature. `Other`,
     `Home` and any page not in docs.tsv go to Backlog.
   - A health finding's feature is the docs.tsv page whose path is the longest prefix of the finding's subject (a file
     path), or the page whose name the subject is (case-insensitive). Anything else goes to Backlog.
   - A feature milestone that exists but is closed is used as it is (an issue may sit on a closed milestone); it is
     never reopened or recreated.
6. **The automation places an issue once and then leaves it to the owner.** It sets the milestone when it opens an
   issue, and moves an open issue only while that issue has no milestone or sits on Backlog. An issue the owner moved
   to another milestone stays there, so `milestone.py move` and the issue body's advice keep working.
7. **AUT-2's schedule is already met** (`17 */4 * * *` and `push: tags: v*`); this goal adds regression rows that
   prove it, not new triggers.
8. **A round's cost is the time its jobs ran, not the wall clock.** The idle half hour between regression and health
   costs nothing, and the owner's limit is a cost limit.
   - The round's regression run: the newest regression run created before this health run was created, whatever its
     trigger (a tag or a by-hand run is a round too). None: `regression: no run found`, and the round is health only.
   - Round duration = the regression run's job time (each job's `completedAt - startedAt`) + this health run's job time
     so far (its job's `startedAt` to the moment the digest is written). The health part is labelled "so far"; the mail
     and summary steps after it add seconds, never minutes.
   - A regression run still in progress counts its elapsed job time and is labelled `regression still running, partial`.
   - Actions minutes are counted the way GitHub bills them: each job's minutes rounded up, summed over both runs. A
     public repo isn't billed, so it's shown as "Actions minutes", not money.
   - The flag: round duration over `round_budget_minutes` (45) says `OVER 45 min`. A partial round is flagged only
     when its partial time already passes the budget.

## Approaches Considered

### Approach A: two small new scripts beside automation.py (recommended)
- `skills/workflow-health/scripts/mail.py`: `mail.py send` finds the digest issue and this run's comment, turns it into
  a plain-text and a simple HTML body, and sends it through the configured sender; `mail.py check` says which secrets
  are missing. Senders: `cloudflare` (REST `POST /accounts/{account_id}/email/sending/send`, Bearer token, through
  urllib) and `smtp` (smtplib, SSL on 465 or STARTTLS on 587). Standard library only.
- `skills/workflow-health/scripts/rounds.py`: reads the round's runs and jobs with gh, returns duration, Actions minutes
  and the over-budget flag for the digest and the run summary.
- `automation.py digest`: groups the new, still-open and fixed issues by milestone, adds a "round cost" row, writes the
  cost lines to the run summary, and reads and writes the marker by the grammar below.
- `file.py`: plans each finding's milestone, opens on it, and moves an open issue only while it has no milestone or
  sits on Backlog (premise 6).
- `actions.py`: the regression workflow reads `.loop/docs.tsv` itself (it stays self-contained), creates a missing
  feature or Backlog milestone, files the defect issue on it, and moves an unplaced open one (premise 6).
- Effort M-L, risk medium. Reuses `milestone.py`'s feature table, the digest marker, `tests.py`'s feature map.

### Approach B: mail from inside automation.py digest
One step, fewer files. Ruled out: the digest step would hold the mail key and the address (AUT-6 wants the fewest
places), and automation.py would pass 20 KB.

### Approach C: a Cloudflare Worker that receives a webhook and mails
The binding needs no API token in GitHub. Ruled out: it adds a deployed service and a webhook, which the PRD's
non-goals exclude ("no chat or webhook notifications"), and the template would need a Cloudflare deploy to work.

## Recommended Approach

Approach A.

### Settings (in `.loop/config.json`, written by setup)
- `digest_mail`: `cloudflare` (default), `smtp`, or `off`. Off sends nothing and says so.
- `round_budget_minutes`: 45 by default; a round over it is flagged in the digest and the summary, with a warning.
- `smtp_host`, `smtp_port`: for `smtp` only (default `smtp.gmail.com`, 465). A host isn't a secret.

### Secrets (names only; values live only in GitHub secrets)
- Always: `DIGEST_TO` (the owner's address), `DIGEST_FROM` (the sender address).
- Cloudflare: `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_EMAIL_TOKEN`.
- SMTP: `SMTP_USER`, `SMTP_PASSWORD` (a Gmail app password, for example).
- Missing any the chosen sender needs: `MAIL: skipped, missing secrets: <names>`, exit 0, nothing written.

### The mail step
- `Email the digest`, right after `Post the digest`, `if: always() && steps.routine.outputs.on == 'true'`.
- Env: `GH_TOKEN` (the job token: the health job's `issues: write` covers reading comments and editing the body,
  `actions: read` covers rounds.py), `DIGEST_RUN`, and the mail secrets. It writes one line to the run summary.
- Outcomes, each one line on the log and the summary:
  - `MAIL: off (digest_mail)`, exit 0; `MAIL: skipped, missing secrets: ...`, exit 0; both write nothing.
  - `MAIL: already sent for run R`, exit 0.
  - `MAIL: no digest comment for run R, so nothing was sent` (no digest issue, no bot comment for R), exit 1: the
    digest step failed, and the run should show it.
  - `MAIL: gh couldn't read the digest issue, so nothing was sent`, exit 1.
  - `MAIL: <provider> refused it: <code> <message>`, exit 1, with every secret value replaced by `***`.
  - `MAIL: sent for run R` (no address), exit 0; or the state-write warning of premise 4.

### The digest, grouped by feature
```text
@owner Automation round, 2026-11-10 12:47 UTC
| Routine | Result |
| regression | failure, 2026-11-10 12:17 ([run](...)) |
| health | HEALTH: green (...) |
| round cost | 31 min, 33 Actions minutes (regression 24 min, health 7 min) |

### Automation
**New** (1): [#12](...)
**Still open** (0): none
**Fixed** (1): #5
### Backlog
...
### Ask the agent
- [#12](...): `/workflow-delivery go "Fix #12"`
```
A round over the budget says `OVER 45 min: slow a routine down or turn it off` in the cost row. The feature of an open
issue is its milestone; a fixed issue is shown under the milestone it had in the previous state.

### The state marker
- Grammar: `<!-- automation-digest run=R open=N:M,N:M mailed=R -->`, space-separated `key=value` tokens read in any
  order. `R` is a run id (`[0-9]+`, or `none`/`local`); `N` an issue number; `M` the issue's milestone **number**
  (0 for none), never its title, so no title can break the comment. Titles are looked up when the digest is written,
  from the repo's milestones (all states).
- The old form `open=12,9 run=R` still reads: each issue with milestone 0. A fixed issue whose previous milestone is 0
  or no longer exists is listed under `No milestone`.
- The digest writes `run=R open=...` and no `mailed` (a new round has mailed nothing). The mail step re-reads the body,
  and adds `mailed=R` only while the body's `run` is still R, keeping `run` and `open` as they are; any other body text
  is kept.
- Round-trip tests: the old form, the new form, keys in another order, and a milestone titled with a space and a comma.

### Mail
- Subject: `Automation digest: N new, M open, K fixed (<owner/repo>)`.
- Text: the comment with the mention and the marker removed. HTML: the same lines, escaped, links kept as anchors.
- Errors: the provider's code and message, with every secret value replaced by `***`; never the response body whole.
- Never prints the address. GitHub also masks secret values in logs.

### Filing on milestones
- Regression: on create, the issue goes on its feature's milestone, or Backlog (premise 5). An open issue is moved only
  while it has no milestone or sits on Backlog; one the owner placed on another milestone is left where it is
  (premise 6).
- Health: the workflow runs `milestone.py new --all --live` (idempotent) instead of Backlog only; `file.py` opens on
  the finding's milestone and adds a `move` action only for an open issue with no milestone or on Backlog, never for
  one the owner placed elsewhere (premise 6). Marker keys stay, so nothing is duplicated.
- Milestones are read with `state=all` (as milestone.py's LIST does), a milestone that exists in any state is never
  created again, and the milestone is set by **number** through the REST API (`gh api -X PATCH
  repos/{owner}/{repo}/issues/N -F milestone=<number>`, and `-F milestone=<number>` on `POST .../issues` for a new one),
  so a closed feature milestone works where `gh issue create --milestone <title>` would not find it.
- Rows: an owner-placed issue on a non-Backlog milestone stays there (under AUT-2 and AUT-3); a closed feature
  milestone is used, not recreated.

### Run summary
Both workflows' summaries keep their own run time; the health summary adds `## Round` with the round's duration,
Actions minutes and the flag, written by `automation.py digest` (it already reads the regression run).

### R2-1 — consistency (blocking)

**Problem**

> Premise 6 and Approach A now say an open issue is moved only while it has no milestone or sits on Backlog. The unchanged 'Filing on milestones' section still says the opposite: for regression, 'an open issue on another milestone is moved', and for health, file.py 'adds a `move` action when an issue's milestone differs'. An implementer following that section would undo the owner's manual `milestone.py move` every round, which is the conflict R1-7 raised. The done-line map also has no regression row for the chosen behavior (an owner-moved issue stays put).

**Remedy**

> Rewrite both 'Filing on milestones' bullets to match premise 6: move only an open issue with no milestone or on Backlog, and never one the owner placed elsewhere. Add a regression row, under AUT-2/AUT-3, showing an issue on a non-Backlog milestone is left where it is.

### R2-2 — feasibility (blocking)

**Problem**

> Filing on a closed milestone 'as it is' isn't supported by the filing mechanism the design names. Today file.py files with `gh issue create --milestone <title>`, and the regression filing says 'on create `--milestone <feature or Backlog>`'. gh resolves `--milestone` by title among open milestones, so a closed feature milestone is likely reported as not found and the create fails. The step that ensures a milestone exists ('ensured first with `gh api .../milestones`') would also try to create a milestone that already exists (closed), and get 422 already_exists, unless the lookup uses state=all. So the newly committed closed-milestone behavior can fail the filing step.

**Remedy**

> Look up milestones with state=all, as milestone.py's LIST already does, and never create a milestone that exists in any state. Set the milestone by number through the REST API (`gh api repos/{o}/{r}/issues -f milestone=<number>` on create, PATCH on move) rather than gh's `--milestone <title>`. Alternatively, verify that gh accepts a closed milestone's title and cite the evidence. Add a toy row that files on a closed feature milestone.

### R2-3 — feasibility (minor)

**Problem**

> Reading only the last page of 30 can miss this run's comment. The last page can hold as few as one comment, so any comment posted after the digest (a human reply, or a newer round's digest before a rerun of the mail step) can push run R's comment onto the previous page. The step would then fail with 'no digest comment for run R', which undercuts the promise that a rerun can still send a mail that failed.

**Remedy**

> Read comments with `since=` the health run's creation time, or read the last two pages, so run R's comment is always in range.

### R2-4 — feasibility (minor)

**Problem**

> Persisting R1-10: `DIGEST_MAIL_URL` still overrides the Cloudflare API base in production code, described only as 'for tests only'. If it is set in a runner environment, the bearer token and the owner's address go to an arbitrary host.

**Remedy**

> State that the generated workflow never sets it, and limit it to localhost/127.0.0.1 or require an explicit test flag. Add a check that the workflow text doesn't contain it.

### R2-5 — clarity (minor)

**Problem**

> Persisting R1-11: in the mail subject `N new, M open, K fixed`, it is still unclear whether M counts the 'Still open' issues or all open issues (new plus still open).

**Remedy**

> Name the count explicitly ('M still open') or define M as total open.

**Remedy**
