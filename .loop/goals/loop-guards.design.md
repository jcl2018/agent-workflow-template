## Problem Statement

Goals that run in worker sessions stop or stall for reasons that aren't failures of the work. These were seen on real
goals on 2026-11-09 and 2026-11-10, filed as issues 147, 148, 149, 157, 121 and 160:

- **147.** A reply-format rule added mid-goal (the DEPTH line, v0.12.1) failed goals whose steps were already under
  way. yc-ready was stopped.
- **148.** A refused record that changes nothing (a missing DEPTH line, the qa lane not run on this HEAD) counts as a
  failed try against the goal's shared budget (max_tries, 3). Two format slips stopped yc-ready with green work.
- **149.** A goal that stopped can only be resumed headless (`watch.py resume`, which runs `mend.py --resume`).
  Session repos edit the run JSON by hand.
- **157.** Widening a goal's touches meant editing JSON by hand. `goal.py finding` always calls `fail_stop`, which marks
  even a finished goal stopped. This worker hit it too: narrow-rows nearly stopped itself after its merge.
- **121.** `goal.py record --in-session` refuses without `LOOP_ROLE=worker`, and the refusal points at
  `batch.py start` (the operation session's command), not at the variable.
- **160.** A goal's worktree edits are refused by the worktree-isolation edit hook when the worker session started in
  another worktree. That hook is not in this repo. It is the desktop app's guard for sessions started in
  `.claude/worktrees`. The owner chose option (a) on 2026-11-10, relayed by the operation session ("a"): line 6 is
  read as "sessions.py bind/assign prints the goal worktree to work in, refuses with a clear hint when the session's
  folder is elsewhere, and a toy test checks it". The app's own guard is out of the template's reach, and #160 stays
  open for the app-side part.

## What Makes This Cool

Every stop becomes a real signal. When the board says a goal stopped, the work failed. A format slip, a rule that
changed under the goal, a finding after merge, or a restart can no longer end a goal. Fixing a slip costs one rerun of
`record`, not a third of the goal's budget.

## Constraints

- Scripts stay under 20 KB. goal.py is 18,955 bytes and role.py 17,711, so new code goes in a new module.
- Done lines are frozen. Line 6 depends on a hook this repo doesn't own.
- The worker guard must keep stopping the operation session from running goal steps. A refusal can say how; the guard
  must not get weaker.
- No private names or paths in committed files. A toy test for each guard is seen failing on the old code.

## Premises

Each "Agreed" below is the worker's own call, using the recommended answer in an unattended step. The owner approves
them at the plan's final gate.

1. A refusal that changes no goal state is not a try. Only work that ran and failed (STEP: failed, a failed lane, a
   reply with no STEP line from a headless run) uses the budget. Agreed (recommended).
2. A format rule has an id and the release that added it. It binds a step only if the rule was already known when
   that step started. When a step starts, the ids of the rules known then are recorded with it. That happens in
   flow.py's `begin`, and for in-session steps when the previous step was recorded (at `new` for the first step).
   Comparing rule ids avoids comparing version strings, and avoids choosing which VERSION file to read. Agreed.
3. Resume in a session never launches a process. It resets the run record for the bound session and logs who and why.
   Agreed.
4. A finding on a finished goal (status done or merged) is a note, not a stop. Agreed.
5. Binding cannot set an environment variable inside another process. "Sets LOOP_ROLE=worker for it" is met by bind
   handing the session the exact command form (printed, and sent through the session tool when one is configured).
   The refusal names that form. Agreed.

## Approaches Considered

### Approach A: patch in place
Edit goal.py, role.py and sessions.py directly. Effort S, risk medium. It is the smallest diff, but goal.py would pass
20 KB, so it fails the size rule.

### Approach B: a guards module (recommended)
A new `skills/workflow-delivery/scripts/guards.py` holds:
- the versioned rule registry and the record checks moved out of role.py (DEPTH, full markers);
- a `refuse_no_try()` helper that prints `REFUSED (no try used): <rule> ... Fix: ...` and leaves status, step, tries and
  the ran marker untouched;
- the bodies of `resume`, `touches` and `finding`.

goal.py only wires the commands. sessions.py bind prints and sends the worker command form and the goal worktree path.
Effort M, risk low. It reuses `role.report`, `save`, `write_finding`, the session tool's `send`, and the toy harness in
dev/toy (`make.sh`, fakegh).

### Approach C: format-free records (rejected)
Never refuse on format; infer a missing DEPTH line as full. Rejected: it removes review_depth's guarantee (a condensed
review could pass as full).

## Recommended Approach

B. Each guard:
- **147.** `RULES = {"depth-line": "0.12.1", "depth-condensed": "0.12.1", "full-markers": "0.12.1"}`, mapping each
  rule id to the release that added it. That release is only text for messages and is never compared. The ids are
  stored as `state["rules_at"][step]` (sorted): by `new` for the idea step, by flow.py's `begin` for the step it starts,
  and by each successful record for the next step; `begin` overwrites an earlier entry, because the step really starts
  then. A check runs only when its id is in `rules_at[step]`. A run record or
  step with no `rules_at` gets every rule known today (status quo for goals already running). A refusal names the rule
  and its release: `no DEPTH line (rule depth-line, added in v0.12.1). Fix: ...`. A skipped rule logs `rule <id>
  (v<release>) not applied: <step> started before it`. The toy test removes `depth-line` from a step's `rules_at`,
  which stands in for a rule added after the step started.
- **148.** DEPTH and marker slips, and a missing STEP line in an in-session reply, return through `refuse_no_try()`:
  exit 2, ran marker kept, tries unchanged. need_lane already exits without a try, and its message keeps that. A
  headless reply with no STEP line stays a try (the run may have crashed). record's other refusal, "<step> wasn't run
  by flow.py" (the reply isn't at the run's reply path, or the step's `.ran` marker is missing), already exits through
  `no()` before touching state, so it is not a try today and stays that way; its message gains "(no try used)". There
  is still a limit:
  `state["refusals"]` counts no-try refusals in a row and resets on a successful record. At 5, the goal stays running,
  but `state["note"]` says "<step>: 5 refused records in a row: <last reason>", so the operation's board shows it and
  the operation decides. A worker that keeps slipping is seen, not silently looping or stopped. The counter and note
  are the only state a refusal writes. The note updates on each refusal from the 5th on, and a successful record clears
  both. The flow.py-marker refusal counts too: it increments the counter before exiting.
- **149.** `goal.py resume SLUG --why TEXT [--by WHO]` is the operation session's command. Under LOOP_ROLE=worker it
  refuses ("a worker can't resume its own goal: ask the operation session"), so a worker can't reset its own budget.
  It refuses unless status is failed or stopped and the run record names a bound session. Otherwise it points at
  `sessions.py bind` or `watch.py resume`. If the done lines changed since the freeze, it refuses with exit 1: "the
  done lines changed after they were frozen; a wrong done line needs a new goal". The goal is already stopped, so that
  path writes nothing. Otherwise it sets status running, tries 0, refusals 0, finding "" and waiting None. It logs
  `resumed by WHO: WHY` (WHO defaults to "operation session"), reports it, and when a session tool is set, sends the
  bound session "resumed: continue at <step>". It never starts a process.
- **157.** `goal.py touches SLUG --add PATH --why TEXT` is the operation session's command too: it refuses under
  LOOP_ROLE=worker, so a worker can't widen its own limits. It adds to state touches and the goal file's Touches line,
  then commits only that file with `git -C <state worktree> commit -m ... -- .loop/goals/<slug>.md` on the goal's own
  branch. A path-limited commit leaves the worker's other staged changes out. It refuses with exit 1, changing nothing,
  when the worktree's index lock exists, located with `git -C <worktree> rev-parse --git-path index.lock` (in a
  linked worktree it lives under the common git dir) ("the worker is committing; try again") or the goal file has uncommitted edits ("commit
  or drop the goal file's edits first"). If the commit itself fails (a lock race, a hook, a git error), the goal file
  is restored with `git -C <worktree> checkout -- .loop/goals/<slug>.md` and it refuses, so no uncommitted edit is left
  behind. State touches are written only after the commit succeeds. The Touches line is not part of the
  done-line hash (only the numbered done lines are), so the freeze check still passes. It logs `touches +PATH: WHY`.
  `goal.py finding` on a goal whose run status is `done` or `merged` appends to `state["findings"]` with a log line and
  prints `FINDING recorded (goal stays <status>)`. Every other status (running, waiting, failed, stopped, queued)
  keeps today's fail_stop.
- **121.** LOOP_ROLE is a role convention against running a step in the wrong session by accident. It was never a
  security boundary, since any process can set it. The guard keeps refusing every caller without it. Its refusal
  depends on the goal:
  - When the goal's run record names a bound worker session, it says `REFUSED: <cmd> is worker work and LOOP_ROLE is
    not worker here. Fix: run it in <session name> as LOOP_ROLE=worker <the exact command>; the operation session
    doesn't run goal steps.`
  - Otherwise it says how to start a worker: `batch.py start NAME`, or `sessions.py bind SLUG ID`.

  bind prints `WORKER <slug>: run goal steps as LOOP_ROLE=worker python3 <path>/goal.py ...`, and sends that line to the
  session when a session tool is set. That is how binding "sets" the role, since no process can set another process's
  environment. The operation session's own instructions already forbid it from running goal steps, so naming the form
  in the bound-session case gives it nothing new.
- **160.** The owner chose (a). bind and assign print `WORKTREE <path>` (the goal worktree to work in) and include it
  in the message sent to the session. bind takes `--cwd DIR` (the session's folder, given by whoever binds) and refuses
  when DIR is not inside the goal worktree: `REFUSED: session folder DIR is outside the goal worktree PATH. Fix: start
  or move the session in PATH, then bind again`. With no `--cwd`, it uses the binding process's own folder when that
  process runs as the worker (LOOP_ROLE=worker). The operation binding from the main checkout prints only the hint.
  assign starts the session through the session tool, and the session's first message names the worktree. The tool
  reports no folder, so assign can't check one. The folder check fires only when the folder is known: bind with
  `--cwd`, or a worker binding itself. Otherwise bind and assign print the WORKTREE hint and nothing is refused. The
  toy test checks both: the refusal with a known outside folder, and the hint without one.
  This hands over the path and catches a wrong folder at bind time when the folder is known. The limit, that the
  refusal fires only when the folder is known and assign only prints the hint, goes to the plan's final gate as a
  decision for the owner on how their choice (a) is met. It does not stop the app's own guard, which keys
  on the folder the session started in. The PR says so, and #160 stays open.

### R3-2 — feasibility (blocking)

**Problem**

> The goal's state worktree is a linked git worktree. In a linked worktree `.git` is a file, and the index lock lives at `<common git dir>/worktrees/<name>/index.lock`, not at `<worktree>/.git/index.lock`. As written, the check never finds the lock, so the promised 'try again' refusal never fires and the commit fails some other way.

**Remedy**

> Find the lock path with `git -C <state worktree> rev-parse --git-path index.lock`. Also treat a commit failure caused by the lock as the same 'try again' refusal, since the lock can appear between the check and the commit.

### R3-3 — completeness (blocking)

**Problem**

> touches edits the goal file's Touches line and then commits it. Only state touches is held back until the commit succeeds. If the commit fails (lock race, hook, or git error), the goal file keeps an uncommitted Touches edit. The next touches then refuses ('commit or drop the goal file's edits first'), and the worker's next commit could sweep that edit in. So the promise 'refuses with exit 1, changing nothing' does not hold on the failure path.

**Remedy**

> Say that a failed commit restores the goal file (for example `git checkout -- .loop/goals/<slug>.md`, or write it only on success through a temp file), exits 1 with the git error, and leaves both the file and state unchanged.

### R3-4 — consistency (minor)

**Problem**

> The flow.py-marker refusal exits before touching state, so it apparently doesn't add to state["refusals"]. The limit is described as counting 'no-try refusals in a row' so that a worker that keeps slipping 'is seen, not silently looping'. A worker that repeats this refusal would loop without the 5-in-a-row note.

**Remedy**

> Say whether this refusal adds to state["refusals"]. If it doesn't, say why the note isn't needed for it.
