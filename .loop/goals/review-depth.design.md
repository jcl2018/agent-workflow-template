# Design: review-depth

Generated by the idea step on 2026-11-08
Branch: loop/review-depth
Repo: jcl2018/agent-workflow-template
Status: DRAFT
Mode: Builder

## Problem Statement

Workers have run the plan and review steps in a condensed form without saying so, and the owner found out only by
reading transcripts. The owner wants depth to be a repo setting, `review_depth` (`full` or `condensed`, default
`full`). With `full`, a worker never condenses on its own. Every recorded step result names the depth that ran, and the
live board and the pull request body show it. Setup writes the setting with its default and a one-line explanation,
and the settings reference lists it.

## What Makes This Cool

The worker's quality call becomes the owner's, and it is visible. A goal's pull request body reads
`review: done (depth full)`, and the board shows each running goal's depth next to its worker. A condensed review under
`full` does not slip through. It costs the goal a try, using the retry the flow already has.

## Constraints

- Every script stays under 20 KB. `goal.py` has about 1.5 KB left, so new parsing goes into `role.py`, which goal.py
  already imports.
- The repo never names a skill suite. Anything skill-specific lives in the private flow file
  (`~/.workflow-loop/flow.json`).
- Done lines are frozen (see `review-depth.md`).

## Premises

1. The setting lives in `.loop/config.json` as `review_depth` and is read fresh on each run, like every other repo
   setting. An unknown value reads as `full`.
2. A step's reply states its depth on a `DEPTH: full|condensed` line before the `STEP:` line, and record checks it.
   Revised after the second opinion: the line is only a claim. For plan and review under `full`, the private flow file
   may list `full_markers` per step, and record also requires each marker to appear in the reply.
3. Reuse what exists:
   - the step prompt in `flow.py`, which both the headless and the IN SESSION paths print;
   - the record parser;
   - the pull request body, which lists `state["flow"]`;
   - the live board's worker line;
   - the settings `TABLE`.

## Cross-Model Perspective

The Codex outside voice was unavailable: the configured model is not supported for the account (model_not_found), so
no outside review ran. A Claude subagent cold read ran instead. Its points:

- **Coolest version:** depth receipts rather than labels. Record counts the sections a full run must produce, so the
  board shows `review: full 5/5`.
- **Challenged premise 2 (High):** a worker that condenses silently will also write `DEPTH: full`, so checking the
  line proves only that the line is there.
- **Build first:** the record-time gate in `role.py`, with a toy test, before the board and settings work.

Synthesis: agreed. The gate goes in `role.py` and the test comes first. A fixed section list can't live in the repo,
because it would name skill output. So the evidence list is an optional per-step setting in the private flow file.
With no list, the `DEPTH:` line alone is checked.

## Approaches Considered

### Approach A: setting plus a DEPTH line
The setting, the `DEPTH:` line in the prompt and the reply, a check at record time, and display on the board and in the
PR body. Effort S, risk low. It can't catch a false `full` claim.

### Approach B: A plus private evidence markers (chosen)
A, plus `full_markers` per step in the private flow file. Record fails a `full` plan or review reply that lacks a
marker. Effort S–M, risk low.

### Approach C: mandatory structural receipts
A fixed section schema per step, kept in the repo. Rejected: it names skill output in the repo and is brittle across
skill suites.

## Recommended Approach

Approach B. It catches a false `full` claim only where the owner configures `full_markers`, and only as far as those
markers are hard to fake. With no markers it is Approach A: the `DEPTH:` line is checked, and that remains a known risk.
The step prompt never shows the markers, but a worker that reads the private flow file could find them. That is noted as
a limit.

The rules, in one place:

1. **Setting.** `review_depth` in `.loop/config.json` is `full` or `condensed`, and `full` when absent. `settings.py
   fill-repo` refuses an unknown value with one line and the fix, like `criteria_max`. Scripts that only read it treat
   an unknown value as `full`.
2. **Prompt (`flow.py`).** The prompt gains the depth rule, and both the headless path and the IN SESSION path print it:
   - Plan and review under `full`: "run the skill's full pipeline, every phase and pass it has; never condense it".
     Under `condensed`: "a condensed run is allowed; say so".
   - Every step's reply ends with `DEPTH: full` or `DEPTH: condensed` on the line before the `STEP:` line.
3. **Check at record (`role.check_depth`).** `goal.py record` (headless and `--in-session` alike) makes one call:
   `role.check_depth(text, step, setting, markers)`, which returns `(depth, error)`.
   - **No valid line:** a missing or malformed `DEPTH:` line in any step is an error: "give a DEPTH: full or DEPTH:
     condensed line before STEP:".
   - **Condensed under full:** plan or review claiming `condensed` while the setting is `full` is an error.
   - **Missing marker:** plan or review claiming `full`, under either setting, with a configured marker absent from the
     reply text before the `STEP:` line, is an error that names the marker. The match is a case-insensitive substring.

   An error is a failed try with that reason. It counts against `max_tries`, and on the last try the goal stops with a
   finding, as today. The reason shows in the goal's log and in its finding on the board's Issues.
4. **Stamp.** On success the flow entry gets `(depth full)` or `(depth condensed)`, and `state["depth"][step]` is
   saved. The pull request body lists the flow entries, so it shows every step's depth.
5. **Markers (private).** `full_markers` in `~/.workflow-loop/flow.json` is a map from step to a list of strings, for
   example `{"review": ["security", "tests"]}`. A value that is not a list of strings counts as none for that step, and
   record prints `NOTE: full_markers for review is not a list of strings; ignored`. The repo never holds the strings.
6. **Board (`live_board.py`).** The running goal's worker line adds every recorded step's depth and the current
   setting, labeled: `depth: idea full, plan full, review full (setting full)`.
7. **Setup (`settings.py`, `setup.py`).** The `TABLE` gains a `review_depth` row (default `full`, one line of
   explanation) and a private `full_markers` row (default `{}`), and the reference is regenerated. Setup and `fill-repo`
   write `review_depth` with its default, plus one explanation, in a single map: `"_help": {"review_depth":
   "<line>"}`. No other key gets one. Repo config readers use `.get` on named keys, and none checks for unknown keys,
   so `_help` is ignored. The toy test checks that.
8. **Goals in flight.** Goals whose step prompt came before this change reply without a `DEPTH:` line. Their next
   record fails once with the reason in rule 3. The re-run prints the new prompt, so the second try passes. The PR says
   in-flight goals may lose one try.
9. **Size.** goal.py gets only the call and the stamp. The logic goes in `role.py`, and the 20 KB check runs. If
   goal.py would pass the limit, the stamping moves into `role.py` too.
10. **Toy test** `dev/toy/test-review-depth.sh` checks:
    - full is the default;
    - a reply with no `DEPTH:` line fails;
    - a condensed review under full fails;
    - condensed is recorded when it is set;
    - a claimed full missing a marker fails, under either setting;
    - the recorded entry, the PR body text and the board's worker line name the depth;
    - setup and `fill-repo` write `review_depth: full` and its `_help` line;
    - fill-repo refuses an unknown value;
    - the settings reference lists `review_depth`.

## Open Questions

- Should idea, qa and ship be held to the setting? No for now: the setting governs plan and review only. Every step
  must still state its depth, which is recorded and shown.

## Success Criteria

The four done lines in `review-depth.md`, each proven by a row in `.loop/regression.tsv` that runs the toy test.

## Distribution Plan

Ships with the template's normal release: `merge.py` bumps the version and publishes the GitHub release.

## Dependencies

session-workers (merged in v0.10.0): `goal.py record --in-session` and the IN SESSION prompt.

## The Assignment

Turn on `full_markers` for the review step in the private flow file. Then watch one goal fail a condensed review on
the board, before you trust the setting.

## What I noticed about how you think

- "By default, it should not use condensed." You care less about speed than about the worker never making that call
  for you.
- You asked for the depth on the board and in the pull request body, not in a log. You want to see the decision without
  going looking for it.

## Reviewer Concerns

Disposition: COMPLETED

No blocking findings remain. The 5 open minor finding(s) below are recorded for the user, not fixed.

### R2-1 — consistency (minor)

**Problem**

> Premise 2 (unchanged) still says markers apply 'For plan and review under `full`'. Rule 3 now checks them for a claimed full 'under either setting'. The premise contradicts the committed rule.

**Remedy**

> Reword Premise 2 so markers are checked whenever plan or review claims full, whatever the setting.

### R2-2 — feasibility (minor)

**Problem**

> Rule 8 assumes an in-flight goal loses only one try and that 'the second try passes'. A goal that has already used max_tries - 1 tries would stop with a finding on that first DEPTH failure. The design also doesn't show that an IN SESSION worker that got the old prompt is re-shown the new prompt on retry.

**Remedy**

> Say that a goal on its last try can stop over this, and that the owner can resume it. Confirm the retry path re-prints the step prompt for both headless and IN SESSION workers.

### R2-3 — clarity (minor)

**Problem**

> A finding is raised only when the goal stops on its last try. The design doesn't say whether a failed try that isn't the last one shows its reason on the board. The Assignment ('watch one goal fail a condensed review on the board') depends on that.

**Remedy**

> Say where a non-final depth failure appears on the board, for example on the worker line or in the try count with its reason, or point the Assignment to the goal log.

### R2-4 — completeness (minor)

**Problem**

> The marker search covers all reply text before STEP:, and that includes the DEPTH: line and any echoed prompt text. A marker like 'full', or a common word like 'tests', matches trivially, which weakens the check. The design names only the 'worker reads flow file' limit.

**Remedy**

> Exclude the DEPTH: line from the search, and add a note that markers should be distinctive strings a condensed run would not produce.

### R2-5 — clarity (minor)

**Problem**

> This is asserted without naming the readers that were checked. A toy test can exercise the known readers, but it can't prove that no reader rejects unknown keys.

**Remedy**

> List the config readers that were checked (or the grep that was used), and have the toy test run the real loaders against a config that includes `_help`.
