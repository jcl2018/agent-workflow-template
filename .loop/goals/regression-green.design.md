# Design: regression-green

Status: shaped by office-hours with the recommended answer at every question. Nothing approved, merged or pushed.
The goal's done lines are frozen; this design meets them.

## Problem

The nightly GitHub regression run is red on 7 rows (`wiki-release`, `wiki-release-pycache`, `adopt-set-1` to `adopt-set-5`; issues 58, 68-72, 74),
and the health check fails on two criteria with no test, DEL-4 and REG-3.

## What was found

- **Cause, reproduced locally.** `PYTHONDONTWRITEBYTECODE=1` is set in the owner's shell and not on GitHub. Without it the earlier toy
  tests leave `skills/*/scripts/__pycache__/` in the checkout. `dev/package.py` then refuses the package (`__pycache__` is in `BAD_DIRS`),
  so `test-adopt.sh` stops at `v1 package refused` (`env -u PYTHONDONTWRITEBYTECODE bash dev/toy/test-adopt.sh SET-4` fails here, passes with the variable set).
  That is why SET-1 to SET-5 all go red together: the SET-1 issue body shows SET-1/2 passing, then the shared package step failing.
- **wiki-release / wiki-release-pycache** fail on GitHub with an empty failure body (the row's own `echo ... >&2` shows PASS lines on stderr only when the row runs). Locally with the variable unset, `test-wiki.sh` passes in a clean tree.
  So the failure on GitHub is not yet explained by the same cause; it is order- or environment-dependent (git identity, `gh`, branch name, or the pycache state left by earlier rows).
- Issue 58 is the old defect for this; the `wiki-release-pycache` row already exists with a link to it, seen failing.

## Approach (recommended, taken)

1. **Reproduce CI, not the owner's shell.** Add a way to run the suite the way GitHub does: `env -u PYTHONDONTWRITEBYTECODE`, a clean checkout, no global git identity, branch not `main`-assumed.
   Use it to find the real wiki-release cause before changing anything. Fix the cause where it lives, not by setting the variable in the workflow.
2. **Fix the pycache cause at the root.** Make the packaging step ignore or not see bytecode folders the tests themselves create: the toy tests that run skill scripts run them with `PYTHONDONTWRITEBYTECODE=1`
   (or `mk` in `test-adopt.sh` copies skills without `__pycache__`). Keep `package.py` strict, since a real pycache in a shipped package should still be refused.
3. **Make the run one command (REG-3).** `regression.py run` already runs the rows; the workflow embeds its own copy of that loop in python. Replace the inline loop in `.github/workflows/regression.yml`
   with a call to `regression.py run` plus a small issue-sync step, so me, the loop and GitHub run the same code. The workflow text is generated by `workflow-regression`, so change the generator and `workflow-setup`'s copy together.
4. **Criterion tests for DEL-4 and REG-3, seen failing once.**
   - DEL-4: row over the pull request body (`dev/toy/test-defect.sh pr-body` already checks the steps; extend or add a case asserting the body carries the done lines, the plan, the Verify by hand steps and each step's result). Link it to DEL-4.
   - REG-3: row asserting the workflow file calls the same command a local run uses (no inline copy of the loop) and that the command's output is the same locally and in the workflow's env. Link it to REG-3.
   - Each is recorded red first (break the code or point at the old workflow, run, record `seen_red`), then green after the fix, per REG-2.
5. **Close the issues by themselves.** No manual closing: the workflow already closes an open issue when its row passes. Done line 1 is met when the next run is green.
6. **Checks.** Repo checks, the full suite locally with the variable unset, and `criteria.py render` so DEL-4 and REG-3 stop showing "not enforced".

Touches stay inside the goal's list: `.loop/regression.tsv`, `.github`, `skills/workflow-regression`, `skills/workflow-setup`, `skills/workflow-release`, `dev/toy`.

## Alternatives not taken

- Set `PYTHONDONTWRITEBYTECODE=1` in the workflow: smallest diff, but hides the fault and leaves REG-3 (same way everywhere) false.
- Add the failing rows to `.loop/regression-known.tsv`: turns the run green without fixing anything; against done line 1.

## Risks

- wiki-release has no reproduced local failure yet; step 1 may find a different cause than pycache. The run log on GitHub is truncated by the row's own redirects, so the row should print its failing line to stdout.
- A change to the generated workflow reaches adopting repos through `workflow-setup`; the SET tests cover that.
