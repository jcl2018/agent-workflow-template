## Implementation plan

# Plan: local-schedule

Source: .loop/designs/local-schedule.md (APPROVED). Goal: .loop/goals/local-schedule.md. The seven done lines there are frozen; this plan meets
them and changes none. Where this plan and the design differ, this plan wins (each difference is named in "Corrections to the design").

## 1. What gets built, in one paragraph

One user launch agent (`com.workflow-loop.schedule`, no root) fires on the owner's Mac. Its `tick` walks a registry of repos kept outside every repo
and, for each repo that is due, runs health (all rule groups, the judge through the owner's own `claude` login), files the findings, runs the full
regression for a private repo, and posts the digest. GitHub no longer has a health workflow at all. A public repo keeps `regression.yml` unchanged and gains a separate generated `regression-pr.yml` that runs only the affected rows on a `pull_request` or a branch `push`. A private repo gets no GitHub regression; its goal's pr lane posts its real result
as commit statuses named after every required check, so the merge needs no click and no bypass.

## 5. Corrections to the design (found by reading the code)

1. `STALE_WORKFLOW` is not in health.py. It is `automation.py cmd_workflow --check`. The health rule that reads health.yml is `scheduled` in rules.py
   (`for name in ("regression.yml", "health.yml")`). That rule is rewritten (part 7); health.py is untouched.
2. `regression.py run --reuse` does NOT give the REG-4 selection in GitHub: it needs a recorded run in the git common dir, and a fresh checkout has none, so it
   runs FULL. The selection a fresh checkout can use is `regression.py run <ci_levels> --reuse --tier goal` (tiers.plan: rows the change reaches since the
   merge-base with origin/<base>, needs `fetch-depth: 0`). The push/pull_request step uses that.
3. The Actions suite-time artifact fetch lived in health.yml ("Fetch the newest full-suite time"). With health.yml gone, a public repo's Mac health
   run would show the full-suite time as unknown. The tick takes over that fetch for a public repo (about 600 bytes, in workflows.py `tick`).
4. The digest's regression row (`regression_line`) reads `gh run list --workflow regression.yml`. A private repo has none. The tick passes the Mac run's
   result line in env `DIGEST_REGRESSION` and `regression_line` returns it when set.
5. `rounds.order()` treats a non-numeric run id as oldest, and `created(run)` calls `gh run view <id>`. The local run id is the 12-digit UTC minute
   `YYYYMMDDHHMM`: numeric (so ordering and "same run twice posts nothing" work), larger than any Actions run id (so a local round is never "older"),
   and `created()` parses it directly instead of calling gh. A local id is exactly 12 digits starting `20` (`rounds.is_local`); `created()` parses only those, `round_cost` returns the local cost line for them, and every other numeric id stays an Actions run id. A repo whose health round once ran in Actions keeps its older Actions ids; local ids sort after them, so nothing posts twice and no local round reads as older. Switching `regression_runs` changes nothing about ids.
6. The design adds a `Last ran` line to every health issue body. Rejected: a changing line makes `file` rewrite every open issue every 4 hours. The line goes in
   the digest comment only; done line 4 says "the issue or digest", so it is met.
7. `mail.py` reads the address and keys only from environment variables; there is no private settings file for them. The tick reads
   `<schedule home>/mail.env` (KEY=VALUE lines, outside the repo; refused with `MAIL_ENV_MODE` unless the mode is 0600) and passes those variables to `mail.py send` only; no file, no mail,
   and the digest's email row says `not set up (MAIL_NOT_SET_UP)`.
8. A statuses hook only on the lane's head is not enough. `merge.py` accepts a PR head that moved by wiki-page commits after the lane (`wiki_only`), and a
   status belongs to one sha: the moved head would have none and a private repo would block. merge.py re-posts the lane's result for the new head (only on the
   `wiki_only` path, where merge.py already proved no row's code moved), through `autorelease.restatus`.
9. The release PR's head is built in a temporary worktree that `push_release_commit` removes; its sha is the function's return value (merge.py `start`
   discards it today). `start` keeps it; `autorelease.release_statuses` runs the affected rows in a new temporary detached worktree at that sha and posts the real result.
10. Every existing toy test that runs setup would now run `local install` against the real home folder. `dev/toy/reap.sh` (sourced by every toy test)
    exports `LOOP_SCHEDULE_HOME` and `LOOP_AGENTS_DIR` into a per-test temp folder, removed at exit. No production branch is keyed on a test marker.
11. One shared agent cannot honor a different `health_cron` per repo. The agent's calendar is the union of every registered repo's slots; `tick --scheduled`
    runs a repo only when it is due (last tick start older than its interval minus 60 minutes (or half the interval if smaller)), which also makes the one coalesced fire after sleep catch up.
12. Unknown visibility is not public. `regression.py workflow` and setup write no regression workflow when visibility cannot be read, and say why
    (a wrongly written pull_request check would block a private repo; a missing public workflow only needs a rerun). Where the regression runs is one
    recorded fact, not a probe every caller repeats: a new repo setting `regression_runs` (`actions`, the default, or `mac`), written by setup from the one
    live `private.py visibility` answer (`mac` only for a private repo). `regression.py workflow`, the tick and the health rule `scheduled` all read the setting,
    so the health check stays offline and deterministic. `regression.py workflow --visibility public|private` overrides it for builders and tests (no network).
    Only the statuses code probes live every time, because posting on a public repo is the one irreversible mistake.
13. Docs: `local stop` does not exist; the design's Usage list named it. The commands are `local install|uninstall|status|plist|tick`; stopping is the owner's
    `launchctl bootout` line, printed by `install`.
14. `private.py` is the private-NAME scan; the status code is a different concern living there only because every other delivery script is full. Its docstring
    is retitled to say it holds both (the private-name scan and the private-repo statuses). Callers from other skills use the loader pattern
    autorelease.py already has (`sibling("private")`) or the CLI by path.

## 6. Parts

### Part 1. Commit statuses (done line 7)

`skills/workflow-delivery/scripts/private.py`, anchored lines (the red breaks in section 9 target them):

- `repo_is_private(top)`: `gh repo view --json isPrivate -q .isPrivate`, 20 s timeout; `"true"` -> True, `"false"` -> False, anything else or error -> None.
- `required_checks(top, base)`: returns `(contexts, bound)` or None when unreadable. Reads `gh api --paginate repos/{owner}/{repo}/rules/branches/<quoted base>` (rules of
  type `required_status_checks`, each `parameters.required_status_checks[]` with `context` and `integration_id`) and
  `gh api repos/{owner}/{repo}/branches/<quoted base>/protection` (one call: `required_status_checks.contexts` and `.checks[]` with `context`, `app_id`, and `required_pull_request_reviews` for the review advice). HTTP 404 on
  the classic endpoint means not protected (empty, readable); any other error means unreadable. A context whose integration or app id is neither null,
  0 nor -1 is `bound`: a plain status cannot satisfy it, so it is returned in `bound`, never posted. `contexts` is the sorted union minus `bound`.
- `post_statuses(top, head, ok, contexts)`: one `gh api -X POST repos/{owner}/{repo}/statuses/<head>` per context with `-f state=`, `-f context=`,
  `-f description=`. The state line is exactly `state = "success" if ok else "failure"`. Description: `workflow-loop pr lane, local run, <UTC date>`
  (under 140 characters; `, <k> rows left to the schedule` is added when the lane left k rows to the scheduled suite), no target_url. Each POST retries up to 2 more times on a 5xx or network error (never on a 4xx). A failed POST prints `STATUS_FAILED <context>: <http status> <scrubbed gh error, 160 chars> (STATUS_FAILED)`; after the loop one line says `posted k of n; failed: <list>; safe to rerun: private.py statuses --head <sha> --ok`, and the function returns False; it never turns a failure into a success.
- `pr_result(top, base, head, branch, ok)`: the only entry other scripts call. Order: `repo_is_private` (not True: print `STATUSES none: public or unreadable
  visibility` and return) -> `required_checks` (None: `STATUSES none: required checks unreadable: <endpoint> <http status>; Fix: gh auth refresh -s repo (STATUSES_UNREADABLE)`; empty: `STATUSES none: no required checks`) -> when `ok` is False,
  require `git ls-remote origin refs/heads/<branch>` to equal `head` (else `STATUSES none: head not on the remote`, nothing posted) -> `post_statuses`. One result line:
  `STATUSES posted <success|failure> for <contexts> on <sha12>`; `bound` names print `BLOCKS: required check <name> is bound to an app; a plain status cannot satisfy it`. `required_checks` also reports, as advice `BLOCKS:` lines only, a rule that no status can satisfy (a `pull_request` rule or classic protection needing approving reviews, a merge queue, `strict` up-to-date branches, required linear history, required signed commits, required conversation resolution); it never posts for them.
- CLI (also what the toy tests drive): `private.py statuses --head SHA --ok|--fail [--base B] [--branch NAME]`, `private.py required [--base B]` (prints the
  contexts, one per line, then `BLOCKS:` lines), `private.py visibility` (prints `private|public|unknown`).

`goal.py cmd_pr`, two one-line calls: after `PR` is created (the push has happened, so the head exists remotely) `private.pr_result(root(), config()["base"], head, state["branch"], True)`;
in the `gate == "fail"` branch `private.pr_result(..., False)`. `head` is the value after `role.bump_version` (the sha the lane tested). A failed lane is not pushed (unchanged), so
`pr_result(..., False)` posts only for a rerun of a head already on the remote; otherwise nothing posts and nothing can read as success. The head is on the remote when an earlier passing `goal.py pr` pushed it and the pr is rerun on the same head (a flaky row, an environment change); GitHub keeps the newest status per context, so the new `failure` replaces the earlier `success`. `st-rerun-failed-head` builds exactly that: a pass and push, then a failing rerun. A failing POST on the success path
prints `STATUS_FAILED` and `NEXT: the pull request will not merge until the status posts; run private.py statuses --head <sha> --ok`; the goal still ends `done` with the PR open and its state records `statuses: failed`, but `goal.py pr` exits 5 (not 0), so no flow or agent reads a pull request that cannot merge as clean; exit 5 is in the Messages table.

`autorelease.py`: `restatus(top, cfg, state, head)` calls `private.pr_result(top, base, head, state["branch"], True)` (only invoked on merge.py's `wiki_only` branch); `release_statuses(top, cfg,
branch, sha)` makes a detached worktree at `sha` (the same temp-worktree recipe as `push_release_commit`), runs `regression.py run <ci_levels or nightly> --reuse --tier goal`
there, sets `ok` from the exit code, removes the worktree and calls `pr_result(top, base, sha, branch, ok)`. A release commit that changes only VERSION and CHANGELOG reaches no row
(`NO_EFFECT`), so it is a fast real pass; a row failure is a real `failure`. The run is capped at 20 minutes; a timeout or any non-zero exit posts `failure` (never success); rows the budget leaves to the scheduled suite (`LEFT`) do not fail the run, exactly as in the goal's own lanes. With no recorded run, `tiers.plan` selects by files changed since the merge-base with `origin/<base>`, so a release commit reaches no row. The result is recorded in the release state (`release_status`); `advance` re-runs `release_statuses` whenever it is not `success`, so a flaky failure is retried on the next merge.py run. `merge.py`: `start` keeps the sha (`version, sha = ...`) and calls `autorelease.release_statuses(top, cfg, branch, sha)`
after `gh pr create`; immediately before the `gh pr merge` call, when `tested` was moved by the `wiki_only` branch (`tested != state.get("pr_head")`), merge.py calls `autorelease.restatus(top, cfg, state, tested)`; every refusal (HEAD_MOVED, BASE_MOVED, the private scan, the requirement hold) comes first, so no status is posted for a head the same run then refuses. merge.py gains only these two lines and pays their bytes from comments.

No bypass: merge.py's `gh pr merge` calls are unchanged (`--merge`, optional `--match-head-commit`); no `--admin`, no `--auto`.

### Part 4. The launch agent, registry and due test (done lines 1, 4)

All in `skills/workflow-health/scripts/workflows.py` (docstring retitled: the local schedule's texts and tick). Homes, each overridable by env so a toy never touches the real home:
`LOOP_SCHEDULE_HOME` (default `~/.workflow-loop/schedule`, mode 0700), `LOOP_AGENTS_DIR` (default `~/Library/LaunchAgents`), `LOOP_LAUNCHCTL` (default `launchctl`; one `launchctl(*args)` helper runs it).

- Registry `<home>/repos.json`, mode 0600, outside any repo: `{"repos": {"<key>": {"path": ..., "origin": ..., "last_run": ..., "last_ok": ..., "regression": ...}}}`. Key = first 12 hex of sha1 of the origin normalized to `host/owner/repo` (ssh, https and `.git` forms of one repository give one key). A second clone of the same origin is refused (`REFUSED: <path> is already registered for this origin; run local uninstall there first (SCHEDULE_DUPLICATE_ORIGIN)`); a repo with no `origin` remote is refused (`SCHEDULE_NO_ORIGIN`).
  Writes are atomic (temp file + rename) under a mkdir lock with a 10-minute stale timeout. The tick never scans the disk; a path that has vanished is named once per run and skipped.
- `plist_text(program, slots)`: `plistlib.dumps` of `{Label: com.workflow-loop.schedule, ProgramArguments: [python3 abs, <abs path of automation.py>, local, tick, --scheduled], StartCalendarInterval: [{Hour, Minute}, ...],
  RunAtLoad: False, ProcessType: Background, EnvironmentVariables: {PATH}, StandardOutPath/StandardErrorPath under <home>/log}`. Slots are the union over registered repos of the slots of each `health_cron`.
  Only `M */N * * *` (N divides 24) and `M h[,h...] * * *` are read; any other shape makes `install` refuse with `REFUSED: health_cron <value> is not an every-N-hours or fixed-hours shape. Fix: edit .loop/config.json (SCHEDULE_CRON)`.
  `off` registers the repo as disabled (tick skips it, says so). PATH is built from the directories holding the install-time `gh` and `claude` (found with `shutil.which`) plus `/usr/bin:/bin`.
- `local install [--root R]`: first refuses a program path that will vanish: automation.py under a `loop/worktrees/` folder or the system temp
  (`REFUSED: run install from the installed skills or the repo's main checkout (SCHEDULE_PROGRAM_PATH)`); then registers this repo, writes the plist if its text changed, prints `SCHEDULE installed for <key> (<n> repos)`, the exact `launchctl bootstrap gui/<uid> <plist>` line, the stop line
  (`launchctl bootout gui/<uid>/com.workflow-loop.schedule`) and, if `launchctl print` says it is loaded and the plist changed, `RELOAD: bootout then bootstrap`. It loads the agent only with `--load` (an explicit owner flag that runs the printed bootstrap line through the same `launchctl` helper; setup never passes it). It ends with the next commands (bootstrap unless `--load` was given, `status`, `tick --dry-run`) and the status block with the next due time. Off macOS it refuses with `SCHEDULE_PLATFORM` (`plist`, `status` and `tick` still work).
- `install` first removes any entry registered for the same path under another key (an origin that changed), and `status` prints `ORIGIN_CHANGED: run local install again` when an entry's recorded origin differs from the repo's.
- `local uninstall [--root R]`: removes this repo's entry; when the registry is empty it runs `launchctl bootout` (a "not loaded" answer is fine) and removes the plist; otherwise rewrites the plist for the remaining repos and prints `NOTE: the agent stays loaded for <n> other repos`.
- `local status`: lists entries with `last_run`, `last_ok`, when each is next due and `OVERDUE` when it is past due by an interval, the plist path, whether it is loaded and whether its program path still exists
  (`PROGRAM_MISSING: run install again`), plus `gh: logged in|not`, `claude: found|missing` (read-only probes); each check prints `OK <check>` or `FIX <check>: <command>`, `--json` prints the same as one object for an agent, a skipped judge shows from the first skip (`JUDGE_SKIPPED <n> ticks`) and offline runs show `SKIPPED_OFFLINE <n> ticks in a row` with the cause. `local plist`: prints the plist text for the current registry.
- `due(entry, interval, now)`: True when there is no `last_run` or `now - last_run >= interval - slack`, where slack is the smaller of 60 minutes and half the interval and `last_run` is the tick's start time shared by every repo of that tick. `interval` is N hours for `M */N * * *` and, for fixed hours `M h1,h2,...`, the largest gap between adjacent slots around the clock (a single fixed hour means 24 hours); `MISSED` uses the same interval. `tick --scheduled` runs only due repos; `tick` by hand runs every registered repo (`--repo PATH` one);
  `tick --dry-run` prints each repo's plan (due or not, which steps, which skills) and writes nothing: no worktree, no gh write, no registry change, no log line.
- A registry that cannot be parsed is never overwritten: `install`, `uninstall` and `tick` stop with `REGISTRY_UNREADABLE <path>: fix or remove it` and exit 1 (an empty read would drop every repo).
- `<home>/log/tick.log` is trimmed to its last 200 KB at the start of each tick, so it cannot grow without bound. Every captured child stderr line passes one scrub helper (token patterns, `Bearer` headers, URLs with credentials) before it reaches the log, the digest or the screen; private.py has its own two-line scrub for gh error text.

### Part 5. What a tick does for one repo (done lines 1, 4, 5)

`workflows.tick`, sequential over repos, each under a mkdir lock `<home>/<key>.lock` (stale after the repo cap plus 5 minutes) and a per-repo wall-clock cap (`LOOP_TICK_MINUTES`, default 60) and a cap for the whole tick (`LOOP_TICK_TOTAL_MINUTES`, default 180), which every child's timeout is cut to; repos run oldest `last_run` first, and a repo the tick does not reach keeps its old `last_run`, so the next fire runs it first. Every child runs in its own process group (`start_new_session=True`) and a timeout kills the whole group (`os.killpg(`), so a hung judge or regression cannot leave orphans past the cap. Each lock file holds its owner's pid and a stale lock is taken over only when that pid is dead (`os.kill(pid, 0)` fails); otherwise the tick skips with `SKIPPED <key> (locked by pid <n>)`. The registry records each repo's last duration and `status` shows it. When the remaining time reaches zero the step is skipped with `SKIPPED <step> (cap reached)`; only the digest (given at least 120 seconds) and the registry update still run, and `last_ok` is false. A `mail.env` of the wrong mode is refused: no mail is sent and the email row says `not set up (MAIL_ENV_MODE)`.

1. Probe, in the repo path: `gh auth status` then `gh api rate_limit`, 20 s each. Failure: one line `SKIPPED <key> (gh auth status failed) Fix: gh auth login (SCHEDULE_AUTH)` or `SKIPPED <key> (gh api rate_limit failed) Fix: check the network (SCHEDULE_OFFLINE)` to `<home>/log/tick.log` and stdout; no issue changed; `last_run` untouched; the registry counts the skip; exit 0 with `--scheduled` (launchd must not throttle the job) and exit 3 when run by hand.
2. Checkout without touching the owner's tree: `git fetch origin <base>` (60 s), then a detached worktree of `origin/<base>` at `<home>/<key>/tree`, `git worktree prune`, reset (`checkout --detach -f`, `clean -fdx`) on every run. Skills come from the tree's `skills/` when present, else the
   skills beside the running automation.py; the log line says which (`SKILLS: checkout|installed`). The tree lives outside `loop/worktrees/`, so the hygiene `worktrees` rule ignores it (lean.py:243-245 skips any worktree not under that folder).
3. Child environment: the owner's, minus `ANTHROPIC_API_KEY` and `CLAUDECODE` (so the judge cannot take an API key and cannot mistake the tick for a session); plus `DIGEST_RUN=<YYYYMMDDHHMM UTC>`, `HEALTH_REPORT=<tick file>`, `DIGEST_LAST` and `DIGEST_REGRESSION`.
4. Health: `health.py check` (every group; report to the tick file), `health.py file` (the default groups, as the workflow filed them plus the groups only this machine can read), `health.py judge` (output appended to the log; a missing `claude` or login makes the
   judge `skipped` and the report says so, as today). A failed read of issues changes no issue; a failed filing is named in the digest (unchanged rules).
5. Regression, when the `regression_runs` setting is `mac`, or is unset and `private.py visibility` says private (the log then says `NOTE: regression_runs unset; run setup to record it`): `regression.py run <ci_levels or nightly> --live --timeout 900` in the tree; any other repo instead downloads the newest `suite-time` artifact of regression.yml into the git common dir's `suite-times.tsv` (the old health.yml step, ported).
   `regression_cron` of `off` skips the Mac regression. The tick also probes `private.py visibility` every run; when it disagrees with a recorded `regression_runs`, the digest carries `DRIFT: regression_runs says <x> but the repo is <y>; run setup` and the setting still decides what runs.
6. Digest: `automation.py digest --live`; then mail, only if `<home>/mail.env` exists (its variables go to `mail.py send` and nowhere else), else the row says not set up.
7. The tick runs only merged base code (the tree is `origin/<base>`), never a PR head, and rows run with the owner's login exactly as the existing local lanes do; no new exposure is added.
8. Registry update: `last_run` (the tick's start time, shared by every repo of that tick), `last_ok` (every step ran), `regression` (the RESULT line), `judge_skipped` (consecutive ticks whose judge was skipped; `last_ok` ignores it, but the digest and `status` say `JUDGE_SKIPPED <n> ticks in a row` from 3). A crash prints `TICK_CRASH <key>: <ExceptionName>; trace <home>/log/trace-<key>.txt. Fix: run local tick --repo <path> by hand (TICK_CRASH)`, writes the scrubbed traceback to that file, names the failure in the digest and makes the tick exit 1; the next repo still runs.

## 7. Review decisions that shaped the parts

Premises the design relies on, so a change to any of them reopens it: one Mac per owner, a solo owner, the Mac is on often enough for a 4-hour cadence, and CI results are read through commit statuses and the digest.

## 11. Risks and answers

- Size margins: measured after every edit; the fallback order is in section 4. `ls-size-budget` fails the lane if a ceiling is broken.
- A required check that is an Actions check run, not a status, cannot be satisfied by a lane: setup names it (`BLOCKS:`); the owner removes it (the Assignment).
- GitHub may treat a status and a check run of the same name differently: advice `NOTE:` in setup; private repos have no regression workflow, so the clash is limited to other workflows.
- launchd fires at local time; DST shifts only move a slot, coalesced anyway. Power off runs nothing; sleep catches up at wake (`due`).
- The agent runs in the login session: the Mac must be logged in for the keychain; documented.
- A tick that hangs: per-repo wall-clock cap, lock stale timeout, child timeouts cut to the remaining time.
- A commit pushed to the pull request after the lane (other than a wiki-only one) leaves its head with no status: merge.py already refuses it with HEAD_MOVED; the fix is `goal.py pr`, which posts for the new head.
- A required context that is also an Actions job name: the lane posts it anyway (done line 7: the lane is the check); setup's `NOTE:` names the clash and the owner removes the Actions job or the required check.
- `health.py file` from the tick and from an owner session are idempotent by issue marker, as when it ran in Actions; no new lock.
- A pr whose lane passed but whose status POST failed would block merge silently: `STATUS_FAILED` plus the `NEXT:` line and a goal journal entry make it loud; `private.py statuses --head SHA --ok` is the hand fix.
