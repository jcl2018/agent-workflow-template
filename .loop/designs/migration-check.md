# Design: migration-check, one command that judges a repo's migration

Generated by /office-hours on 2026-11-12

Status: DRAFT
Mode: Intrapreneurship (owner-run internal tooling; every question answered with the recommended option, no condensing)

The goal's done lines (`.loop/goals/migration-check.md`, 1 to 11) are frozen. This design meets them and never changes them. Nothing below is an owner decision about a done line.

## Problem Statement

Adopted repos drift. A repo set up before v0.27.17 has no Settings or Automation blocks on Home and README, because re-running setup says NO CHANGE and update never inserts them. A repo can carry no `template_version`, an old PRD format, no local schedule task, a routine with no Runbook, or wiki pages that no longer have a source page. Nothing today says "this repo is fully migrated", and nothing tells a person starting work in a lagging repo.

## Demand Evidence

The owner asked for it twice (goal header, 2026-11-11): to prepare a full migration check before adoption is done, to migrate all existing repos and tighten them, and how to suggest and enforce an update when working in another repo. A steward session reported "no .loop/config.json on its base branch" for a repo whose main had it (done line 7). render-readme-guard found the pre-v0.27.17 hole (done line 11).

## Status Quo

- `update.py --check` reports only the version and LOCAL FIXes; it lists no files and no settings.
- `entry.py check` prints LAG (never fails); `board_page.template_lag` lists lagging followed repos in Issues; health's `template-version` rule only compares this repo's VERSION with its CHANGELOG.
- `docs.py check` already holds the PRD format, stale-block (`render.stale_blocks`) and Runbook (DOC-16, `deployments.owed`) checks, but nobody runs them as one verdict for a migration.
- The wiki's published pages are never compared with `docs/wiki`: `docs.py publish` writes pages and never removes one.

## Target User and Narrowest Wedge

The operation session and the owner. Wedge: one read-only command whose exit code is the migration's done test, built by composing the checks that already exist, plus the five things nothing checks (local task, automation entries, published-page orphans, template-version nag, block insertion).

## Constraints

- Package cap: the skills package is at 99 of 99 counted files (96 under skills/ plus listing.json, README, LICENSE; `dev/package.py` MAX_FILES 99). NO new file under skills/. No exception is needed (see Approach).
- Every script under skills/ stays at or under 20,480 bytes. Sizes now: update.py 20458, sync.py 20354, setup.py 20340, survey.py 20207, seed.py 20174, goal.py 19726, render.py 19882, settings.py 19243, rules.py 18502, agents.py 18275, workflows.py 17778, defects.py 7659, board_page.py 15459, operate.py 9440, entry.py 15031, report.py 16816. update.py, sync.py, setup.py, survey.py and seed.py are full: this design adds at most 110 bytes to setup.py, nothing to update.py, survey.py and seed.py, and removes bytes from sync.py.
- A parallel goal (operator-setup) edits skills/workflow-setup and docs/wiki/Setup.md. Own code, own function, named edit points (below); expect to merge main before the PR.
- migration-check writes nothing in the repo (done line 3). Not editing Automation.md wording or any Reviewed requirement.

## Premises

1. One engine, two callers: `setup.py migration-check` and health's Adoption group call the same function, so their gaps cannot disagree (done lines 1, 2).
2. Compose, do not copy: version, files, settings, blocks, PRD format and Runbook gaps come from the existing read-only checks (`entry.py`, `docs.py check`, `settings.py`, `render.py`); only new kinds get new code.
3. Warn, never block, except goal.py new on a differing major (done line 5); the migrate goal itself is exempt from that refusal or the repo could never migrate.
4. `update.py --check` judges the base branch (origin/base first, never the checkout it happens to be on; done line 7). `migration-check` judges the working tree it runs in, which is the PR's content: in a migrate goal's worktree it can pass before the merge; on a base-branch checkout, the health tick's detached tree and a merged repo the two are the same.
5. The check is offline-tolerant: a wiki or registry it cannot read is a named gap, never a crash.

## Approaches Considered

### Approach A (minimal): print the existing checks one after another
Effort S. No new rule kinds. Rejected: cannot meet done lines 8, 9, 11 (nothing checks local task, orphans or inserts blocks) and gives no single exit code.

### Approach B (recommended): one engine inside workflow-health's defects.py, thin callers
Effort M. Engine `migration_gaps(root, online=True)` returns `[(code, subject, what, fix)]`. `setup.py migration-check` (dispatch in agents.py) prints them and exits 0 only on none. Health's `migration` rule (Adoption) maps each gap to one WARN row. The pieces that must exist for the gaps to be closable (version stamp, automation entries, block insertion) go in the functions that already own them. No new file.
Reuses: `entry.installed/lagging`, `docs.py check`, `render.stale_blocks/refresh`, `workflows.load/key_of/slots`, `docs.py clone/wiki_url`, `deployments.owed`, `controls.CONTROLS` auto-import from defects.py.

### Approach C (ideal, rejected): a new `migrate.py` with its own state and an apply mode
One owner-facing command that checks and fixes. Rejected: file 100 of the cap (no room for the next goal), and the fixing already belongs to `update --apply` plus the migrate goal; a check that also writes would break done line 3.

## Recommended Approach

Budget +11,000 bytes (hard stop 18,700 total). Fallback: move the wiki half (`wiki_gaps`) into `enforce.py` (5,490 bytes) as a lazy import.
2. Classes and exit codes. PR-closable codes (MIG_VERSION, MIG_FILES, MIG_SETTINGS, MIG_BLOCKS, MIG_AUTOMATION, MIG_RUNBOOK, MIG_FORMAT, MIG_CHECKS) can be closed by a pull request. State codes (MIG_TASK, MIG_WIKI_ORPHAN, MIG_WIKI_STALE, MIG_WIKI_UNREADABLE) live on the Mac or in the wiki and close only after the merge. Every gap, of either class, makes the exit nonzero (WIKI_UNREADABLE too, when the repo has a `.loop/docs.tsv` and an origin). `--pr` checks the PR-closable codes only; `--offline` skips only the three wiki codes. A repo with no `.loop/docs.tsv` has no wiki: no wiki, blocks, Runbook or format codes. On a host that is not a Mac (CI, Linux) MIG_TASK prints `SKIP MIG_TASK (not a Mac)` and is not counted, since the task can only live on the owner's Mac; in health a state-code gap is a WARN row and an unreadable wiki or registry is an INFO row, never a crash. Output, one line per gap: `GAP <CODE> <subject>: <what>. Fix: <one-line fix>`; last line `MIGRATION OK` or `MIGRATION: N gap(s)`; `--json` for callers; exit 0 only when none. Codes are stable: MIG_VERSION, MIG_FILES, MIG_SETTINGS, MIG_BLOCKS, MIG_AUTOMATION, MIG_TASK, MIG_WIKI_ORPHAN, MIG_WIKI_STALE, MIG_WIKI_UNREADABLE, MIG_RUNBOOK, MIG_FORMAT, MIG_CHECKS.

Nothing is read from update.py: it needs no read-only entry point.

A routine shown off or "not deployed" while its setting is not off is a gap: "off without an explicit off setting". Today `render.BUILT_IN` points health at `health.yml`, which no longer exists, so every repo would show health off: the declared entries override it ("an entry named like a built-in replaces it"), so render.py needs no wording change.

Health and the full regression run in that one task; so `regression_runs` must be `mac` whenever `regression_cron` is on (public or private), and MIG_FILES, MIG_CHECKS and the truth table agree: `regression.yml` is required only while regression runs in Actions. Fix lines name `automation.py local install`.
   - MIG_WIKI_ORPHAN and MIG_WIKI_STALE [9]: shallow-clone the published wiki into a temp dir (outside the repo, removed after; `docs.clone`, `docs.wiki_url`; toys use the local bare wiki next to the toy origin). Every `*.md` there that is not a source page (`read_map` rows plus generated pages) and is not `_`-prefixed is an orphan, named (retired, renamed, old format, or hand-made); every source page whose published text differs is stale, named. Fix for an orphan: `git rm <page>.md` in the wiki clone, commit, push (the owner said, 2026-11-11, to delete stale and old pages at migration; this check only lists; the owner removes them after the merge). Unreadable wiki, with a `.loop/docs.tsv` and an origin: MIG_WIKI_UNREADABLE (a gap in the CLI, an INFO row in health).
